前提知識

AWS Snowballファミリーの特徴について

AWS Snowball Edge：100TBの総容量（83TB利用可能）を提供し、コンピュート機能とS3互換ストレージを搭載しています。大容量データの物理転送に最適で、ネットワーク帯域幅の制約を完全に回避できます。オンボード処理能力により、データの前処理も可能です。

AWS Snowball（従来型）：50TBまたは80TBの容量制限があり、シンプルなストレージ転送に特化しています。60TBのデータには80TBモデルが必要ですが、容量に余裕が少なく拡張性に制限があります。

物理デバイス配送：通常1-2週間で配送・回収が完了し、ペタバイト規模のデータでも効率的な転送が可能です。

データマイグレーションサービスについて

AWS Database Migration Service（DMS）：同種および異種データベース間のマイグレーションに特化したサービスです。MySQLからAurora MySQLへの移行に最適化されており、スキーマ変換、データ型マッピング、継続的レプリケーション機能を提供します。S3をソースとしたマイグレーションも正式にサポートしています。

AWS Application Migration Service：物理サーバーやEC2インスタンスのリフト&シフトマイグレーション用サービスです。データベースの構造的マイグレーションには適しておらず、Aurora MySQLへの直接移行機能は提供していません。

AWS DataSync：ネットワーク経由でのデータ同期サービスですが、既存の帯域幅制約は解決できません。

ネットワーク接続オプションについて

AWS Direct Connect：専用線接続による高速・安定した通信を提供しますが、導入には数週間から数ヶ月の期間が必要です。継続的な利用では有効ですが、一回限りのマイグレーションではコスト効率が悪くなります。

インターネット接続の最適化：DataSyncやTransfer Accelerationなどの技術により効率化は可能ですが、根本的な帯域幅制約の解決にはなりません。

解くための考え方

この問題の解決には、大容量データ転送における帯域幅制約の回避が最重要課題となります。60TBという大容量データを現在の限られた帯域幅で1ヶ月かかる状況では、ネットワーク経由のソリューションは根本的な解決になりません。

物理的なデータ転送デバイスの活用が必要で、AWS SnowballファミリーがこのニーズにMATCHします。60TBのデータ容量を考慮すると、Snowball Edgeの100TB容量（83TB利用可能）が最も適切で、将来の拡張や一時的なデータ増加にも対応できます。

データベースマイグレーションの観点では、単純なファイル転送ではなく、適切なスキーマ変換とデータ型マッピングが必要です。AWS DMSはMySQLからAurora MySQLへのマイグレーションに特化した機能を提供し、S3をソースとした移行パターンも正式サポートしています。一方、Application Migration Serviceはサーバーマイグレーション用であり、データベース構造の変換には対応していません。

時間効率の観点では、Direct Connectの導入期間（数週間〜数ヶ月）を考慮すると、Snowball Edgeの配送期間（1-2週間）の方が圧倒的に短時間で済みます。

アーキテクチャ図の解説

オンプレミスデータ準備と物理転送

オンプレミス環境の60TB MySQLデータベースから、mysqldumpまたは同等のツールを使用してデータをエクスポートし、Snowball Edgeデバイスに転送します。Snowball Edgeの100TB容量（83TB利用可能）により、データ全体を余裕を持って収容でき、S3インターフェースを通じた高速ローカル転送が可能です。デバイスの物理配送により、帯域幅制約を完全に回避し、1-2週間でAWSデータセンターへの確実な転送を実現します。

AWS環境でのデータ処理と変換

Snowball EdgeからS3バケットにデータがアップロードされた後、AWS DMSがS3をソースとしてAmazon Aurora MySQLへのマイグレーション処理を実行します。DMSはMySQLからAurora MySQLへの最適化された変換機能を提供し、スキーマ変換、データ型マッピング、制約の移行を自動的に処理します。CloudWatchによる詳細な監視により、マイグレーション進捗とエラーハンドリングを確実に管理できます。

データ検証と本番切替

Aurora MySQLへのデータ移行完了後、包括的なデータ整合性チェックとパフォーマンステストを実施します。行数の照合、チェックサム検証、サンプルクエリの実行により、データの完全性を確保します。検証完了後、アプリケーションの接続先変更とDNS更新により、ダウンタイムを最小限に抑えた本番環境への切り替えが完了します。

他のソリューションとの比較

Snowball Edge + AWS DMSの組み合わせが他のソリューションより優れている理由は、時間効率とコスト効率の両立にあります。

Direct Connect接続は理論上高速ですが、導入期間が数週間から数ヶ月必要で、一回限りのマイグレーションでは投資対効果が低くなります。DataSyncによる最適化は既存帯域幅の制約を根本的に解決できず、1ヶ月という長期間の改善は限定的です。

Application Migration Serviceを使用するアプローチは、データベース構造の適切な変換ができず、Aurora MySQLへの移行に必要なスキーマ最適化や制約処理が不十分になります。Snowball Edge + AWS DMSの組み合わせにより、最短時間でのデータ転送と適切なデータベースマイグレーションが同時に実現されます。

実装の考慮事項

実装前にデータベースのエクスポート戦略を詳細に計画し、テーブル単位での分割や圧縮方式を決定する必要があります。Snowball Edgeデバイスへの転送時には、データ整合性を保つためのチェックサム生成と検証プロセスを組み込みます。

AWS DMS設定では、ソーステーブルとターゲットテーブルのマッピング定義、データ変換ルールの設定、エラーハンドリング戦略を事前に準備します。マイグレーション中の監視体制を整備し、CloudWatchアラームによる異常検知とエスカレーション手順を確立することが重要です。

本番切替時には、アプリケーション接続の段階的移行と、必要に応じたロールバック手順を準備し、ビジネス影響を最小限に抑制する運用計画が不可欠です。

前提知識
キャッシングソリューションの特徴について

DynamoDB Accelerator（DAX）は DynamoDB専用のフルマネージドインメモリキャッシュで、マイクロ秒レベルのレスポンス時間を提供し、DynamoDB APIと完全互換性があるため、アプリケーションコードの変更が最小限で済みます。最大10倍の読み取りパフォーマンス向上を実現できます

Amazon ElastiCacheは汎用的なインメモリキャッシングサービスで、RedisやMemcachedをサポートしますが、DynamoDBとの直接統合はなく、アプリケーション側でキャッシュロジックを実装する必要があり、運用複雑性が高くなります

容量モードの特徴について

オンデマンド容量モードは容量計画が不要で、トラフィックに応じて自動的にスケールしますが、予測可能なワークロードに対してはプロビジョンド容量モードより高コストになる場合があります

プロビジョンド容量モードは事前に読み取り・書き込み容量ユニットを指定し、一定の使用量がある場合はオンデマンドよりもコスト効率が良く、Auto Scalingと組み合わせることで負荷変動に自動対応できます

コスト最適化機能について

DynamoDB Auto Scalingはテーブルの実際の使用率に基づいて、プロビジョンド容量を自動的に調整し、無駄なキャパシティ費用を削減しながら必要な性能を維持できます

AWS Savings Plansには計算リソース向けのプランに加えてDatabase Savings Plansがあり、DynamoDBを含む複数のデータベースサービスを対象に、1年間のコミットメントでオンデマンド利用には最大18%、プロビジョンド容量には最大12%程度の割引が適用されます。ただし、いずれも読み取り要求自体を削減する仕組みではないため、本シナリオのようなキャッシュ最適化が必要なケースでは単独での効果は限定的です

解くための考え方
この問題では、コスト削減という明確な目標に対して、複数の技術的要素を組み合わせた最適解を見つける必要があります。まず、現在のワークロードパターンを分析すると、限定されたキーセットが繰り返し検索されるという特徴から、キャッシングによる読み取り最適化が非常に効果的であることが分かります。
DynamoDBの読み取り容量ユニット消費を削減することで、直接的なコスト削減を実現できます。次に、容量モードの選択について考えます。毎日決まった時間に大量データが書き込まれ、日中はバーストパターンの読み取りが発生するという比較的予測可能なワークロードであるため、オンデマンド容量モードよりもプロビジョンド容量モードの方がコスト効率が良いと判断できます。
Auto Scalingを組み合わせることで、バーストトラフィックに対する自動対応も可能になります。一方、Database Savings PlansはDynamoDBにも適用できるようになりましたが、その割引率はキャッシュ戦略や容量モードの最適化によるコスト削減効果に比べると限定的であるため、Savings Plansの購入のみに依存する選択肢は本シナリオの最適解とは言えません。
シーケンス図




シーケンス図の解説
データフローと読み取り最適化
アプリケーションからの読み取り要求は、まずDAXクラスターに送信されます。DAXは頻繁にアクセスされる限定キーセットをインメモリでキャッシュしているため、キャッシュヒット時はマイクロ秒レベルの低レイテンシでデータを返却します。キャッシュミスが発生した場合のみDynamoDBテーブルへの直接アクセスが行われ、結果は自動的にDAXキャッシュに保存されます。この仕組みにより、DynamoDBの読み取り容量ユニット消費を大幅に削減できます。
書き込み処理とスケーリングメカニズム
毎日深夜0時のバッチ処理による大量書き込みは、DAXをバイパスしてDynamoDBテーブルに直接実行されます。プロビジョンド容量モードとAuto Scalingの組み合わせにより、書き込み負荷の増加時は自動的に書き込み容量ユニットが増強され、処理完了後は適切なレベルに自動縮小されます。CloudWatchメトリクスを基に使用率を監視し、設定した閾値に応じてスケーリングが実行されます。
コスト最適化の実現
DAXによるキャッシュ効率とプロビジョンド容量の予測可能な料金体系、Auto Scalingによる無駄なキャパシティ削除の組み合わせが、総合的なコスト削減を実現します。オンデマンド容量モードと比較して、安定したワークロードパターンに対してはプロビジョンド容量モードの方が大幅にコスト効率が良く、DAXによる読み取り要求削減効果と相まって、大きなコスト削減効果を得ることができます。
他のソリューションとの比較
プロビジョンド容量モードのみの解決策では、容量料金は削減できても、繰り返される読み取り要求によるRCU消費は改善されません。一方、DAXを含む包括的な解決策では、キャッシュによる読み取り最適化とプロビジョンド容量による予測可能な料金体系、Auto Scalingによる無駄なキャパシティ削減が組み合わさり、多角的なコスト削減を実現します。
また、Database Savings PlansによってDynamoDBにも割引が適用できるようになりましたが、その割引率はDAXによる読み取り要求削減や容量モード最適化によるコスト削減効果と比較すると限定的であり、単独でのコスト最適化手段としては不十分です。ElastiCacheを用いる汎用的なキャッシング解決策と比較すると、DAXはDynamoDB専用に最適化されているため、統合の複雑性が大幅に軽減され、運用負荷とコストの両面でメリットがあります。
実装の考慮事項
DAXクラスターの実装時は、可用性向上のため複数のAZにノードを配置し、適切なノードタイプとクラスターサイズを選択する必要があります。プロビジョンド容量の初期設定では、過去のワークロード履歴とピーク時の要求を分析して適切な容量を設定し、Auto Scalingの閾値を調整してスケーリングの頻度を最適化します。
また、深夜バッチによる大量書き込みはDAXを経由せず直接DynamoDBに書き込まれるwrite-aroundパターンであるため、DAX経由のwrite-throughで生じる追加のネットワークホップやレイテンシーの影響を受けません。これはAWSが大量データのバルクロード時に推奨するアプローチですが、バッチ処理自体の書き込みスループット要件は事前に検証しておくことが重要です。運用開始後は、CloudWatchメトリクスを継続的に監視し、キャッシュヒット率やスケーリング動作を定期的に評価することで、さらなるコスト最適化を図ることができます。

AWS Storage Gatewayの種類と特徴

File Gateway：NFS/SMBプロトコルによるファイルレベルアクセス。ファイルを直接S3オブジェクトとして保存。オンプレミスアプリケーションからS3への透過的なアクセスを提供

Volume Gateway：iSCSIプロトコルによるブロックレベルアクセス。EBSスナップショットとしてS3に保存。Stored VolumesとCached Volumesの2つのモードを提供

Tape Gateway：VTL（Virtual Tape Library）として動作。既存のバックアップソフトウェアとの統合に特化

SQL Serverエクスポートの特性

データベースエクスポートはファイル形式（.bak、.sql等）で生成される

ファイルレベルでのアクセスと管理が必要

SMB/CIFSプロトコルによるWindows環境との親和性が重要

Amazon FSx for Windows File Serverとの比較

完全管理型Windowsファイルシステムサービス

解くための考え方

この問題の核心は、ファイルベースのデータベースエクスポートを最もコスト効率的にS3に移行することです。SQL Serverのエクスポートはファイルとして生成されるため、ファイルレベルでのアクセスが必要です。

AWS Storage Gateway file gatewayは、オンプレミスのファイルサーバーインターフェース（SMB）を提供しながら、データを直接S3に保存する設計となっています。中間ストレージが不要で、データパスが最もシンプルかつ効率的です。

Amazon FSxは高機能ですが、単純なバックアップ保存用途には過剰で、FSx自体のストレージコストとS3バックアップコストの二重負担が発生します。Volume gatewayはブロックストレージ用途であり、SMBファイル共有とは技術的に適合しません。

アーキテクチャ図


アーキテクチャ図の解説

透過的なファイルアクセスによるシームレスな移行

Storage Gateway file gatewayは、オンプレミスのSQL ServerからSMBファイル共有として認識され、既存のバックアップ処理を変更することなく利用できます。Direct Connect経由での高速転送により、200GBのデータベースエクスポートも効率的に処理され、書き込まれたファイルは即座にS3オブジェクトとして保存されます。

コスト効率的な直接S3保存

File gatewayは中間ストレージを経由せず、ファイルを直接S3オブジェクトとして保存するため、追加のストレージコストが発生しません。従来のローカルストレージからS3の低コストで高耐久性のオブジェクトストレージへの移行により、長期的なコスト削減と データ保護が同時に実現されます。

継続的な最適化とガバナンス

CloudWatch監視により転送性能とエラー状況を継続的に追跡でき、S3ライフサイクルポリシーにより古いバックアップファイルの自動アーカイブやIntelligent Tieringによるコスト最適化が可能になります。これにより運用負荷を最小化しながら長期的なコスト効率を維持できます。

他のソリューションとの比較

AWS Storage Gateway file gatewayを選択する理由は、技術的適合性とコスト効率性の両立にあります。Amazon FSxは高機能ですが、バックアップ保存という用途には過剰で、FSxストレージとS3バックアップの二重コストが発生します。

Volume gatewayはiSCSIブロックストレージ用途に設計されており、SMBファイル共有とは技術的に互換性がありません。SQL Serverのファイルベースエクスポートには、ファイルレベルアクセスを提供するfile gatewayが最適です。直接S3保存により、データパスがシンプルで管理も容易になります。

実装の考慮事項

実装時は、まずAWS VPC内にfile gatewayインスタンスをデプロイし、Direct Connect接続との適切なネットワーク設定を構成します。file gatewayのサイジングでは、200GBの夜間転送とピーク時のネットワーク帯域幅を考慮した適切なインスタンスタイプを選択します。

SMBファイル共有の設定では、SQL Serverからのアクセス権限とセキュリティ設定を適切に構成し、既存のActive Directory統合も検討します。S3バケットでは、適切なライフサイクルポリシーを設定してコスト最適化を図り、必要に応じてCross-Region Replicationによる災害復旧対策も実装します。

監視面では、CloudWatchメトリクスによる転送性能の継続的な監視と、S3イベント通知による転送完了確認機能を実装します。また、Direct Connect接続の帯域幅使用率も監視し、他のワークロードとの競合を避ける運用体制を確立することが重要です。

前提知識

ECS on Fargateでのスケーリング概念

Service Auto Scaling：ECSサービス内のタスク数を自動調整。CloudWatchメトリクス（CPU、メモリ、カスタムメトリクス）に基づく動的スケーリング。Target Tracking、Step Scaling、Scheduled Scalingをサポート

Cluster Auto Scaling：EC2ベースのECSクラスターでEC2インスタンス数を調整。Fargateでは基盤インフラが完全に管理されているため適用外

Application Load Balancer vs Network Load Balancer

ALB：レイヤー7（アプリケーション層）で動作。HTTP/HTTPSリクエストの内容を理解し、パス、ホスト、ヘッダーに基づく高度なルーティングが可能。WebSocketサポート、SSL終端、認証統合

NLB：レイヤー4（トランスポート層）で動作。TCP/UDPトラフィックを処理し、超低レイテンシと高スループットを提供。HTTPSはTCPとして処理されるため、アプリケーション層の機能は利用不可

ECSブルー/グリーンデプロイメント

CodeDeployとの統合：新バージョン（グリーン）環境の段階的デプロイ。トラフィックの段階的シフトと自動ロールバック機能。本番環境での無停止デプロイメント

ALB統合：ターゲットグループの切り替えによるトラフィック制御。ヘルスチェックベースの自動フェイルオーバー

解くための考え方

この問題の核心は、Fargateの特性とHTTPSアプリケーションに適したロードバランサーの選択、そして正しいスケーリング手法の理解です。

Fargateはサーバーレスコンテナプラットフォームで、EC2インスタンスの管理が不要な完全管理型サービスです。そのため、EC2ベースのクラスタースケーリングは概念的に適用されません。Service Auto Scalingがタスクレベルでの適切なスケーリング手法となります。

HTTPSアプリケーションにはApplication Load Balancerが最適です。パスベースルーティング、ホストベースルーティング、SSL終端等の機能により、マイクロサービスアーキテクチャで必要な高度なトラフィック制御が可能になります。

ブルー/グリーンデプロイメントでは、ALBのターゲットグループ機能を活用してトラフィックの段階的シフトを実現し、デプロイメントリスクを最小化できます。

アーキテクチャ図


アーキテクチャ図の解説

Application Load Balancerによる高度なトラフィック制御

ALBがHTTPSトラフィックを受信し、SSL終端を実行してセキュアな通信を提供します。ブルー/グリーンデプロイメント時は、ブルーターゲットグループで現在の本番トラフィックを処理し、グリーンターゲットグループで新バージョンの段階的検証を実行します。パスベースルーティングにより、マイクロサービス間の効率的なトラフィック分散が実現されます。

Fargateでのサーバーレススケーリング

各ECSサービスでService Auto Scalingが有効化され、CloudWatchメトリクス（CPU使用率、メモリ使用率、カスタムメトリクス）に基づいてFargateタスク数が動的に調整されます。500万から3000万ユーザーへの成長に対応するため、需要増加時は自動的にタスクを増加させ、負荷減少時は自動的にスケールダウンしてコストを最適化します。

統合されたブルー/グリーンデプロイメント

AWS CodeDeployがブルー/グリーン環境間のトラフィック移行を制御し、新バージョンの段階的デプロイメントを実現します。グリーン環境での検証完了後、ALBのターゲットグループ設定を更新してトラフィックを安全に移行します。問題が検出された場合は自動ロールバック機能により、即座にブルー環境に復旧できます。

他のソリューションとの比較

Application Load BalancerとService Auto Scalingの組み合わせを選択する理由は、HTTPSアプリケーションとFargateプラットフォームの特性に最適化されていることです。Network Load Balancerも技術的にはHTTPSトラフィックを処理できますが、レイヤー4での処理となるため、HTTP/HTTPSプロトコルの高度な機能を活用できません。

Cluster AutoscalerやAuto Scalingグループの概念は、EC2ベースのECSクラスターには適用されますが、Fargateでは基盤インフラが完全に抽象化されているため適用されません。Service Auto Scalingは、Fargateでのタスクレベルスケーリングに特化した正しいアプローチです。

実装の考慮事項

実装時は、まずECSサービスでService Auto Scalingポリシーを設定し、Target Tracking Scalingでの自動調整を推奨します。CPU使用率70%、メモリ使用率80%等の閾値を設定し、スケールアウト・スケールインの動作を最適化します。動画配信アプリケーションの特性を考慮し、ネットワーク使用率やアプリケーション固有のメトリクスも監視対象に含める必要があります。

ブルー/グリーンデプロイメントでは、CodeDeployアプリケーションとデプロイメントグループの適切な設定が重要です。Linear10PercentEvery1MinuteやCanary10Percent5Minutesなど、アプリケーションの特性に応じたトラフィック移行戦略を選択します。ヘルスチェック設定とロールバック条件も慎重に設計し、サービス品質を維持しながら安全なデプロイメントを実現します。

ALBの設定では、Sticky Sessionやパスベースルーティングを活用してマイクロサービス間の効率的な通信を構築します。SSL証明書の管理とHTTPS リダイレクト設定により、セキュリティを確保します。大規模ユーザー基盤に対応するため、ALBのConnection Drainingや適切なタイムアウト設定も重要な考慮事項となります。
