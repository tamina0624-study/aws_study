前提知識
API Gateway SDK生成の自動化について

API GatewayのSDK生成はREST APIでサポートされる機能で、JavaScript、iOS、Android、Java等の言語別に自動生成できます（HTTP APIはSDK生成をサポートしていません）

get-sdk APIを使用してプログラマティックにSDKをダウンロードでき、ステージ、SDK言語、パラメータを指定可能です

SDKにはAPIエンドポイント、認証設定、モデル定義などが含まれ、クライアントアプリケーションでの統合を簡素化します

API変更時には新しいSDKを生成・配布することで、クライアントとの整合性を保持できます

CodePipelineカスタムアクションの活用について

Lambda InvokeアクションによりCodePipeline内で任意のLambda関数を実行でき、複雑な処理を統合できます

アクション実行結果の成功・失敗により、パイプライン全体の制御が可能で、エラー時の自動停止やロールバックを実現できます

環境変数やアーティファクト経由での情報受け渡しにより、前段の処理結果を後段で活用できます

並列実行やステージ間での承認プロセス統合により、複雑なデプロイワークフローも管理できます

V2タイプのパイプラインでは、Commandsアクション（2024年10月追加）でシェルコマンドを直接記述して実行することもできます。CodeBuildプロジェクトを事前に作らずに済む一方、実行はCodeBuildコンピューティング上で行われるためCodeBuild料金が別途発生します

CloudFrontキャッシュ無効化戦略について

CreateInvalidation APIにより、特定のパスまたはワイルドカードパターンでのキャッシュクリアを実行できます

無効化は通常数分で完了しますが、大量のファイルでは時間がかかる場合があります

無効化は月1,000パスまで無料で、超過分は有料です。この無料枠はディストリビューション単位ではなくアカウント単位の合計で数えられますが、SDK更新の頻度であれば通常は無料範囲内に収まります

バージョニング戦略（ファイル名にハッシュ値追加等）との組み合わせにより、キャッシュ管理を最適化できます

アーキテクチャ図の解説



APIの更新からSDKの配布までをCodePipelineのワークフロー内に閉じて自動化します。デプロイステージの完了直後にLambda Invokeアクションが起動し（①）、LambdaがAPI GatewayからSDKを取得して（③④）S3へアップロードし（⑤）、CloudFrontの該当パスを無効化します（⑥）。WebプレイヤーはCloudFront経由で最新のSDKを取得できます（⑦）。デプロイの成否が追跡でき、失敗の検知と再実行も容易です。EventBridgeで監視する案は、SDK更新と厳密に連動しない、あるいはS3 APIではCloudFrontのキャッシュを消せないため成立しません。消す対象はS3ではなくCloudFrontのキャッシュです。
解くための考え方
SDK生成はAPIデプロイの直後に、同じパイプラインのInvokeアクションで走らせます。LambdaがSDKを取り、S3へ置き、CloudFrontを Invalidate します。EventBridgeでデプロイ完了を待つと、失敗時の再実行やステージとの結びつきが弱くなります。S3の削除APIではエッジキャッシュは消えません。
実装の考慮事項
InvalidateのパスはSDKの配布パスに限定し、全パス無効化で枠を消費しないようにします。LambdaがSDK生成APIで失敗したらパイプラインを失敗させ、部分的に古いSDKを残しません。

前提知識
Service Control Policy（SCP）の動作原理について

SCPは組織レベルでのアクセス制御境界を定義し、各アカウントのIAMポリシーで許可されたアクションでも、SCPで制限されていれば実行できません

デフォルトでは「FullAWSAccess」ポリシーがルートOUにアタッチされており、全AWSサービスへのアクセスが許可されています

SCPの効果的な制御には、FullAWSAccessの削除と明示的な許可ポリシーの適用が必要です

SCPは継承されるため、ルートに適用されたポリシーは配下の全OUとメンバーアカウントに影響します

SCPが効くのはメンバーアカウントのみで、管理アカウントのユーザーとロールには適用されません。そのためガードレールを効かせたいワークロードは管理アカウント以外に置きます

ホワイトリスト vs ブラックリスト方式の比較について

ホワイトリスト方式では承認されたサービスのみを明示的に許可し、それ以外は全て拒否されるため、セキュリティが強化されます

新しいAWSサービスはデフォルトで利用不可となり、承認プロセスを経て許可される仕組みが自動的に適用されます

ブラックリスト方式では未承認サービスを個別に拒否する必要があり、新サービス追加時の管理漏れリスクがあります

運用負荷の観点でも、承認済みサービスリストの管理の方が、拒否サービスリストより効率的です

組織単位（OU）構造とポリシー継承について

Organizations内のOU構造により、階層的なポリシー適用と権限管理を実現できます

ルートOUに適用されたSCPは組織全体に継承され、一貫したガバナンスを確保できます

特定のOUや個別アカウントに追加のSCPを適用することで、段階的な権限制限も可能です

同一階層に複数のSCPがアタッチされている場合はいずれか1つで許可されていればその階層では許可となり、ルート・OU・アカウントの各階層すべてで許可されているアクションのみが有効になります（階層をまたいだ実質的な交集合）

アーキテクチャ図の解説



ホワイトリスト方式のSCPをルートOUに適用し、あらかじめFullAWSAccessを外すと、明示許可したサービス以外を組織全体で遮断します。管理アカウントがルートOUのデフォルトポリシーFullAWSAccessを削除し、承認済みサービスのみを許可するSCPを作成してルートOUにアタッチします。SCPは配下の全アカウントに継承されるため、各チームは自アカウントを自律管理しつつ、未許可サービスのアクセスは拒否されます。新サービスもデフォルトでブロックされ、承認を経てSCPへ追記する運用が成立します。ブラックリスト方式で未承認サービスを個別に拒否すると、新サービスの追加ごとに更新漏れが生じます。
解くための考え方
チームには自アカウントの裁量を残しつつ、会社が承認したサービスだけを使わせます。アカウント管理者が書き換えられない境界が必要なので、SCPを使います。IAMポリシーやStackSetsはアカウント管理者が外せるため、組織全体の強制にはなりません。
方式はホワイトリストです。ルートOUから FullAWSAccess を外し、承認サービスだけを許可するSCPをルートへ付けます。新サービスは既定で使えず、承認後に許可リストへ足します。未承認サービスを個別拒否するブラックリストは、新サービスのたびに更新が要り、FullAWSAccess が残っていると拒否漏れが通ります。Control Towerをアカウントの配置にだけ使い、制限をIAM Identity Centerの権限セットに置く構成では、各アカウントで独自に作られたIAMユーザーやロールを素通ししてしまいます。
実装の考慮事項
FullAWSAccess を外す前に、現行ワークロードが使うサービスを許可リストへ入れます。置き換えなしに FullAWSAccess を外すとメンバーアカウントの全APIが失敗するので、まず開発用のOUで試し、問題がなければルートへ広げます。なお管理アカウントはSCPの対象外なので、制御を効かせたい作業は必ずメンバーアカウント側で行います。

AWS Configコンフォーマンスパック機能について

統合管理パッケージ 複数のConfigルールと修復アクション、関連するLambda関数を単一のデプロイメント単位として管理する機能。ルール間の依存関係、共通パラメータ、実行順序を統一的に制御し、複雑なコンプライアンス要件を効率的に実装可能

Organizations委任管理者モデルの特徴

責任分離とセキュリティ強化 管理アカウントの使用を最小限に抑え、専門チームが特定サービスの管理権限を持つモデル。Configの委任管理者はConfig関連の全権限を持ちながら、他のOrganizations管理機能からは分離される

スケーラブルな運用体制 複数サービスの委任管理者を異なるアカウントに設定することで、チーム別の責任分担とアクセス制御を実現。セキュリティ、ネットワーク、コンプライアンス等の専門領域ごとの効率的な運用を可能

Config自動修復機能について

Systems Managerオートメーション統合 Configルールの非準拠検出時に、Systems Manager Automationドキュメントを自動実行して修復アクションを実行。セキュリティグループ設定修正、暗号化有効化、タグ付与等の標準的な修復手順を自動化

カスタム修復アクション Lambda関数を使用したカスタム修復ロジックの実装により、組織固有のコンプライアンス要件に対応。複雑な修復手順や外部システム連携を含む高度な自動化を実現

IAMアクセス制御とガバナンス機能の特徴

組織コンフォーマンスパックの保護 委任管理者アカウントから組織全体に展開したコンフォーマンスパック（およびそこに含まれるルール・修復アクション）は、メンバーアカウント側では読み取り専用として扱われ、メンバーアカウントのユーザーは変更・削除できない。これにより非管理者による不正な設定変更を防止

Service Control Policy統合 OrganizationsのSCPと連携してConfigサービスへのアクセス制御を強化し、アカウントレベルでのConfig無効化や設定変更を防止する

委任管理者モデルでコンフォーマンスパックを組織全体へ展開する構成です。管理アカウントがメンバーアカウントをConfig委任管理者として設定し、日常のConfig運用を委ねて責任を分離します。委任管理者がConfigルールと修復アクションをまとめたコンフォーマンスパックを作成し（①）、既存の全メンバーアカウントへ一括配布します（②）。組織に新規追加されたアカウントへは自動的に適用されます（③）。メンバーアカウントの非管理者ユーザーがルールの変更・削除を試みても拒否され、ガバナンスが強制されます（④）。StackSetsで個別ルールを配る案は依存関係や更新手順の運用負荷が高く、コンフォーマンスパックの一括管理に劣ります。
解くための考え方
全アカウントへ同一のConfigルールと修復を配り、非管理者が変えられないようにする必要があります。StackSetsでも配れますが、Config専用のコンフォーマンスパックの方がルールと修復を1単位で扱えます。
コンフォーマンスパックは複数のConfigルールと修復を1つの単位にまとめ、パラメータと依存関係を揃えて配れます。「セキュリティベースライン」などテーマごとにパックを分けられます。
委任管理者アカウントの活用は、Organizations運用のベストプラクティスです。管理アカウントは組織構造の管理に専念し、個別サービスの運用は専門チームが担当する委任管理者アカウントが担うことで、責任分離とセキュリティを向上させます。
自動適用機能により、新規アカウントが組織に追加された際に、手動作業なしでコンフォーマンスパックが適用されます。これにより、組織の成長に伴うコンプライアンス管理の継続性を確保できます。
非管理者による変更防止は、組織コンフォーマンスパックがメンバーアカウント側で読み取り専用として扱われる仕組みにより実現されます。委任管理者（および管理アカウント）以外のユーザーは、組織コンフォーマンスパックやその構成要素を変更・削除できないように制限されます。
実装の考慮事項
パックのパラメータは環境差が出る値だけにします。修復は影響範囲を確認してから有効化し、委任管理者のIAMはConfig運用に必要な範囲に留めます。委任管理者から組織デプロイを行う場合、AWS Configはサービスにリンクされたロール（SLR）を自動作成しないため、IAMで事前に作成しておきます。既存ルールと重複しないよう整理し、変更はCloudTrailで監査します。

前提知識
AWS CloudFormation IaCジェネレーターについて
AWS CloudFormation IaCジェネレーターは、2024年2月にリリースされた機能で、CloudFormationの管理外にある既存のAWSリソースを自動スキャンし、CloudFormationテンプレートまたはAWS CDKアプリケーションを自動生成します。500種類以上のAWSリソースタイプに対応しており、Lambdaやその関連リソース（IAMロールなど）もまとめてスキャン対象にできます。CloudFormationコンソール、AWS CLI、SDKから利用可能で、IaCへのオンボーディングにかかる週単位の手動作業を大幅に削減します。スキャンはリージョン内のリソースを対象に実行し、スキャン結果からテンプレートを作成する段階でリソースタイプを指定して絞り込めるため、Lambda関数だけをIaC管理へ移すこともできます（cdk migrate --from-scanでは--filterでリソースタイプを指定します）。
AWS CDKのLambdaコード指定方法について

Code.from_asset(path): ローカルファイルシステム上のディレクトリまたは.zipファイルを指定します。デプロイ時にCDKが自動的にzipアーカイブを作成してS3にアップロードします。既存Lambda関数をCDKで管理する場合、コードをローカルに取り込んでこの方式で管理します。

Code.from_inline(code): コードを文字列としてテンプレートに埋め込みます。サイズ上限は4,096バイトであり、単純な一行スクリプト以外には使用できません。

Code.from_bucket(bucket, key): 既存S3バケット上のzipを直接参照します。ただし、S3上のコードが更新されてもLambdaは自動更新されないため、CDKによる継続管理には不向きです。

Code.from_ecr_image(): コンテナイメージを使用するLambda関数専用の指定方式です。

CloudFormation LambdaリソースのCodeプロパティについて

Code.S3Bucket + Code.S3Key: zip形式のコードが格納されたS3バケット名とキーを指定する標準的な方法です。IaCジェネレーターがCloudFormationテンプレートを生成した場合、zip形式のLambdaはこの形式で出力されます。

Code.ZipFile: テンプレート内にインラインでコードを記述するためのプロパティです。利用できるランタイムはNode.jsとPythonのみで、コードはindexという単一ファイルに展開され、生成されるzipには4MBの上限があります。依存ライブラリを同梱できないため、実用的な関数コードには向きません。

Code.ImageUri: コンテナイメージ（ECRなど）を使用するLambda関数専用のプロパティです。zip形式のLambdaには使用できません。

アーキテクチャ図の解説



IaCジェネレーターは、手動作成済みのLambdaをスキャンしてCDKアプリへ変換します。既存関数をIaCジェネレーターでスキャンし（①）、Lambdaリソースタイプに絞り込んでCloudFormationテンプレートを生成します（②）。そのテンプレートをcdk migrateでPythonのCDKアプリへ変換し（③）、各関数にfrom_assetを設定してローカルコードを管理します（④）。あとはcdk deployでコードがS3へ自動アップロードされ（⑤）、スタックが更新されてLambdaがCDK管理下に入ります（⑥）。テンプレートをダウンロードしてプロパティを手動置換する工程が省けるため、工数が最小で済みます。ここでCode/ZipFileやCode/ImageUriへ置き換える案は、ランタイム制限やコンテナイメージ専用という制約に当たり、zip形式の関数をIaC管理へ移す正攻法ではありません。
解くための考え方
評価軸は「何ステップかかるか」と「手動作業がどれだけ残るか」です。
まず、全ての選択肢に共通しているのは「Lambda関数のスキャン」と「CDKアプリの作成」というゴールです。違いは、そこに至るまでの中間ステップの数と内容にあります。
正解の選択肢はIaCジェネレーターでスキャンしたリソースからテンプレートを生成し、cdk migrateでCDKアプリへ変換するアプローチです。
IaCジェネレーターはcdk migrateコマンドとの連携により、スキャンしたリソースから生成したCloudFormationテンプレートを、Python等の言語で記述されたCDKアプリケーションへ直接変換できます。
これにより、「CloudFormationテンプレートを作成 → 手動でプロパティを編集 → CDKに変換」という手作業が不要になり、ダウンロードやプロパティ置換を挟まずにCDKアプリを得られます。
次に不正解となる他の選択肢について考えます。
2つの選択肢はIaCジェネレーターでCloudFormationテンプレートを作成した後、プロパティの手動置換とCDK変換という追加作業が必要です。
Code/ZipFileへの置き換えは特に問題です。ZipFileはコードを文字列で埋め込む方式で、Node.jsとPythonの単一ファイルにしか対応せず、生成されるzipにも4MBの上限があります。依存ライブラリを含む実運用のLambdaコードは表現できないため、移行手段として不適切です。
Code/ImageUriへの置き換えはさらに誤りが明確です。ImageUriはコンテナイメージベースのLambda専用であり、本問のzip形式Lambda関数には使用できません。
AWS Configを使う選択肢は、リソースインベントリを.csvとしてエクスポートし、そこからCDKコードを手動で記述する流れです。
AWS Configに自動IaCコード生成機能はなく、最も手動作業が多くなります。関数の数が多ければ多いほど作業量が増加するため、明らかに「最小実装工数」の要件を満たしていません。
したがって、IaCジェネレーターで生成したテンプレートをcdk migrateでCDKアプリへ変換し、from_assetでコードを管理する方法が、手順数・手動作業量ともに最小であり、正解となります。

前提知識
CloudFormation・Infrastructure as Code管理の特徴

AWS CloudFormationは、AWSリソースをコードで定義・管理するInfrastructure as Codeサービスで、1つのテンプレートあたり最大500リソースをサポートします（スタック数のクォータはデフォルトでアカウント・リージョンあたり2,000スタックで、引き上げ申請も可能です）。 JSON・YAML形式でのテンプレート記述、依存関係の自動解決、ロールバック機能による安全な変更管理を提供し、スタック単位でのリソースライフサイクル管理を実現します。 Parameters、Resources、Outputs、Conditions でテンプレートを組み立て、スタック単位でライフサイクルを管理します。

ネストされたスタック（Nested Stack）は、CloudFormationテンプレート内で他のテンプレートを子スタックとして呼び出す機能で、複数階層のネスト構造を構成できます。 AWS::CloudFormation::Stackリソースタイプによる子テンプレートの参照、パラメータ渡し、出力値の取得により、モジュール化されたインフラ構成を実現します。 子スタックのテンプレートは独立して開発・再利用できますが、スタック更新などの操作はルートスタック（親スタック）から開始することが推奨されており、ルートスタックを更新するとテンプレートに変更のあった子スタックだけが更新されます。これにより再利用性とメンテナンス性を大幅に向上させます。

スタック間連携・値共有の特徴

Fn::ImportValue関数は、他のCloudFormationスタックがエクスポートした値を参照する組み込み関数で、同一リージョン内のスタック間でのデータ共有を提供します。 エクスポート側スタックのOutputsセクションでExport指定による値公開、インポート側でのFn::ImportValueによる値取得により、スタック間の疎結合連携を実現します。 ネットワーク情報（VPC ID、サブネットID）、セキュリティリソース（IAMロールARN）、共有設定値等の参照に適用され、環境間の一貫性確保に貢献します。

変更管理・デプロイメント制御の特徴

CloudFormation変更セット（Change Set）は、スタック更新前に変更内容をプレビューする機能で、リソースの追加・変更・削除を詳細表示し、影響範囲の事前確認を可能にします。 CreateChangeSet APIによる変更セット作成、変更内容の詳細レビュー、ExecuteChangeSetによる実際の変更適用という安全なワークフローを提供します。 置換が必要なリソース、ダウンタイムの発生可能性、依存関係への影響等の重要情報を事前に把握でき、本番環境での安全な変更管理を実現します。

マルチアカウント・大規模デプロイメントの特徴

CloudFormation StackSetsは、複数のAWSアカウントや複数のリージョンにわたって同一のCloudFormationテンプレートを一括管理・デプロイするサービスです。 組織単位でのアカウント管理、リージョン間での一貫したインフラ配布、中央集約的な設定管理と個別アカウントでの独立運用を両立します。 AWS Organizations統合による自動アカウント管理、Service Control Policyとの連携によるガバナンス強化機能を提供します。

アーキテクチャ図の解説



ネットワーク用スタックと開発環境の親スタックを疎結合に分け、ネストされたスタックで ALB・Auto Scaling・DynamoDB・セキュリティグループをモジュール化します。ネットワークチームのスタックがVPC IDとSubnet IDsをOutputsにエクスポートし、親スタックがResourcesセクションのFn::ImportValueでそれらを参照します。取得した値をALB・Auto Scaling・DynamoDB・セキュリティグループの各子スタックへパラメータとして渡すため、環境ごとに重複して値を書き直す必要がありません。更新はCreateChangeSetで差分を確認してからExecuteChangeSetで適用します。Fn::ImportValueをParametersセクションに置くとインポートできず、エクスポートされた値を無視してTemplateURLで外部参照するのも無駄な複雑さです。
解くための考え方
半日かかる手作業の払い出しをやめ、既存のネットワーク出力（VPC・サブネット）を壊さずに、共通の ALB・ASG・SG・DynamoDB を何度も立てる必要があります。更新は変更セットで差分確認してから適用します。
ネストされたスタックの活用により、ALB、Auto Scalingグループ、セキュリティグループ、DynamoDBテーブル等の標準的な開発環境コンポーネントを独立したモジュールとして定義できます。各コンポーネントを独立したテンプレートで管理することで、テンプレート単位でのバージョン管理が可能になり、異なる開発チームが並行して作業する際の競合を避けられます。実際の更新はルートスタックから開始し、変更のあった子スタックだけが更新される点に注意します。
既存のネットワークインフラとの統合では、Fn::ImportValue関数による適切な値参照が重要です。ネットワークチームが既にVPCとサブネットの情報をスタック出力としてエクスポートしているため、これらの値を直接参照することで、環境間での一貫性を保ちながら疎結合なアーキテクチャを維持できます。
変更管理では、CreateChangeSetとExecuteChangeSetの活用により、本番環境への影響を事前に評価できます。特に、インフラの拡大が予想される環境では、リソース置換の必要性やダウンタイムの発生可能性を事前に把握することで、適切なメンテナンス計画を立てられます。
StackSetsは複数アカウント・リージョン展開に特化しており、単一アカウント内での開発環境管理には過剰な機能となります。TemplateURLによる外部テンプレート参照も、既にエクスポートされた値が利用可能な状況では不要な複雑性を生み出します。
実装の考慮事項
子スタックへ渡すパラメータはインスタンスタイプやスケーリング設定など環境差がある値に限ります。更新順は親の依存関係に任せ、適用前は CreateChangeSet で置換の有無を確認します。コンソールでの手動変更はドリフト検出で拾います。

前提知識
ECR認証メカニズムについて

Amazon ECRは認証トークンベースのアクセス制御を採用し、全てのDocker操作で事前認証が必要です

aws ecr get-login-passwordコマンドは一時的な認証トークンを生成し、デフォルトで12時間有効です

GetAuthorizationToken APIはユーザー名AWSとパスワードを含むBase64エンコード済みトークンを返しますが、aws ecr get-login-passwordはこれをデコードしてパスワード部分だけを出力するため、docker login --username AWS --password-stdinの標準入力へそのまま渡せます

CodeBuild環境では、IAMロールに適切なECR権限（ecr:GetAuthorizationToken、ecr:BatchCheckLayerAvailability、ecr:GetDownloadUrlForLayer、ecr:BatchGetImage、ecr:PutImage等）が必要です

buildspec.ymlでのECR統合パターンについて

pre_buildフェーズでaws ecr get-login-passwordとdocker loginを実行し、後続のbuildフェーズでdocker pushを実行する構成が標準的です

環境変数でAWS_DEFAULT_REGIONとAWS_ACCOUNT_IDを設定し、ECRリポジトリURIを動的に構築できます

複数のECRリポジトリに対するマルチステージビルドでは、各リポジトリへの個別認証が必要です

イメージタグ管理では、$CODEBUILD_RESOLVED_SOURCE_VERSIONやカスタム環境変数を活用してバージョン管理を自動化できます

CodeBuild環境でのDocker実行について

CodeBuildの標準イメージにはDocker CLIが含まれ、docker build、docker tag、docker pushコマンドを実行できます

Dockerデーモンとやり取りするビルドプロジェクトでは特権モード（privilegedMode）の有効化が必要で、これを設定しないとDockerデーモンを使うビルドは失敗します（Windows環境は特権モード非対応）

カスタムビルド環境では、独自のDockerイメージを使用してビルド環境をカスタマイズできます

ビルドアーティファクトとしてのイメージレイヤーキャッシングにより、ビルド時間の短縮と効率化を実現できます

アーキテクチャ図の解説



ECRプライベートリポジトリへのアクセスには、IAM権限だけでなくDockerレジストリへの認証トークンが必要です。CodeBuildのサービスロールの認証情報はpre_buildフェーズに渡り、aws ecr get-login-passwordが一時トークン（約12時間有効）を取得してdocker loginを実行します（①）。認証が済んで初めてbuildフェーズでイメージをビルドし（②③）、post_buildフェーズでECRへプッシュできます（④）。S3へのアップロードはIAM署名だけで完結しますが、Dockerクライアントはその署名を使えないため、認証を省くとビルドは通ってもプッシュの段階で失敗します。IAM権限の変更だけでは足りません。
解くための考え方
S3へのアップロードはIAM署名付きAPIだけで済みます。ECRへのDocker操作は違います。IAMの ecr:GetAuthorizationToken などに加え、aws ecr get-login-password で一時トークンを取り、docker login でレジストリに入る必要があります。
ロールの権限とbuildspecのリポジトリURIを直しただけでは、Dockerクライアントがレジストリに入れません。pre_build でログインし、その後に docker build と docker push を実行します。追加のAssumeRoleやリポジトリのパブリック化、Secrets Managerに置いた固定パスワードでは、ECRの12時間トークン方式に合いません。
実装の考慮事項
認証トークンの有効期限は約12時間です。ビルドがそれを超える場合は、pushの直前にもう一度 get-login-password を実行します。サービスロールには ecr:GetAuthorizationToken と、対象リポジトリへの ecr:PutImage などを付けます。

前提知識
CodeDeployアーキテクチャとエージェント通信について

CodeDeployエージェント EC2インスタンス上で動作するソフトウェアで、CodeDeployサービスからデプロイメント指示を受信してローカルでアプリケーション更新を実行。エージェントは定期的にサービスエンドポイントをポーリングして新しいデプロイメントをチェックし、S3またはGitHubからアプリケーションリビジョンをダウンロード

サービス通信要件 エージェントはHTTPS(ポート443)経由でCodeDeployサービスエンドポイントと通信する必要があり、インターネット接続またはVPCエンドポイント経由のアクセスが必須。通信障害時にはライフサイクルイベントの実行がスキップされる

ネットワーク接続とVPC構成の特徴

NAT Gateway機能 プライベートサブネット内のEC2インスタンスがインターネット上のリソースにアクセスするための機能で、アウトバウンド通信のみを許可。プライベートサブネットのエージェントがインターネット経由でCodeDeployとS3のエンドポイント（HTTPS 443）へ到達するには、この経路かVPCエンドポイントのいずれかが必要

VPCエンドポイント プライベートネットワーク内でAWSサービスに直接アクセスするための仕組みで、インターネットゲートウェイを経由せずにCodeDeployサービスとの通信が可能。EC2デプロイではcom.amazonaws.<リージョン>.codedeployとエージェント用のcom.amazonaws.<リージョン>.codedeploy-commands-secureの両方が必要で、リビジョン取得のためのS3への経路も別途用意する。セキュリティとネットワーク分離を重視する環境では推奨される構成

IAMロールとインスタンスプロファイル機能について

EC2インスタンスプロファイル EC2インスタンスがAWSサービスにアクセスするための認証情報を提供する仕組みで、IAMロールを関連付けて権限を付与。CodeDeployエージェントの動作には最低限のS3アクセス権限とCodeDeploy関連権限が必要

CodeDeploy必要権限 インスタンスプロファイルには、アプリケーションリビジョンを格納するS3バケットに対するs3:GetObject、s3:ListBucket等の読み取り権限が基本権限セットとして必要。エージェントはこの認証情報を用いてCodeDeployサービスへのポーリングも行うため、プロファイル自体の欠如は通信不能に直結する

デプロイメント構成ファイルについて

appspec.yml デプロイメント手順を定義するYAML形式の設定ファイルで、ファイル配置先、実行権限、ライフサイクルフック等を指定。アプリケーションリビジョンのルートディレクトリに配置が必要で、構文エラーや欠如は明確なエラーメッセージで報告される

アーキテクチャ図の解説



プライベートサブネット内のEC2インスタンスは、NAT Gateway経由でCodeDeployへ通信します。エージェントは定期的にHTTPSでポーリングし（①）、NAT GatewayとInternet Gatewayを経由してCodeDeployサービスエンドポイントへ到達します（②③）。サービスからのデプロイ指示が返送され（④）、S3からアプリリビジョンを取得します（⑤）。この経路のどこかに欠落があると、エージェントは指示を受け取れず、デプロイのライフサイクルイベントが実行されないまま「スキップ」として記録されます。プライベートサブネットなのにNAT Gatewayが無い、またはパブリックサブネットなのにInternet Gatewayが無い構成が典型的な原因です。



EC2インスタンスは、IAMインスタンスプロファイル経由でS3とCodeDeployへアクセスします。インスタンスはIAMインスタンスプロファイルを介してIAMロールの認証情報を取得し（①②）、そのロールに含まれるS3ポリシーでアプリリビジョンをダウンロード（③）、CodeDeployポリシーでデプロイ状況をサービスへ報告します（④）。インスタンスプロファイルが未設定、あるいは権限が不足していると、エージェントはリビジョンを取得できず処理を進められません。この場合も、明確なエラーではなくライフサイクルイベントが「スキップ」として記録されます。ネットワークは通っているのに配布が行われない場合は、このインスタンスプロファイル側を疑うのが定石です。IAMロールシミュレーターで実際に必要なアクションが許可されているか確認できます。
解くための考え方
「スキップ」は、CodeDeployサービスが指示を送ったのに、対象EC2側でライフサイクル処理が走らなかったときに付きます。
最も可能性が高い原因は、EC2インスタンスとCodeDeployサービス間の通信障害です。プライベートサブネットでNATゲートウェイが設定されていない、またはパブリックサブネットでインターネットゲートウェイが欠如している場合、CodeDeployエージェントはサービスエンドポイントにアクセスできません。この通信不能状態では、エージェントがデプロイメント情報を取得できず、全てのライフサイクルイベントがスキップされます。
もう一つの重要な原因は、EC2インスタンスプロファイルの権限不足です。CodeDeployエージェントがS3からアプリケーションリビジョンをダウンロードし、デプロイメント状況をサービスに報告するためには、適切なIAM権限が必要です。これらの権限が不足していると、エージェントは必要な操作を実行できず、結果的にデプロイメントプロセス全体がスキップされます。
他の選択肢は、デプロイメント開始時の権限エラー、インスタンス登録問題、設定ファイル欠如等ですが、これらは「スキップ」ではなく明確なエラーメッセージとして報告される問題であり、症状と一致しません。
実装の考慮事項

前提知識
S3アクセス制御評価メカニズムについて

評価優先順序: どこかに明示的Denyがあれば最優先で拒否され、無い場合はIAMポリシー、バケットポリシー、ACLのいずれかにAllowがあれば許可、どこにもAllowが無ければ暗黙的Deny（デフォルト拒否）となります。別アカウントからのリクエストでは、リクエスト元アカウント側のIAM許可と、バケット所有者側のバケットポリシーまたはACLによる許可の双方が必要です。複数のポリシー種別の相互作用により、予期しない結果を回避するには評価順序の理解が重要

ACLの特殊性: オブジェクトレベルでの古典的アクセス制御機能で、authenticated-readはAWSアカウントの認証を受けた全てのユーザー（AuthenticatedUsersグループ）に読み取り権限を付与。現代のベストプラクティスでは、ACLを無効化し、より柔軟で詳細なバケットポリシーの使用が推奨

バケットポリシーによる高度アクセス制御の特徴

条件ベース制御: IPアドレス、時間帯、リクエストヘッダー、MFA認証状況等の多様な条件を組み合わせた詳細なアクセス制御ルールを設定可能。クロスアカウントアクセスでの信頼関係管理と組み合わせて制御できる

JSON形式ポリシー構文: Principal、Action、Resource、Conditionの組み合わせによる宣言的ポリシー定義により、複雑なビジネスルールを表現可能。バージョン管理とコードレビューによるポリシー品質管理も実現

CodeBuildとS3統合セキュリティについて

サービスロール権限設計: CodeBuildサービスロールに必要最小限のS3アクセス権限を付与し、過剰な権限による横展開攻撃リスクを軽減。クロスアカウント環境では、適切な信頼関係設定と一時的権限移譲メカニズムを活用

アーティファクト暗号化: S3のサーバーサイド暗号化（SSE-S3、SSE-KMS、SSE-C）による保存時暗号化と、HTTPS転送による転送中暗号化と組み合わせてデータを保護します

マルチアカウントアクセス制御パターンについて

クロスアカウント信頼: IAMロールの信頼関係とバケットポリシーのPrincipal指定による、アカウント境界を越えたセキュアなリソースアクセスを実現。外部IDや条件キーによる詳細な制御も可能

組織単位ベース制御: AWS Organizationsとの統合により、組織階層に基づいたアクセス制御と、SCPによるガードレールを設定できる

アーキテクチャ図の解説



--acl authenticated-read による成果物の過剰公開をやめ、buildspec の ACL 指定を外してバケットポリシーに一本化します。--acl authenticated-readは認証済みの全AWSアカウント（AuthenticatedUsersグループ）に読み取りを許可するため、共有先以外にもダウンロードを許してしまいます。修正後はCodeBuildがACLなしでアップロードし（①）、バケットポリシーが特定アカウントだけを許可します（②③）。落とし穴は--acl public-readへの変更です。匿名ユーザーを含む全世界へ公開し、状況を悪化させます。ACLを外してポリシーで絞るのが定石です。
解くための考え方
S3のリクエストは、明示的Denyが無ければ ACL、バケットポリシー、IAMポリシーのいずれかのAllowで許可されます（別アカウントからのアクセスでは、リクエスト元のIAM許可とバケット側のACLまたはバケットポリシーの双方が必要です）。--acl authenticated-read が残ると、バケットポリシーで配布先を絞ってもオブジェクトACL側の許可が生き続け、認証済みの全AWSユーザーが読めます。
オブジェクトACLとバケットポリシーは独立して評価されるため、--acl authenticated-readを残したままバケットポリシーだけで制限しようとしても、ACL由来の許可は取り消せません。なお、2023年4月以降に作成された新規S3バケットではACLがデフォルトで無効（オブジェクト所有者が「バケット所有者の強制」）になっており、ACLを無効化してバケットポリシーに一本化することが現在のベストプラクティスです。この問題のように明示的なACL指定が機能している環境は、ACLが有効なまま運用されている既存バケットが前提となります。
根本的解決には、過剰な権限付与の源泉である--acl authenticated-readを除去し、バケットポリシーによる適切な制御に統一することが必要です。この手法により、アクセス制御ロジックが単純化され、セキュリティリスクが軽減されます。
CodeBuild環境では、サービスロールに必要最小限の権限のみを付与し、クロスアカウントアクセスが必要な場合は信頼関係を通じた一時的権限移譲を活用することが、セキュリティベストプラクティスに適合します。
実装の考慮事項
バケットポリシーの Principal は配布先アカウントに限定します。ACL を外す前に、既存パイプラインが authenticated-read 前提でないかを確認します。取得状況はアクセスログと CloudTrail で追います。

CloudWatchアラーム統合機能について

前提知識
Kinesis Data Streams処理アーキテクチャについて

Consumer Application パターン EC2インスタンス上で動作するKinesisクライアントライブラリ（KCL）を使用した処理モデル。各シャードに対してワーカーインスタンスが割り当てられ、レコードの順次処理を実行。チェックポイント機能によりプロセス障害時の自動復旧をサポート

シャードとコンシューマの関係 KCLでは1つのシャードのリースを同一アプリケーション内の1つのワーカーが担当して処理するため、水平スケーリング時はシャード数とコンシューマインスタンス数の適切なバランシングが必要

CloudWatch監視メトリクスの特徴

GetRecords.IteratorAgeMilliseconds コンシューマが現在処理しているレコードの年齢を示すメトリクスで、処理遅延の正確な測定が可能。このメトリクス値の増加は、コンシューマの処理速度がストリームへの取り込み速度に追いついていないことを示す重要な指標

IncomingRecords、OutgoingRecords ストリームへの書き込み・読み取り速度を測定するメトリクスで、スループット監視とキャパシティプランニングに活用。これらの値の乖離がボトルネック発生を示唆

Auto Scalingとコンシューマ管理について

EC2 Auto Scaling統合 CloudWatchメトリクスアラームをトリガーとしたAuto Scalingグループの動的拡張により、処理能力の自動調整が可能。GetRecords.IteratorAgeMillisecondsの閾値設定により、適切なタイミングでのスケールアウトを実現

コンシューマインスタンス管理 KCLのワーカー自動配布機能により、新しいインスタンスが追加された際の自動的なシャード再分散を実行。処理負荷の均等分散と高可用性を確保

ストリーム設定と保持期間管理機能の特徴

データ保持期間設定 デフォルト24時間から最大365日（8,760時間）までの延長が可能で、一時的な処理遅延時のデータ損失防止に有効。追加料金が発生するが、ビジネス継続性とデータ保護の観点で重要な設定項目

シャードレベルメトリクス 個別シャードの処理状況を監視し、特定シャードでのホットスポット検出と負荷分散最適化に活用。不均等なデータ分散の発見と対策に重要

アーキテクチャ図の解説



Kinesisコンシューマーの処理遅延をCloudWatchのGetRecords.IteratorAgeMillisecondsで検知し、Auto Scalingで水平スケールする構成です。配信基盤が視聴イベントをストリームへ書き込み（①）、EC2上のKCLコンシューマーが処理しますが、追いつかないとレコードが滞留します（②）。滞留時間を示すこのメトリクスの増加をCloudWatchが検知し（③）、Auto Scalingグループへスケールアウトを指示（④）、追加インスタンスがKCLのシャード再分散で処理を引き継ぎます（⑤）。あわせて保持期間を168時間へ延長し、スケール完了までの間にレコードが消えるのを防ぎます。シャード数を増やすだけでは読み取り側の処理能力は増えず、遅延は残ります。
解くための考え方
データ量急増時にコンシューマの処理が追いつかず、保持期間内に消化できないレコードが失われます。追いつかせるには、処理遅延を測るメトリクスでコンシューマを水平スケールします。
GetRecords.IteratorAgeMillisecondsメトリクスは、コンシューマの処理遅延を定量的に測定する最も適切な指標です。このメトリクス値が増加傾向を示した場合、それは処理速度がデータ取り込み速度に追いついていないことを意味します。このメトリクスをCloudWatchアラームのトリガーとして使用し、Auto Scalingグループによる動的な EC2インスタンス追加を自動化することで、負荷急増に対する迅速な対応が可能になります。
保持期間の延長は、スケーリング動作が完了するまでの時間的バッファを提供します。新しいコンシューマインスタンスの起動とKCLによるシャード再分散には数分を要するため、その間にデータが期限切れで削除されることを防ぐ重要な設定です。
他のアプローチは、S3とEMRによる非リアルタイム処理への変更、Lambdaへの全面的な書き換えに伴うコストとシャード数に依存する同時実行数、単純なシャード増加による部分的解決等、いずれも根本的な問題解決や運用効率最大化の要件を満たしません。
実装の考慮事項
GetRecords.IteratorAgeMillisecondsの閾値とAuto Scalingのクールダウンを、起動時間と負荷の戻り方に合わせて決めます。スケールイン時はKCLのリースを手放すグレースフルシャットダウンを入れ、チェックポイント間隔も合わせて調整します。

前提知識
S3リージョン間レプリケーションの仕組みについて

CRRは非同期レプリケーションで、ソースバケットでのオブジェクトの作成・更新が自動的にターゲットバケットに反映されます（削除マーカーのレプリケートはDeleteMarkerReplication設定で制御され、バージョン指定の削除はレプリケートされません）。ソース・ターゲット双方のバケットでバージョニングの有効化が必須です

レプリケーション処理はS3サービス自体が実行し、ユーザーのインフラストラクチャは不要で、99.999999999%（11 9's）の耐久性を維持します

暗号化されたオブジェクトのレプリケーションでは、KMSキーへのアクセス権限とターゲット側での再暗号化設定が必要です

レプリケーション時間は通常数分以内ですが、オブジェクトサイズとネットワーク状況により変動し、S3 Replication Time Control（RTC）で15分以内の保証も可能です

IAMロールとクロスアカウントアクセスについて

レプリケーションIAMロールには、ソースバケットでのs3:GetReplicationConfiguration、s3:ListBucket、s3:GetObjectVersionForReplication、s3:GetObjectVersionAcl、s3:GetObjectVersionTagging、ターゲットバケットでのs3:ReplicateObject、s3:ReplicateDelete、s3:ReplicateTagsアクションが必要です

信頼関係でs3.amazonaws.comを信頼されたエンティティとして設定し、S3サービスがロールを引き受けられるようにします

KMS暗号化の場合、kms:Decrypt（ソース側）とkms:Encrypt、kms:GenerateDataKey（ターゲット側）権限も必要になります

クロスアカウント設定でも、S3サービスが引き受けるのはソースアカウント側のレプリケーションロールであり、ターゲットアカウント側はバケットポリシーでこのロールにアクセスを許可します（レプリカの所有権をターゲットバケット所有者に移したい場合はAccessControlTranslationを使いますが、2023年4月以降の既定であるオブジェクト所有者「バケット所有者の強制」ではACLが無効になり、レプリカは自動的にターゲットバケット所有者のものになるため、この設定もs3:ObjectOwnerOverrideToBucketOwner権限も不要です）

バケットポリシーとレプリケーション設定について

ターゲットバケットポリシーでは、Principal要素でソースアカウントのレプリケーションロールを指定し、オブジェクトに対するs3:ReplicateObject・s3:ReplicateDelete・s3:ReplicateTagsと、バケットに対するs3:List*・s3:GetBucketVersioning・s3:PutBucketVersioningを、それぞれのResourceに分けて許可します

レプリケーションルールでは、Filter条件によるオブジェクト選択、Priority設定による複数ルール管理、DeleteMarkerReplicationやReplicaKmsKeyIdなどの詳細オプション設定が可能です

Destination設定では、StorageClass指定による自動階層化、AccessControlTranslation設定によるオブジェクトACL制御、Account指定によるクロスアカウント複製を管理できます

レプリケーション設定の変更は既存オブジェクトには適用されず、S3 Batch Replicationで既存オブジェクトの一括レプリケーションが必要になる場合があります

アーキテクチャ図の解説



レプリケーション処理の主体はソースアカウント側にあり、ソースとターゲットで行う設定は分かれています。ソースバケットでオブジェクトの作成・更新が起きるとS3サービスが検知し（①）、ソースアカウントのレプリケーションIAMロールを引き受けて（②）オブジェクトを読み取ります（③）。その後、ロールがターゲットアカウントへクロスアカウントアクセスを要求し（④）、ターゲットバケットポリシーが許可して書き込みます（⑤）。必須の設定はソース側のIAMロール作成、ターゲット側のバケットポリシー修正、ソースバケットのレプリケーションルール定義の3つです。役割を取り違えると複製は始まりません。
解くための考え方
CRRはソース側が能動、ターゲット側が受動です。ソースアカウントにレプリケーション用IAMロールを作り、ソースバケットにルールを置きます。ターゲットではバケットポリシーでそのロールに s3:ReplicateObject、s3:ReplicateDelete、s3:ReplicateTags を許可します。ロールをターゲットに置く必要はなく、ソースバケットポリシーの追記も不要です。ルールをターゲットに置くと、そのバケットを別複製のソースにする意味しかありません。
ソースとターゲットの両方でバージョニングを有効にします。既存オブジェクトはルール追加後の新規書き込みにしか乗らないので、過去分が要る場合は S3 Batch Replication を使います。
実装の考慮事項
暗号化オブジェクトがある場合、ソース側ロールに kms:Decrypt、ターゲット側キーに kms:Encrypt と kms:GenerateDataKey を付けます。ソース側の読み取り権限は s3:GetObjectVersion ではなくレプリケーション専用の s3:GetObjectVersionForReplication を使います。レプリケーションメトリクスで失敗件数を監視し、権限不足はイベント履歴で特定します。

前提知識
高可用性アーキテクチャ設計原則について

単一障害点排除: システム全体の可用性を脅かす単一コンポーネントの特定と冗長化により、部分的障害がサービス全体に影響することを防止。水平スケーリング、地理的分散、フェイルオーバー機能により総合的な耐障害性を実現

マルチAZ設計: 異なるアベイラビリティゾーンへのリソース分散により、データセンターレベルの障害に対する保護を実現。独立した電源、ネットワーク、冷却システムを持つAZ間でのリソース複製により、地理的冗長性を確保

Application Load Balancer機能の特徴

インテリジェント負荷分散: Layer 7での高度なルーティング制御により、HTTP/HTTPSトラフィックを複数ターゲット間で最適分散。パス、ホスト、ヘッダー、クエリパラメータベースのルーティングルールにより、マイクロサービス環境での複雑な分散要件に対応

ヘルスチェック機能: 定期的なターゲットヘルス監視により、異常なインスタンスを自動的にトラフィック分散から除外。アプリケーションレベルでの詳細なヘルス評価により、表面的な稼働ではなく実際のサービス提供能力を判定

NATゲートウェイ高可用性機能について

フルマネージド運用: AWS側でのハードウェア管理、OS更新、セキュリティパッチ適用、監視により、インフラ運用負荷を完全に排除。自動スケーリング機能により、帯域幅要件の変動に動的対応し、パフォーマンス最適化を実現

AZ内冗長性: 単一AZ内での自動冗長化により、NATゲートウェイレベルでの障害に対する保護を提供。複数AZでの展開により、AZ障害時の継続的なアウトバウンド接続を保証

補足: 2025年11月のアップデートで、単一のNATゲートウェイが複数AZに自動的に拡張・縮小するリージョナルNATゲートウェイも提供開始されています。従来型のゾーナルNATゲートウェイで高可用性を実現する場合は、本問の正解のとおり各AZへの個別配置が定石です

ネットワーク設計とルーティング制御について

ルートテーブル設計: 各プライベートサブネットのルートを同じAZのNATゲートウェイへ向けることで、AZ間データ転送料を抑えつつ、あるAZの障害が他AZの外向き通信へ波及しない構成にできます。ゾーナルNATゲートウェイのルートは静的で、障害時に別AZのNATゲートウェイへ自動で切り替わるわけではないため、切り替えが必要な場合はルートテーブルを更新する自動化を別途用意します

セキュリティグループ統合: ALBとEC2インスタンス間でのセキュリティグループ連携により、最小権限原則に基づいたネットワークアクセス制御を実現。動的なポート管理と自動ルール更新により、セキュリティと運用効率を両立

アーキテクチャ図の解説



単一EC2とNATインスタンスを、ALBによるマルチAZ負荷分散と各AZのNATゲートウェイへ置き換え、二層の単一障害点を解消します。エンドユーザーのHTTPSをALBが受け（①）、複数AZのEC2へ分散します（②③）。ヘルスチェックで異常インスタンスは自動的に配信対象から外れます。各EC2のアウトバウンドは自AZのNATゲートウェイを経由し（④⑤）、そこからインターネットへ接続します（⑥⑦）。注意すべきはNATゲートウェイを単一AZに1つだけ置く案です。そのAZが落ちると全サブネットの外向き接続が同時に断たれ、高可用性を満たしません。NATインスタンスのAuto Scaling化も可能ですが、パッチや障害対応の自前運用が残ります。
解くための考え方
単一障害点は Web 層の EC2 1台と、出口の NAT インスタンスの2つです。Web 層は複数 AZ の EC2 と ALB で、インスタンス障害と AZ 障害の両方に耐えます。
ネットワーク層の高可用性化では、NATインスタンスからNATゲートウェイへの移行が重要です。NATゲートウェイのフルマネージド特性により、運用負荷を削減しながら可用性を向上させることができます。
NAT は各 AZ に NAT ゲートウェイを置き、プライベートサブネットはその AZ のゲートウェイへ向けます。片方だけ直しても、残った単一障害点でポータルは止まります。
実装の考慮事項

EFSアクセス制御機能について

EFSファイルシステムポリシー リソースベースポリシーとしてクロスアカウントアクセス権限を付与する機能。特定のAWSアカウント、IAMプリンシパル、条件に基づいてファイルシステムとアクセスポイントへのアクセスを制御可能。POSIX権限と組み合わせて細かいアクセス制御を実現

EFSアクセスポイント ファイルシステム内の特定パスへのアクセスを提供するエントリーポイントで、POSIXユーザーとグループIDの強制設定が可能。Lambda関数からの接続時に一貫したファイルアクセス権限を確保し、セキュリティを強化

Lambda VPC統合とEFS連携の特徴

Lambda VPC設定 Lambda関数をVPC内で実行するために必要な設定で、サブネット指定とセキュリティグループ設定が必要。ENI（Hyperplane ENI）はVPC設定を行った時点で作成され、準備が完了するまで関数はPending状態になるが、その後の呼び出しごとのコールドスタートに大きな遅延は加わらず、プライベートリソースへ安全にアクセスできる

Lambda EFS統合 Lambda関数とEFSの直接統合機能で、ファイルシステムを/mnt/配下の指定パスにマウント可能。永続ストレージとして大容量データやMLモデル、共有ライブラリの保存に活用でき、複数Lambda関数間でのデータ共有を実現

VPCネットワーキング機能について

VPCピアリング接続 異なるVPC間でのプライベートネットワーク通信を実現する機能で、クロスアカウント、クロスリージョン接続をサポート。接続後は両VPCのルートテーブル設定とセキュリティグループ設定により通信制御が必要

セキュリティグループ設定 EFS通信に必要なNFSポート2049の開放設定が必要。Account BのLambda関数セキュリティグループからAccount AのEFSマウントターゲットセキュリティグループへのインバウンド許可設定

IAMアクセス制御システムの特徴

IAMポリシー vs リソースベースポリシー IAMポリシーはプリンシパルにアタッチされる権限設定で、リソースベースポリシーはリソース側で定義される許可設定。クロスアカウントアクセスでは両方の評価が実行され、明示的な許可が必要

Service Control Policy 組織レベルでのアカウント権限制限機能で、最大権限の境界を設定。許可ポリシーではなく制限ポリシーのため、具体的なリソースアクセス権限付与には使用不可

アーキテクチャ図の解説



クロスアカウントのEFSアクセスは、リソース側の許可・実行側の権限・ネットワーク経路の3点で成立します。Account AのEFSファイルシステムポリシーでAccount Bのプリンシパルを明示許可し、Account BのLambda実行ロールにはEFS接続とVPC実行の権限を付与します。①②VPCピアリングでAccount BのLambdaからAccount Aのマウントターゲットへプライベートに到達し、NFSのポート2049で接続します。③④既存のアクセスポイント経由で素材データを読み書きします。SCPは最大権限を制限するガードレールで許可を付与するものではないため使えません。DMSでの複製はストレージが二重になり、Account AのIAMロールを引き受ける案はマウント時の認可に使われないため、いずれも要件を満たしません。
解くための考え方
クロスアカウントのEFS利用は、リソース側の許可、実行ロールの権限、ネットワーク経路の3点が揃って成立します。第一に、Account AのEFSファイルシステムポリシーでAccount Bのプリンシパルを明示許可します。これがないと、Account BからAccount AのEFSへ到達できません。
第二に、Account BのLambda関数実行ロールには、EFSアクセスとVPC実行の両方に対応した適切なIAM権限が必要です。elasticfilesystem関連の権限だけでなく、VPC内でのNetworkInterface操作権限も含まれます。これらの権限により、Lambda関数が実際にEFSファイルシステムをマウントし、データ操作を実行できます。
第三に、ネットワークレベルでの接続性確保として、VPC間を結ぶ経路が必須です。EFSのマウントターゲットはVPC内のプライベートIPアドレスとして公開されるため、Account BのLambda関数がAccount AのマウントターゲットへNFSで到達するには、VPCピアリング接続（またはTransit Gateway）による接続が欠かせません。選択肢として提示されているのはVPCピアリング接続であり、これが該当します。
他の選択肢は、SCPによる制限機能の誤解、過度に複雑なデータ同期アプローチ、不要なクロスアカウントロール引き受け等、本質的な要件を満たさないか、実装の複雑性を不必要に増加させるものです。
実装の考慮事項
EFSファイルシステムポリシーは最小権限で付与します。LambdaのVPC設定ではサブネットとセキュリティグループの組み合わせごとにENIが作成されるため、同じ組み合わせを使い回してENIを共有できるようにします。セキュリティグループはNFSのポート2049だけを開けます。アクセスポイントでPOSIXユーザーとパスを固定すると、ファイルシステム内の権限分離がしやすくなります。

前提知識
AWS Organizations・マルチアカウント管理の特徴

AWS Organizationsは、複数のAWSアカウントを階層的に管理する組織管理サービスです（管理可能なアカウント数のクォータはService Quotasで確認・引き上げが可能）。 管理アカウント（旧マスターアカウント）による一元的な課金管理、Service Control Policies（SCP）による組織レベルのセキュリティ制御を提供します。 各メンバーアカウントは独立したセキュリティ境界を維持し、クロスアカウントアクセスには明示的なIAM設定が必要です。 部門別アカウントの課金集約と、SCPによる権限の上限設定に使います。

IAM・クロスアカウントアクセス管理の特徴

IAMロールは、一時的なセキュリティ認証情報を提供するAWSプリンシパルで、最大12時間のセッション持続時間をサポートします。 信頼ポリシー（Trust Policy）により引き受け可能なプリンシパルを定義し、権限ポリシーにより付与する具体的権限を指定します。 AssumeRoleによる一時認証情報取得、ロールチェーン、外部IDプロバイダ統合ができます。 クロスアカウントアクセスやサービス間連携で使います。

AWS Security Token Service（STS）は、一時的なセキュリティ認証情報を発行するサービスで、15分から12時間の有効期間を設定可能です。 AssumeRole、GetSessionToken、AssumeRoleWithWebIdentity等のAPIを通じて、異なる信頼レベルの認証情報を提供します。 一時認証情報による最小権限アクセス、認証情報の自動ローテーション、監査ログの詳細記録を実現します。

EC2・ネットワークセキュリティ管理の特徴

Amazon EC2セキュリティグループは、仮想ファイアウォール機能を提供するネットワークセキュリティ制御で、ステートフル接続追跡による双方向通信管理をサポートします。 デフォルトクォータでは各セキュリティグループに最大60のインバウンドルールと60のアウトバウンドルールを設定でき（上限緩和申請で引き上げ可能）、IPアドレス、CIDR、他のセキュリティグループを参照可能です。 デフォルトでインバウンドトラフィックを拒否し、アウトバウンドトラフィックを許可するホワイトリスト方式を採用します。

AmazonEC2ReadOnlyAccessマネージドポリシーは、EC2関連リソースの読み取り専用アクセス権限を提供するAWS管理ポリシーです。 ec2:Describe* と ec2:GetSecurityGroupsForVpc という参照系の権限を含み、インスタンス、セキュリティグループ、VPC等の設定情報取得を可能にします。 書き込み権限は一切含まれないため、監査・レポート用途での安全な権限付与に適しており、セキュリティグループルール分析での必須権限を提供します。

Lambda・サーバーレス実行環境の特徴

AWS Lambdaは、イベント駆動でコードを実行するサーバーレスコンピューティングサービスで、最大15分の実行時間と10GBのメモリをサポートします。 実行ロール（Execution Role）により必要なAWS権限を取得し、環境変数、レイヤー機能による外部ライブラリ管理を提供します。 boto3 SDKを使用したAWS API呼び出し、STS AssumeRoleによるクロスアカウントアクセス、並列実行による大規模処理が可能です。 定期的な監査処理、レポート生成、コンプライアンスチェックの自動化に使います。

アーキテクチャ図の解説



管理アカウントのLambda関数が、STS AssumeRoleで各メンバーアカウントのロールを引き受け、EC2セキュリティグループ情報を集めます。LambdaがIAM実行ロールを使い、STSのAssumeRole APIで各メンバーアカウントのロールを引き受けます。引き受ける先のロールにはAmazonEC2ReadOnlyAccessポリシーが付与され、DescribeSecurityGroupsでルール情報を読み取って管理アカウントへ返します。ここで重要なのは、メンバーアカウント側のロールが「管理アカウントを信頼する」信頼ポリシーを持っていることです。この信頼関係の方向を逆にしたり、管理アカウントに読み取り権限を付けるだけでは、アカウント境界を越えられず情報を取得できません。
解くための考え方
管理アカウントのLambdaからメンバーのセキュリティグループを読むには、向きの決まった AssumeRole が必要です。メンバー側ロールは管理アカウントを信頼し、AmazonEC2ReadOnlyAccess を持ちます。管理側の実行ロールは、それらロール ARN への sts:AssumeRole を許可します。
まず、各メンバーアカウントでの設定として、EC2セキュリティグループ情報を読み取るためのIAMロール作成とAmazonEC2ReadOnlyAccessポリシーの付与が必要です。このロールには、ec2:DescribeSecurityGroups、ec2:DescribeSecurityGroupRules等の権限が含まれ、実際のデータ取得を可能にします。
次に、クロスアカウントアクセスの実現には、メンバーアカウント側でのトラストポリシー設定が重要です。作成したIAMロールの信頼ポリシーで、管理アカウントの特定プリンシパル（Lambda実行ロールまたは管理アカウント全体）がこのロールを引き受けることを許可する設定を行います。これにより、管理アカウントからメンバーアカウントリソースへのアクセス経路が確立されます。
最後に、管理アカウント側では、Lambda実行ロールにsts:AssumeRoleアクションを許可し、対象となる全メンバーアカウントのIAMロールARNを指定します。Lambda関数内では、boto3のSTSクライアントを使用してAssumeRole APIを呼び出し、各メンバーアカウントの一時認証情報を取得後、EC2クライアントでセキュリティグループ情報を取得する実装が必要です。
信頼関係の方向性を間違えると、メンバーアカウントが管理アカウントにアクセスする逆方向の設定になり、要件を満たせません。また、管理アカウント内でのEC2権限付与だけでは、アカウント境界を越えられないため、クロスアカウントアクセス機能が動作しません。
実装の考慮事項
Lambda関数での実装では、大量のメンバーアカウントに対する並列処理とタイムアウト制御が重要です。各アカウントでのAssumeRole処理と情報取得を効率的に行うため、concurrent.futures等による並行処理と、適切なエラーハンドリング、リトライロジックの実装が必要です。取得結果の保存先（S3、DynamoDB等）への書き込み権限と、週次実行の EventBridge スケジュールを付けます。

CI/CDパイプライン設計の基本原則について

CI/CDパイプラインはソース管理、ビルド、テスト、デプロイの各ステージを自動連携させ、手動介入を最小化します

CodePipelineはワークフロー全体のオーケストレーションを担当し、各ステージの実行順序、依存関係、並列処理を管理します

CodeDeployライフサイクルフックとAppSpec設定について

AppSpecファイルはデプロイプロセスの各段階で実行するスクリプトやファイル配置を定義し、アプリケーション固有の処理を自動化できます

BeforeInstallフックは依存関係のインストール、古いファイルの削除、環境準備に使用され、キャッシュクリアに最適です

CodeDeployアーキテクチャとデプロイ単位について

CodeDeployアプリケーション 論理的なデプロイ単位で、同一のアプリケーションコードとデプロイ設定を共有するリソース群を管理します。アプリケーションレベルでのデプロイ履歴、設定テンプレート、IAMロールを統一管理し、運用の一貫性を確保します。

デプロイメントグループ 実際のデプロイ対象となるEC2インスタンス、Auto Scalingグループ、オンプレミスサーバーなどのリソース集合を定義します。タグベースの動的ターゲット選択、Blue/Greenデプロイ設定、ロールバック条件などを個別に設定できます。

CodePipeline並列実行制御機能の特徴

runOrder属性による並列制御 同一ステージ内の複数アクションに同じrunOrder値を設定することで並列実行を実現します。異なる値の場合は数値順での順次実行となり、アクション間の依存関係を柔軟に制御できます。

ステージレベル並列化 複数のCodeDeployアクションを単一ステージ内で並列実行することで、全体のパイプライン実行時間を短縮します。各アクションはそれぞれ別のデプロイメントグループを対象とするため、互いの完了を待たずに同時に進行し、成功・失敗もアクション単位で判定されます。

マルチターゲットデプロイ戦略について

環境分離とリスク管理 各ALB-Auto Scalingグループを独立したデプロイメントグループとして管理することで、部分的な障害時の影響範囲を限定します。一つの環境でデプロイ失敗が発生しても他の環境への影響を回避し、サービス継続性を確保します。

統一設定管理 単一のCodeDeployアプリケーション配下で全デプロイメントグループを管理することで、共通のデプロイ設定、IAMロール、通知設定を統一適用します。設定の重複排除と管理効率化を実現します。

CI/CD設計パターンの特徴

最小構成原則 必要最小限のコンポーネント数で要件を満たす設計により、運用負荷の軽減と障害ポイントの最小化を実現します。過度な分割は管理複雑性を増加させ、可用性とメンテナンス性を低下させます。

スケーラビリティ考慮 新しいALB-Auto Scalingグループ追加時の設定変更を最小化し、デプロイメントグループの追加のみで対応できる拡張性を確保します。

アーキテクチャ図の解説



単一のCodeDeployアプリケーション配下に複数のデプロイメントグループを置き、同一runOrderで並列デプロイします。CodeCommitへのコミット（①）が単一パイプラインをトリガーし、Sourceステージを経て（②）Deployステージから各デプロイメントグループへ同時に展開します（③）。各グループはALBとAuto Scalingグループの組み合わせを個別に持ち、環境ごとの独立したロールバックを可能にしつつ、アプリ設定やIAMロールは一元管理できます。ビルドステージを持たないため、ダイレクトな並列展開になります。デプロイメントグループを分けずに単一グループへまとめると、部分障害時の切り分けと環境別ロールバックができなくなります。
解くための考え方
5つのALB-Auto Scalingグループへ同時に展開し、障害時は該当環境だけロールバックできる必要があります。単一のCodeDeployアプリケーションにグループを分けると、デプロイスクリプトやIAMロールは共通のまま、対象とロールバックだけを独立させられます。
各デプロイメントグループは独立したリソースプールを対象とするため、一つのグループでの障害が他のグループに影響することなく、リスク分散効果も期待できます。CodePipelineのrunOrder機能により、これらのデプロイメントグループへの並列デプロイが実現されます。
複数のCodeDeployアプリケーションや複数のCodePipelineを使用するアプローチは、技術的には可能ですが、管理複雑性の増加、設定の重複、運用負荷の増大という問題を引き起こします。特に、新しい環境の追加やデプロイ設定の変更時の影響範囲が広くなり、メンテナンス性が低下します。
実装の考慮事項
各デプロイメントグループにALBとAuto Scalingグループを対応付け、失敗時はグループ単位でロールバックします。CodePipelineでは同一runOrderのアクション実行状況を監視し、成功・失敗を通知します。環境別に承認が要る場合は、そのグループのアクションだけに承認を挟みます。

前提知識
AWSクロスアカウントアクセスの仕組みについて

クロスアカウントアクセスは、リソースを所有するアカウントでの信頼関係設定により実現されます

信頼関係では、Principal要素で信頼するアカウントやロールを指定し、Conditionで追加的な制限を設定できます

AssumeRole操作により、一時的な認証情報を取得してクロスアカウントでのAPI操作が可能になります

ExternalIdパラメータを使用することで、Confused Deputy問題を防ぎ、セキュリティを向上させることができます

EKS認証・認可システムについて

EKSクラスターへのアクセスは、IAM認証とKubernetes RBAC認可の二段階で制御されます

aws-auth ConfigMapはIAMプリンシパル（ユーザー・ロール）をKubernetesユーザー・グループにマッピングします

system:masters グループは最高権限を持ち、cluster-admin ClusterRoleがバインドされています

カスタムClusterRole/Roleを作成し、適切な権限レベルでのマッピングも可能です

現在は、aws-auth ConfigMapに代わってEKSアクセスエントリ（2023年12月導入）とアクセスポリシーによるアクセス管理が推奨されています。aws-auth ConfigMapは非推奨扱いですが、クラスターの認証モードがCONFIG_MAPまたはAPI_AND_CONFIG_MAPであれば新規クラスターでも引き続き利用できます（EKS API・SDK・CloudFormationで作成した場合の既定はCONFIG_MAP、マネジメントコンソールで作成した場合はAPI_AND_CONFIG_MAP）

ただし、作成時にConfigMapを有効にしなかったクラスターへ後からConfigMapによる認証を追加することはできないため、新規クラスターでは最初からアクセスエントリで設計するのが安全です

CI/CDパイプラインでのEKS管理について

CodeBuildプロジェクトでのkubectlコマンド実行には、aws eks update-kubeconfigによるクラスター認証情報設定が必要です

Helmチャートデプロイメント、Kubernetesマニフェスト適用、カスタムオペレーター実行などが一般的なユースケースです

環境別の設定管理、シークレット管理、デプロイメント状況監視などの考慮事項があります

GitOpsパターンとの統合により、宣言的なクラスター状態管理も実現できます

アーキテクチャ図の解説



IAMのクロスアカウント信頼とKubernetesのRBACマッピングを二段階で確立します。中央DevOpsアカウントのCodeBuildはIAMサービスロールで実行され（①）、sts:AssumeRoleでアプリケーションアカウントのデプロイロールを引き受けます（②）。このロールはリソース所有側にあり、DevOpsアカウントを信頼する信頼関係がなければ引き受けられません。続いてデプロイロールがEKSのAPIを呼び出し（③）、aws-auth ConfigMapでIAMロールをRBACグループへ対応付けることで、クラスター内の操作権限が決まります。信頼関係の向きを逆にすると引き受けが成立せず、Unauthorizedは解消しません。
解くための考え方
CodeBuildは別アカウントからEKSを操作します。まずアプリ側ロールがDevOpsアカウントを信頼し、CodeBuildがそのロールを AssumeRole します。次に aws-auth ConfigMap（またはEKSアクセスエントリ）で、そのIAMロールをKubernetesグループへ結びます。IAMだけ通ってもRBACが無いと Unauthorized、向きが逆でも AssumeRole が失敗します。
実装の考慮事項
信頼関係の Principal はCodeBuildのサービスロールARNに絞ります。aws-auth の rolearn は引き受け後のロールARNと一致させます。デプロイ権限は対象Namespaceのデプロイに必要なRBACに留めます。
