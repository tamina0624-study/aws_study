Amazon CloudWatch Logsの概要 Amazon CloudWatch Logsは、AWSが提供するフルマネージドのログ管理サービスです。EC2インスタンス、Lambda関数、その他のAWSサービスからログデータを収集、監視、保存することができます。ログデータは階層構造で管理され、ロググループ、ログストリーム、ログイベントという単位で構成されています。
CloudWatch Logs Insightsの詳細機能 CloudWatch Logs Insightsは、ログデータに対してインタラクティブな検索と分析を提供する高度な分析ツールです。主な特徴は以下の通りです：

クエリ言語: パイプ（|）でコマンドをつなぐ専用のLogs Insights QLに加え、OpenSearch PPLとOpenSearch SQLの3種類のクエリ言語を選択できます

自動フィールド検出: ログの内容を自動的に解析し、構造化されたフィールドを抽出します

集計関数: count()、sum()、avg()、min()、max()などの関数でデータを集計できます

時間範囲指定: 特定の期間のデータを対象とした分析が可能です

フィルタリング: 条件に基づいてログエントリを絞り込むことができます

グループ化: 特定のフィールドでデータをグループ化して集計できます

ソート機能: 結果を昇順または降順でソートできます

視覚化: クエリ結果をグラフやテーブルで表示できます

CloudWatch Logsメトリクスフィルタの機能と制限 メトリクスフィルタは、ログイベントを監視し、特定のパターンに一致するイベントが発生した時にCloudWatchメトリクスを生成する機能です。主な特徴は以下の通りです：

リアルタイム処理: ログイベントが発生すると即座にメトリクスを生成します

パターンマッチング: 正規表現やキーワードでログイベントをフィルタリングします

カウンター機能: 一致するイベントの数をカウントできます

制限事項: メトリクスフィルターは作成後に到着したログイベントにのみ適用され、作成前に蓄積済みのログを遡って集計することはできません

用途: アラームの設定やリアルタイム監視に適しています

CloudWatch Logsサブスクリプションフィルタの機能 サブスクリプションフィルタは、ログデータをリアルタイムで他のAWSサービスにストリーミングするための機能です：

データストリーミング: ログデータを他のサービス（AWS Lambda、Amazon Kinesis Data Streams、Amazon Data Firehose）へ送信します。Amazon OpenSearch Serviceへ入れる場合はLambdaを経由します

リアルタイム処理: ログイベントが発生すると即座にデータを転送します

フィルタリング: 特定のパターンに一致するログのみを転送できます

用途: ログの転送、リアルタイム分析、外部システムとの連携に使用されます

制限事項: 過去のデータの分析や直接的な集計機能は提供していません

CloudWatchダッシュボードの機能と制限 CloudWatchダッシュボードは、メトリクスやログデータを視覚化するためのツールです：

視覚化: グラフ、テーブル、テキストウィジェットでデータを表示します

カスタマイズ: 複数のウィジェットを組み合わせてカスタムダッシュボードを作成できます

データソース: CloudWatchメトリクス、Logs Insightsクエリ結果を表示できます

制限事項: ダッシュボード自体にはデータ分析や集計機能はありません

依存関係: 表示するデータは事前に処理されている必要があります

解くための考え方
過去7日間の特定ユーザーのログイン頻度を、ログから集計できるかを見ます。
必要な機能要件の分析

1. 過去データへのアクセス: 既に保存されているログデータを遡って分析する能力が必要です

2. 柔軟なフィルタリング: 特定のユーザー名でログエントリを絞り込む機能が必要です

3. 時間範囲指定: 過去7日間のデータに限定して分析する機能が必要です

4. 集計処理: ログイン回数をカウントする集計機能が必要です

5. 構造化データの処理: ユーザー名、タイムスタンプ、IPアドレスを含むログデータを適切に処理する機能が必要です

各アプローチの評価 過去のデータを分析するという要件において、リアルタイム処理に特化したメトリクスフィルタやサブスクリプションフィルタは適用できません。これらのサービスは新しく発生するログイベントに対してのみ動作し、既存のデータを遡って処理することはできません。
ダッシュボードは視覚化ツールであり、データ分析機能は持っていません。ダッシュボードで表示するためのデータは、別のサービス（Logs Insightsなど）で事前に分析されている必要があります。
CloudWatch Logs Insightsは、これらすべての要件を満たす唯一のソリューションです。パイプでコマンドをつなぐLogs Insights QL（OpenSearch PPLやOpenSearch SQLも選択可能）を使用して、過去のログデータに対して複雑な分析を実行できます。例えば、クエリの実行時に対象期間を過去7日間に指定したうえで、以下のようなクエリで特定ユーザーのログイン回数を取得できます：

filter username = "target_user"
| stats count(*) as login_count by username
このクエリは、指定したユーザー名でフィルタリングし、ログイン回数をカウントします。分析対象の時間範囲（過去7日間）は、コンソールの期間セレクターやAPIのパラメータとしてクエリ実行時に指定します。結果はレポート形式で表示され、要件を完全に満たします。

前提知識
ワークフロー管理の考え方
複数のステージを持つデータ処理ワークフローを効率的に管理するには、以下の要素を考慮する必要があります：

1. 状態管理: 各ステージの実行状態（未実行、実行中、成功、失敗）を追跡する仕組み

2. エラーハンドリング: ステージの失敗を検出し、適切に対応する仕組み

3. 再処理: 特定のステージだけを再実行できる仕組み

4. データの受け渡し: ステージ間でデータを効率的に受け渡す仕組み

5. スケーラビリティ: 処理量の増加に対応できる柔軟性

AWS Step Functions
AWS Step Functionsは、ワークフローを視覚的に構築し管理できるサービスです：

1. ステートマシン: JSON形式で定義されるワークフロー

2. ステート（状態）: ワークフローの各ステップ。Task、Choice、Parallel、Mapなど様々なタイプがある

3. タスク: 実際の処理を行うステート。Lambda関数、ECSタスク、他のAWSサービスなどを呼び出せる

4. 入出力処理: JSONデータを入力として受け取り、処理結果をJSONデータとして次のステートに渡せる

5. エラーハンドリング: Retry（再試行）やCatch（エラー捕捉）などの機能が組み込まれている

6. リドライブ（redrive）: 2023年のアップデートにより、失敗した実行を最初からではなく失敗したステップから再開できる（標準ワークフローが対象。成功済みステップの結果と実行履歴は保持され、再実行されない）

7. 実行履歴: ワークフローの実行状況や結果をログとして保存

AWS Lambda
AWS Lambdaは、サーバーレスでコードを実行できるコンピューティングサービスです：

1. イベント駆動: 様々なイベントをトリガーにして関数を実行できる

2. スケーラビリティ: 需要に応じて自動的にスケールする

3. 短時間実行: 現在は最大15分間の実行が可能

4. ステートレス: 基本的にステートレスだが、外部サービスと連携して状態を管理できる

5. リソース効率: 実行時間に応じた課金で、アイドル時間のコストがない

アーキテクチャ図の解説



複数のステージを1つのステートマシンで直列に管理し、失敗したステージだけへ差し戻す構成です。アップロードAPIがStep Functionsへワークフロー開始を要求すると（①）、ステートマシンは取り込み・トランスコード・サムネイル生成の各ステージをLambda関数として順次呼び出します（②③④）。全ステージが成功した場合だけ処理完了に到達します（⑤）。途中のステージが失敗すると、Step FunctionsのRetryが同じステージへ制御を戻し（⑥⑦）、最初からやり直すことなく当該ステージだけを再実行します。状態追跡とリトライを自前で組まずに済むのが、S3やストリーム、コンテナで代用する案との決定的な違いです。各Lambdaの実行時間は5分以内に収まり、最大15分の上限に抵触しません。
解くための考え方
失敗したステージだけへ差し戻せ、状態をマネージドに追跡できるかを見ます。

1. ワークフロー管理機能: ステージ間の依存関係や制御フローを適切に管理できるか

2. 状態管理: 各ステージの実行状態を追跡できるか

3. エラーハンドリング: ステージの失敗を検出し、適切に対応できるか

4. 再処理能力: 失敗したステージのみを再実行できるか

5. リソース効率: 必要なときだけリソースを使用する効率的な実行が可能か

6. 開発・運用の複雑性: 実装や運用にかかる労力はどの程度か

これらの観点から各選択肢を分析すると：

S3 + SNS + EC2の組み合わせ：ステージの状態管理やエラーハンドリング、再処理の仕組みを自前で実装する必要があり、複雑性が高い

コンテナ化 + Fargate：ワークフロー管理の機能が不足しており、状態管理やエラーハンドリングも自前で実装する必要がある

Kinesis + Lambda：ストリーム処理には適しているが、特定ステージの再処理という要件に直接対応していない

Step Functions + Lambda：ワークフロー管理、状態追跡、エラーハンドリング、再処理の機能が組み込まれており、サーバーレスで効率的

AWS Step FunctionsとLambdaの組み合わせは、以下のような実装が可能です：

1. 各処理ステージを個別のLambda関数として実装

2. Step Functionsのステートマシンで、各ステージの順序や依存関係を定義

3. ステージ間のデータはStep Functionsの入出力メカニズムを使用して受け渡し

4. エラーハンドリングにStep FunctionsのRetry機能を使用し、失敗したステージのみを再試行（標準ワークフローのリドライブ機能を使えば、失敗した実行を失敗ステップから再開することもできる）

5. 必要に応じてフォールバック（代替処理）やエラー通知を実装

この手順により、失敗したステージのみを再処理するという要件を効率的に満たすことができます。

前提知識
ブルー/グリーンデプロイメント
ブルー/グリーンデプロイメントは、アプリケーションの新しいバージョン（グリーン環境）を既存のバージョン（ブルー環境）と並行して稼働させ、段階的にトラフィックを切り替える手法です。
主な利点:

ダウンタイムの削減または排除

新バージョンのテストと検証が可能

迅速なロールバックオプションの提供

デプロイリスクの軽減

ブルー/グリーンデプロイメントのプロセス:

1. 既存のアプリケーション（ブルー環境）が本番トラフィックを処理

2. 新しいバージョン（グリーン環境）をデプロイ

3. グリーン環境のテストと検証

4. トラフィックをブルーからグリーンに段階的に転送

5. 問題がなければグリーン環境が全トラフィックを処理

6. 問題が発生した場合、ブルー環境に迅速にロールバック

AWS CodeDeploy
AWS CodeDeployは、EC2インスタンス、オンプレミスサーバー、Lambda関数、ECSサービスなどへのアプリケーションデプロイを自動化するサービスです。
CodeDeployのデプロイタイプ:

インプレイスデプロイ: 既存のインスタンスでアプリケーションを更新

ブルー/グリーンデプロイ: 新しい環境でアプリケーションをデプロイし、トラフィックを転送

ECSのブルー/グリーンデプロイ: CodeDeployでは、ECSサービスのブルー/グリーンデプロイが可能で、新しいタスクセットをデプロイし、トラフィックを段階的に転送できます。
デプロイ構成: CodeDeployでは、トラフィックの転送方法を定義するために異なるデプロイ構成を使用できます：
Canary: 2ステップのトラフィック移行（例：最初に10%、その後残りの90%）

CodeDeployDefault.ECSCanary10Percent5Minutes: 最初に10%、5分後に残り90%

CodeDeployDefault.ECSCanary10Percent15Minutes: 最初に10%、15分後に残り90%

Linear: 等間隔のステップでトラフィックを移行

CodeDeployDefault.ECSLinear10PercentEvery1Minutes: 1分ごとに10%ずつ

CodeDeployDefault.ECSLinear10PercentEvery3Minutes: 3分ごとに10%ずつ

AllAtOnce: すべてのトラフィックを一度に移行

CodeDeployDefault.ECSAllAtOnce: すべてのトラフィックを即時に新しい環境に移行

基本的な使用方法:

Transform: 'AWS::CodeDeployBlueGreen'
Hooks:
  AWS::CodeDeploy::BlueGreen:
    Applications:
      - Target:
          Type: 'AWS::ECS::Service'
          LogicalID: MyECSService
        Properties:
          TaskDefinition: !Ref MyTaskDefinition
          TrafficRoutingConfig:
            Type: TimeBasedLinear
            TimeBasedLinear:
              StepPercentage: 15
              BakeTimeMins: 1
TrafficRoutingConfigのTypeにはAllAtOnce、TimeBasedCanary、TimeBasedLinearを指定できます。TimeBasedCanaryは最初の増分でStepPercentage分だけ移し、BakeTimeMinsだけ待ってから残りをすべて移す2段階方式です。TimeBasedLinearは各増分の開始時にStepPercentage分ずつ移し、増分と増分の間にBakeTimeMins分の間隔を置く等間隔方式です。TrafficRoutingConfigを省略した場合の既定値はTimeBasedCanary・StepPercentage15%・BakeTimeMins5分です。なお、AWSのドキュメントではこのフック構文のStepPercentageは14%以上とされているため、10%刻みのように細かい割合をそのまま指定したい場合は、CodeDeployのデプロイメントグループ側でCodeDeployDefault.ECSLinear10PercentEvery1Minutesのような名前付きデプロイ構成を使う形になります。いずれにせよ、CloudFormationテンプレートでECSのブルー/グリーンデプロイを成立させるには、トランスフォームとフックの宣言が欠かせません。
また、2025年7月のアップデートにより、Amazon ECS自体にCodeDeployを使わないネイティブのブルー/グリーンデプロイ機能が組み込まれましたが、この問題はAWS CodeDeployとAWS CloudFormationを使用するという前提のため、上記の構成が正解となります。
アーキテクチャ図の解説



CloudFormationがCodeDeployと連携し、ECSのブルー/グリーンデプロイを実行します。テンプレートでAWS::CodeDeployBlueGreenトランスフォームとAWS::CodeDeploy::BlueGreenフックにより対象サービスと移行方法を定義し（①②）、CodeDeployがALBを制御してBlue環境からGreen環境へ1分ごとに10%ずつトラフィックを移します（③④⑤）。TimeBasedLinearでStepPercentageとBakeTimeMinsを指定し、一定割合を一定間隔で移し続けるのが正しい表現で、カナリア（TimeBasedCanary）は最初の10%後に残り90%を一括移行するため要件を満たしません。
解くための考え方
1分ごとに10%ずつ移す線形移行を、CloudFormationとCodeDeployで表せるかを見ます。

1. デプロイ戦略: ブルー/グリーンデプロイメントを実装するため、AWS::CodeDeployBlueGreenトランスフォームを使用する必要があります。

2. トラフィック移行パターン: 「1分ごとに10%ずつ転送」という要件を満たすために、リニア（TimeBasedLinear）のトラフィック移行設定を選択する必要があります。StepPercentageで1回の増分あたりの割合を、BakeTimeMinsで増分間の間隔を指定します。これはCodeDeployの CodeDeployDefault.ECSLinear10PercentEvery1Minutes デプロイ構成に相当する動作です。

3. CloudFormation統合: CloudFormationテンプレートでブルー/グリーンデプロイを正しく実装するために、AWS::CodeDeploy::BlueGreenフックパラメータを使用して、デプロイのライフサイクルイベントをカスタマイズする必要があります。

4. 高可用性: ブルー/グリーンデプロイメント自体が高可用性を提供しますが、適切なヘルスチェックと段階的なトラフィック転送が重要です。

これらの考慮事項から、以下の要素を含むCloudFormationテンプレートが必要になります：

1. AWS::CodeDeployBlueGreenトランスフォームの宣言

2. AWS::CodeDeploy::BlueGreenフックパラメータの設定

3. TrafficRoutingConfigによる、一定割合を1分間隔で移すリニアなトラフィック移行設定

これにより、ECSアプリケーションのブルー/グリーンデプロイメントが正しく実装され、1分ごとに10%ずつ新バージョンにトラフィックが転送されることが保証されます。

前提知識
Service Control Policy（SCP）について SCPは、AWS Organizationsで管理される組織単位（OU）やアカウントに適用できる権限制御ポリシーです。SCPはJSON形式で記述され、IAMポリシーと似た構文を使用しますが、動作原理が大きく異なります。SCPは「ガードレール」として機能し、組織内のプリンシパル（ユーザー、ロール、ルートユーザー）が実行できるアクションの最大範囲を定義します。
SCPの重要な特徴として、明示的拒否（Explicit Deny）の概念があります。SCPで「Deny」ステートメントが適用されると、他のどのようなポリシー（IAMユーザーポリシー、ロールポリシー、リソースベースポリシーなど）でも、その拒否をオーバーライドできません。これにより、組織レベルでの確実なアクセス制御が実現できます。
なお、SCPが効くのはメンバーアカウントのプリンシパルに対してのみで、組織の管理アカウント内のユーザーやロール、およびサービスにリンクされたロール（service-linked role）には適用されません。管理アカウントの操作まで縛りたい場合は、管理アカウントを日常業務に使わない運用と、IAMポリシーやリソースコントロールポリシー（RCP）などの併用で補います。
AWS Organizationsの階層構造 AWS Organizationsは階層構造を持ち、最上位にルート、その下に組織単位（OU）、さらにその下に個別のAWSアカウントが配置されます。SCPは継承性を持ち、上位レベルで適用されたSCPは自動的に下位のすべてのエンティティに適用されます。ルートレベルでSCPを適用すると、配下のすべてのOUとメンバーアカウントに一律に制御が効き、あとから作成・招待されたアカウントにも自動的に継承されます（前述のとおり管理アカウントは対象外です）。
IPアドレス制御の条件キー AWSでは「aws:SourceIp」という条件キーを使用して、リクエストの送信元IPアドレスに基づく制御が可能です。この条件キーは、AWS Management Console、CLI、SDK、APIを通じたリクエストで利用でき、CIDR表記（例：192.168.1.0/24）を使用してIPアドレス範囲を指定できます。ただし、AWSサービスがユーザーに代わってリクエストを実行する場合（AWS CloudFormationによるリソース作成など）やVPCエンドポイント経由のリクエストでは、aws:SourceIpが期待どおりに評価されないことがあるため、実際の運用ではaws:ViaAWSServiceなどの条件キーと組み合わせた例外設定が必要です。
他のサービスとの違い AWS Firewall ManagerとAWS Network Firewallは、主にOSI参照モデルのネットワーク層（レイヤー3）からアプリケーション層（レイヤー7）でのトラフィック制御を行います。これらは、EC2インスタンス間の通信や、インターネットからVPCへのトラフィックを制御するために使用されますが、AWS APIの呼び出し自体を制御することはできません。
Amazon GuardDutyは、機械学習とルールベースの検出を使用して、アカウント内の悪意のある活動を特定する脅威検出サービスです。GuardDutyは異常なAPIアクティビティを検出してアラートを生成しますが、リアルタイムでのアクセス制御機能は提供しません。
アーキテクチャ図の解説



SCPの明示的拒否（Explicit Deny）は、承認済みIP以外からのAPIアクションを組織全体で遮断します。承認済みIPも範囲外IPも同じアカウントへ到達しますが（①③）、SCPがaws:SourceIp条件で評価し、承認済みIPは通過して許可され（②）、範囲外IPは即座に拒否されます（④）。SCPをルートOUへ適用すると、その制御はメンバーOUとアカウント、さらに新規アカウントへも自動継承されます。ここを「GuardDutyやFirewall Managerで送信元を制限すればよい」と読み替えるのが最も起きやすい誤解です。それらは検出やネットワーク経路の制御にとどまり、API認可には関与しません。許可のみのSCPは広いAllowに上書きされ得るため、Denyで塞ぐのが確実です。
解くための考え方
APIアクションを組織全体で止め、承認済みIP以外を明示的拒否できるかを見ます。
1. 要件の分析 まず、「AWSアカウントでアクションを実行することをブロック」という表現から、AWS APIレベルでの制御が必要であることを理解します。これは、ネットワークトラフィックの制御ではなく、認証・認可レベルでの制御を意味します。
2. 適切なサービスの特定 AWS APIアクションの制御には、IAMポリシーまたはSCPが適しています。複数アカウントにまたがる制御が必要なため、AWS OrganizationsのSCPが最適です。
3. 制御方法の決定 IPアドレスベースの制御には、aws:SourceIp条件キーを使用します。セキュリティの観点から、「許可する範囲を指定」するのではなく、「拒否する範囲を明示的に指定」する方が確実です。
4. 適用範囲の検討 組織のルートレベルでSCPを適用することで、すべての配下アカウントに一貫した制御を適用できます。これにより、新しく作成されるアカウントにも自動的に制御が適用されます。

前提知識
Amazon EventBridge
Amazon EventBridgeは、イベントによってアプリケーションコンポーネントを接続するためのサーバーレスイベントバスサービスです。主要な概念と機能は以下の通りです：
イベント：

アプリケーションやサービスの状態変化を表すJSONオブジェクト

ソースから発行され、ターゲットに届けられる

イベントバス：

イベントを受信し、ルールに基づいてターゲットに配信するルーター

デフォルトイベントバス、カスタムイベントバス、パートナーイベントバスの3種類がある

ルール：

イベントパターンと、一致するイベントが発生した際に実行するアクションを定義

複数のターゲットを持つことが可能

ターゲット：

イベントが特定のルールに一致した際に呼び出されるリソース

AWS Lambdaやステップ関数、SNS、SQSなど多様なサービスが対象となる

主な制限と考慮事項：

ターゲットへの配信は「少なくとも1回（at-least-once）」であり、配信失敗時は再試行ポリシーに基づき最大24時間再試行される

再試行期間を超えても配信できなかったイベントは、デッドレターキューを設定していない場合失われる

デフォルトでは失敗したイベントの内容を後から確認する仕組みがない（DLQ等の設定が必要）

CloudTrailは、AWSアカウント内のアクティビティをログに記録し、継続的にモニタリングして監査するためのサービスです。

AWSアカウント内のAPIコールと関連イベントを記録

誰が、いつ、どのリソースに対してどのようなアクションを行ったかを追跡

イベント履歴を過去90日間保存（デフォルト）

S3バケットにログを長期保存可能

PutRule - ルールの作成・更新

PutTargets - ターゲットの追加・更新

RemoveTargets - ターゲットの削除

DeleteRule - ルールの削除

その他のEventBridge API呼び出し

Amazon SQS
Amazon Simple Queue Service（SQS）は、マイクロサービス、分散システム、サーバーレスアプリケーション間のメッセージングを管理するための完全マネージド型メッセージキューイングサービスです。
キュータイプ：

スタンダードキュー：高いスループット、少なくとも1回の配信保証、順序は保証されない

FIFOキュー：正確に1回の処理保証、厳密な順序保証、但しスループットに制限あり

デッドレターキュー（DLQ）：

正常に処理できなかったメッセージを保存するキュー

メインキュー（またはイベントターゲット）の設定でDLQを指定可能

トラブルシューティングや障害分析に有用

保持期間を設定して、後でメッセージを再処理可能

CloudWatch Logsは、システム、アプリケーション、AWS サービスからログファイルをモニタリング、保存、アクセスするためのサービスです。
主な特徴：

ログデータをリアルタイムで監視

CloudWatch Logsインサイトでログデータをクエリ・分析

イベントの詳細をロググループに記録可能

イベントのフォーマット、タイミング、メタデータを検証

イベントの整合性確認やトラブルシューティングに活用

アーキテクチャ図の解説



アプリは変更せず、EventBridgeの周辺に監視と退避の層を足して問題を追います。注文配信アプリから発行されたイベント（①）が本来のターゲットへ届かない場合に備え、CloudWatch Logsを追加ターゲットにして届いたイベントの内容とメタデータを記録し（③）、SQSスタンダードキューをDLQにして配信失敗したイベントを保存します（④）。さらにCloudTrailでPutEventsやPutRuleなどのAPIコールを記録しS3へ長期保存することで（⑤⑥）、発行状況と整合性を確認できます。FIFOキューはEventBridgeのDLQには使えないため、順序を気にせず失敗分を逃さず残せるスタンダードキューが適します。3つの手段はいずれもルールの設定変更だけで済み、再デプロイは不要です。
解くための考え方
アプリは再デプロイせず、EventBridgeの周辺に記録とDLQを足して届かないイベントを追います。
まず、問題の可能性のある原因を整理しましょう：
イベントの発行に関する問題：

イベントが正しく発行されていません

イベントの形式が正しくありません

発行されるイベントの内容やメタデータに問題があります

イベントのルーティングに関する問題：

EventBridgeルールのイベントパターンが不適切でイベントと一致しません

ルール自体に設定ミスがあります

権限の問題でイベントが処理できません

ターゲットへの配信に関する問題：

ターゲットが正しく設定されていません

ターゲットが利用できません

ターゲットの処理に失敗しています

これらの問題を特定し、解決するためには、以下の方法が効果的です：
イベント発行とAPI呼び出しの監視：

AWSアカウント内のAPI呼び出しを記録するCloudTrailを有効化し、S3バケットにログを保存することで、イベントがいつ、どのように発行されたかを確認できます。

EventBridgeルールにSQSスタンダードキューをデッドレターキューとして設定することで、ターゲットに配信できなかったイベントをキャプチャし、その内容を分析できます。

イベントの監視とログ記録：

CloudWatch LogsをEventBridgeルールの追加ターゲットとして設定することで、ルールにマッチするすべてのイベントを記録し、分析することができます。

これらの方法は、アプリケーションコード自体を変更せずに実装できるため、「アプリケーションの再デプロイを行わずに」という要件を満たします。さらに、これらの方法を組み合わせることで、イベントフローの全体像を把握し、問題の根本原因を特定するために役立ちます。

認証方式: HTTPS Git認証情報、SSH公開鍵、またはgit-remote-codecommitを使用した認証が可能です

なお、CodeCommitは2024年7月25日にいったん新規顧客の受け付けを停止しましたが、2025年11月24日に一般提供（GA）へ復帰し、現在は新規のAWSアカウントでもリポジトリを作成できます。したがって本問のようにCodeCommitを前提とした構成は、新規に構築する場合でも成立します。
AWS CodeBuild AWS CodeBuildは、ソースコードのコンパイル、テストの実行、およびデプロイ可能なパッケージの作成を行うフルマネージドの継続的インテグレーション（CI）サービスです：

buildspecファイル: ビルドプロセスを定義するYAML形式の設定ファイルで、install、pre_build、build、post_buildの各フェーズでコマンドを実行できます

環境変数: CODEBUILD_BUILD_SUCCEEDINGなどの組み込み環境変数を使用して、ビルドの成功・失敗を判定できます

Git統合: 標準的なGitコマンドをネイティブにサポートしており、git-credential-helperを有効にすることで、CodeCommitへの認証を自動化できます

フェーズ別実行: 各フェーズで異なるコマンドを実行でき、前のフェーズが失敗した場合は後続のフェーズは実行されません

権限管理: IAMロールを使用してCodeCommitリポジトリへの読み書きアクセス権限を制御できます

AWS CodePipeline AWS CodePipelineは、継続的インテグレーション・継続的デリバリー（CI/CD）パイプラインを構築するためのサービスです：

パイプライン構成: ソース、ビルド、テスト、デプロイの各ステージを定義できます

トリガー機能: CodeCommitリポジトリの変更を自動的に検出し、パイプラインを実行できます

サービス統合: CodeBuild、CodeDeploy、Lambda関数などのAWSサービスと統合できます

Gitタグ Gitタグは、リポジトリ内の特定のコミットに対して人間が理解しやすい名前を付けるGitの機能です：

軽量タグ（Lightweight Tag）: 特定のコミットへの単純な参照で、追加のメタデータは含まれません

注釈付きタグ（Annotated Tag）: タグ作成者の情報、作成日時、タグメッセージなどのメタデータを含む完全なGitオブジェクトです

作成コマンド: git tag <tag_name>で軽量タグ、git tag -a <tag_name> -m "message"で注釈付きタグを作成できます

プッシュ操作: デフォルトではgit pushコマンドでタグはプッシュされないため、git push origin <tag_name>で明示的にプッシュする必要があります

使用目的: 通常はリリースバージョン（v1.0.0など）やマイルストーンを示すために使用されます

アーキテクチャ図の解説



CodeBuildがネイティブGitでリポジトリをクローンし、単体テストの成功後にgit tagでタグを付けてgit pushで反映する点が要点です。開発者がCodeCommitのmainブランチへコミットすると（①）、CodePipelineが変更を検知してパイプラインを起動し（②）、CodeBuildがクローンして単体テストを実行します（③）。テスト成功時のみタグを作成し（④）、git pushでCodeCommitへ反映します（⑤）。CodeCommit APIにはGitタグを直接作成するエンドポイントがないため、AWS CLIでタグを作ろうとしても最終的にはGitコマンドが必要です。クローンからプッシュまでをGitで統一しないと、履歴やメタデータが欠落してエラーを招きます。
解くための考え方
一貫性の重要性 GitリポジトリはGitエコシステムの一部として設計されているため、すべての操作をGitコマンドで統一します。クローン、コミット、タグ付け、プッシュなどの操作を同一のツールセットで行うことで、以下の利点があります：

メタデータの保持: Gitの内部構造やメタデータが適切に維持されます

エラーの最小化: 異なるツール間でのデータ変換によるエラーのリスクが軽減されます

保守性の向上: 標準的なGitワークフローに従うことで、チーム全体の理解が容易になります

API制限の理解 AWS CLIとCodeCommit APIの制限を理解することは重要です：

タグ作成API: CodeCommit APIにはGitタグを直接作成するエンドポイントが存在しないため、タグ作成には必ずGitコマンドが必要です

コードの取得: AWS CLIでコードを「コピー」する方法は、実際にはファイルのダウンロードであり、Gitの履歴や関連メタデータは失われます

CodeBuildでの実装アプローチ CodeBuildでGitタグを作成する最適な方法：

1. git-credential-helper: buildspecファイルでgit-credential-helperをyesに設定し、CodeBuildの自動認証機能を活用します

2. 条件分岐: CODEBUILD_BUILD_SUCCEEDING環境変数を使用して、テスト成功時のみタグを作成します

3. エラーハンドリング: 各ステップでエラーチェックを行い、失敗時の適切な処理を実装します

実装例

version: 0.2
env:
  git-credential-helper: yes
phases:
  install:
    runtime-versions:
      nodejs: 20
  pre_build:
    commands:
      - echo "Installing dependencies..."
      - npm install
  build:
    commands:
      - echo "Running unit tests..."
      - npm test
  post_build:
    commands:
      - echo "Build phase completed with status $CODEBUILD_BUILD_SUCCEEDING"
      - |
        if [ "$CODEBUILD_BUILD_SUCCEEDING" = "1" ]; then
          TAG_NAME="build-$(date +%Y%m%d-%H%M%S)"
          git tag "$TAG_NAME"
          git push origin "$TAG_NAME"
          echo "Tag $TAG_NAME created and pushed successfully"
        else
          echo "Build failed, skipping tag creation"
        fi
このアプローチにより、標準的なGitワークフローを維持しながら、効率的かつ信頼性の高い方法で要件を満たすことができます。

問題72
不正解
ある企業のマーケティング部門は、新製品のプロモーションサイト（静的ウェブサイト）をAmazon S3バケットでホスティングし、AWS CloudFormationで管理しています。このテンプレートにはS3バケットと、Web制作会社が納品した数百の画像・HTML・CSSファイルを指定の場所からS3バケットへ転送するカスタムリソースが含まれています。
キャンペーンの終了に伴い、同社はこのプロモーションサイトを別のドメインへ移行するため、既存のCloudFormationスタックを削除して再デプロイしようとしました。ところが、CloudFormationがスタックを削除できません。
この問題の最も考えられる原因と、今後のプロモーションサイトのデプロイで同じ問題を防ぐ方法を教えてください。

正解
削除の失敗は、S3バケットにオブジェクトが残っていることが原因です。カスタムリソースのLambda関数を変更し、RequestTypeがDeleteのときにバケットを空にするようにします。

説明
正解 AWS CloudFormationは、オブジェクトが残っているS3バケットを既定では削除しません。スタック削除の過程でCloudFormationがバケットの削除を試みても、バケットが空でなければ操作は失敗します。この問題を解消するには、カスタムリソースのLambda関数を調整し、スタックが削除される際（RequestTypeがDeleteのとき）にバケット内のすべてのオブジェクトを削除するロジックを追加します。こうすると、スタック削除の段階でバケットが自動的に空になり、CloudFormationがバケットを正常に削除できるようになります。

削除の失敗は、S3バケットに静的ウェブサイトホスティングの設定が残っていることが原因です。テンプレートを更新して、S3バケットリソースからWebsiteConfigurationプロパティを取り除きます。

説明
不正解 静的ウェブサイトホスティングの設定が有効かどうかは、バケットの削除失敗の原因にはなりません。ホスティング設定の有無にかかわらず、S3バケットは削除できます。この設定はバケットに付随する機能の一つにすぎず、削除操作そのものを妨げる要因ではありません。スタック削除が失敗する原因は、バケットにオブジェクトが残っている（バケットが空でない）ことです。

回答は不正解です
削除の失敗は、S3バケットにオブジェクトが残っていることが原因です。テンプレートのS3バケットリソースにDeletionPolicyプロパティを追加し、値にEmptyを指定します。

説明
不正解 CloudFormationのDeletionPolicy属性にEmptyという値は存在しません。指定できる値はDelete（既定）、Retain（スタック削除後もリソースを保持）、RetainExceptOnCreate（作成失敗によるロールバック時を除きリソースを保持）、およびスナップショットに対応する一部のリソースで使えるSnapshot（削除前にスナップショットを作成）のみです。S3バケットについて、スタック削除時にバケットを自動的に空にする組み込み機能はCloudFormationにはありません。この動作を実現するには、Lambda関数などによるカスタムロジックが必要です。

削除の失敗は、カスタムリソースに削除ポリシーが定義されていないことが原因です。RemoveOnDeletionという値の削除ポリシープロパティをカスタムリソース定義へ追加します。

説明
不正解 CloudFormationで削除時の扱いを指定する正しい属性はDeletionPolicyであり、指定できる値はDelete、Retain、RetainExceptOnCreate、Snapshotのいずれかです。RemoveOnDeletionという値は存在しません。さらに、カスタムリソースに削除ポリシーを設定しても、S3バケットが空でないことに起因する削除失敗は解決されません。カスタムリソース自体の削除と、そのカスタムリソースが転送したコンテンツを保持するS3バケットの削除は別の問題です。

全体的な説明
問われている要件

CloudFormationスタックの削除が失敗している最も考えられる原因を特定すること

別ドメインへの移行後、今後のプロモーションサイトのデプロイで同じ問題を回避する方法を提案すること

状況としては、静的ウェブサイトをホスティングするS3バケットを含むCloudFormationスタックを、キャンペーン終了後の別ドメイン移行に伴って削除して再デプロイしようとしたところ、削除に失敗しているというものです。
前提知識
Amazon S3バケットとCloudFormation
S3バケットの削除条件:

S3バケットを削除するには、まずバケット内のすべてのオブジェクト（ファイル）を削除する必要があります（バケットが空でない状態でのDeleteBucketはBucketNotEmptyエラーになります）

バージョニングが有効な場合は、すべてのバージョン（削除マーカーを含む）も削除する必要があります

マルチパートアップロードの不完全な部分も削除する必要があります

CloudFormationとS3バケットの関係:

CloudFormationはスタック内のリソース（S3バケットなど）を作成・更新・削除します

スタック削除時、CloudFormationは通常、スタック内のすべてのリソースを削除しようとします

しかし、S3バケットが空でない場合、CloudFormationはデフォルトでバケットの削除に失敗します

これは、データの誤削除を防ぐための安全策

CloudFormationのDeletionPolicy
DeletionPolicyの概要:

CloudFormationのリソースに適用できる属性

スタック削除時のリソースの扱いを指定

S3バケットに適用可能な値は次のとおり

Delete: スタック削除時にリソースを削除（デフォルト）

Retain: スタック削除後もリソースを保持

RetainExceptOnCreate: 作成失敗によるロールバック時を除きリソースを保持

DeletionPolicyの例:

Resources:
  MyS3Bucket:
    Type: AWS::S3::Bucket
    DeletionPolicy: Retain
CloudFormationのカスタムリソース
カスタムリソースの概要:

CloudFormationで標準リソース以外の操作を行うための仕組み

AWS Lambdaと組み合わせて使用することが一般的

3つのライフサイクルイベントを処理

Create: リソース作成時

Update: リソース更新時

Delete: リソース削除時

カスタムリソースのLambda関数の基本構造:

exports.handler = async (event, context) => {
  const requestType = event.RequestType;
  if (requestType === 'Create') {
    // リソース作成時の処理
  } else if (requestType === 'Update') {
    // リソース更新時の処理
  } else if (requestType === 'Delete') {
    // リソース削除時の処理
  }
  // CloudFormation にレスポンスを返す
};
S3バケットを空にするためのカスタムリソース実装例:

const { S3Client, ListObjectsV2Command, DeleteObjectsCommand } = require('@aws-sdk/client-s3');
const s3 = new S3Client({});
exports.handler = async (event, context) => {
  const requestType = event.RequestType;
  const bucketName = event.ResourceProperties.BucketName;
  if (requestType === 'Delete') {
    // バケットを空にする処理
    await emptyS3Bucket(bucketName);
  }
  // CloudFormation にレスポンスを返す
};
async function emptyS3Bucket(bucketName) {
  // オブジェクトのリストを取得
  const listed = await s3.send(new ListObjectsV2Command({ Bucket: bucketName }));
  const contents = listed.Contents || [];
  if (contents.length === 0) return;
  // オブジェクトを削除
  await s3.send(new DeleteObjectsCommand({
    Bucket: bucketName,
    Delete: { Objects: contents.map(({ Key }) => ({ Key })) }
  }));
  // すべてのオブジェクトが削除されるまで再帰的に実行
  if (listed.IsTruncated) await emptyS3Bucket(bucketName);
}
アーキテクチャ図の解説



スタックの作成時と削除時で、カスタムリソースのLambdaが担う処理は異なります。作成時（①〜④）は、LambdaがWeb制作会社のサイトデータを指定URLから取得してS3バケットへ転送します。問題になるのは削除時（⑤〜⑧）で、LambdaのRequestType=Delete分岐にバケットを空にする処理が無かったため、オブジェクトが残ったままCloudFormationがバケット削除を試みて失敗していました。削除分岐にlistObjectsV2とdeleteObjectsで全オブジェクトを再帰削除する処理を足せば、空になったバケットをCloudFormationが正常に削除できます。失敗の原因は「オブジェクトの残存」にあります。
解くための考え方
削除時にバケットを空にできず、CloudFormationの削除が止まっていないかを見ます。
S3バケット削除失敗の一般的な原因:

S3バケットが空でない場合、CloudFormationは削除に失敗します

これは最も一般的な原因です

カスタムリソースの役割:

問題文では、カスタムリソースがコンテンツをS3バケットに転送していると言及

しかし、スタック削除時にバケットを空にする処理が含まれていない可能性が高い

解決策の検討:

カスタムリソースのLambda関数を調整して、削除イベント時にバケットを空にします

バケットが空になれば、CloudFormationは通常どおりバケットを削除できます

今後の問題防止:

スタック削除時のクリーンアップ処理を確実に実装

またはDeletionPolicyを使用したリソース管理方法の検討

これらを考慮すると、最も可能性の高い原因は「S3バケットが空でないため削除に失敗した」ことであり、最適な解決策は「カスタムリソース内のLambda関数でRequestTypeがDeleteの場合にバケットを空にする処理を追加する」ことです。
