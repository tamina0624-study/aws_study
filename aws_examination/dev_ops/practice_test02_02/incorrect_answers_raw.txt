前提知識
AWS OrganizationsアカウントタイプとRole自動作成について

AWS Organizationsでは、組織経由で新規作成されたアカウントと、既存アカウントを招待したアカウントで動作が異なります。組織経由で作成されたアカウントでは、OrganizationAccountAccessRoleが自動的に作成され、管理アカウントからのクロスアカウントアクセスが即座に利用可能になります。一方、既存アカウントを招待した場合、このロールは自動作成されないため、手動での設定が必要です。

OrganizationAccountAccessRoleの構成要素について

OrganizationAccountAccessRoleは、AdministratorAccessマネージドポリシーがアタッチされたIAMロールで、メンバーアカウント内のすべてのリソースに対する完全な管理権限を提供します。Trust Policyでは、管理アカウントのルートユーザーまたは特定のIAMプリンシパルを信頼するよう設定し、sts:AssumeRoleアクションを許可します。このロールにより、管理アカウントからメンバーアカウントに切り替えて管理作業を実行できます。

買収アカウント統合時の技術的課題について

企業買収時のAWSアカウント統合では、既存のIAM設定、リソース命名規則、セキュリティポリシー等の差異が課題となります。買収先アカウントは独立した環境で運用されていたため、組織標準のロールや設定が存在しない場合があります。統合作業では、セキュリティを維持しながら管理効率を向上させるため、標準的なクロスアカウントアクセス機能の確立が重要です。

IAMロール信頼ポリシーとクロスアカウントアクセスについて

IAMロールの信頼ポリシーは、そのロールを引き受けることができるプリンシパルを定義します。クロスアカウントアクセスでは、異なるAWSアカウントのユーザーやロールを信頼するよう設定し、AssumeRoleAPIを通じて一時的な認証情報を取得できます。External IDやMFA要求等の追加セキュリティ条件も設定可能で、セキュアなクロスアカウント運用を実現できます。

この問題は、AWS Organizationsにおける買収アカウント統合時の典型的な課題を扱っています。エラーメッセージ「Invalid information in one or more fields」は、通常、指定されたロールが存在しないか、信頼関係が正しく設定されていない場合に発生します。
組織経由で作成されたアカウントでは、OrganizationAccountAccessRoleが自動的に作成され、管理アカウントとの信頼関係も自動設定されます。しかし、既存アカウントを招待した場合、このような自動設定は行われません。これは、既存アカウントの独立性を尊重し、意図しない権限付与を防ぐためのセキュリティ設計です。
問題解決には、メンバーアカウント内でのロール作成が必要です。管理アカウント側での権限追加やSCPの設定では、根本的な原因であるロール不存在を解決できません。また、管理アカウント内でのロール作成も、クロスアカウントアクセスの仕組み上、意味がありません。
正しいアプローチは、メンバーアカウント内でOrganizationAccountAccessRoleを作成し、適切な権限ポリシーと信頼ポリシーを設定することです。これにより、管理アカウントのDevOpsエンジニアが、既存のワークフローを維持しながらメンバーアカウントにアクセスできるようになります。
このような統合作業は、企業買収時のIT統合において重要な要素であり、セキュリティを維持しながら運用効率を向上させるために不可欠です。
実装の考慮事項
実装時は、Trust PolicyでのMFA要求設定、External IDによる追加セキュリティ、ロール利用状況の監視設定が重要です。また、買収先アカウントの既存IAMポリシーとの競合確認、CloudTrailによるクロスアカウントアクセスの監査ログ設定により、セキュアで透明性の高い統合を実現する必要があります。

前提知識
Service Control Policy（SCP）の基本概念について

SCPは、AWS Organizations配下のアカウントやOUに対する最大権限を定義するガードレール機能です。IAMポリシーとは異なり、SCPは権限を付与せず、実行可能なアクションの上限を設定します。SCPで許可されていない（または明示的に拒否された）アクションは、IAMポリシーで許可されていても実行できません。

SCPは組織階層に沿って継承され、親OUのSCPは子OUとその配下のアカウントに自動的に適用されます。複数のSCPが適用される場合、すべてのSCPで許可されたアクションのみが実行可能になります。この継承メカニズムにより、組織レベルでの一貫したガバナンスを実現できます。

SCP評価ロジックと優先順位について

SCP評価では、ルートOUから対象アカウントまでの階層すべてのSCPが評価されます。いずれかのSCPでアクションが拒否されている場合、そのアクションは実行できません。明示的拒否、明示的許可、デフォルト拒否の優先順位により、厳格なアクセス制御が実現されます。

IAMポリシーとSCPの関係では、SCPが「ガードレール」として機能し、IAMポリシーが「実際の権限」を定義します。両方で許可されたアクションのみが実行可能であり、どちらか一方で拒否されれば全体として拒否されます。この二重制御により、意図しない権限拡大を防止できます。

Organizations階層設計のベストプラクティスについて

OUの設計では、機能別のグループ化、SDLC（ソフトウェア開発ライフサイクル）の考慮、将来的な拡張性を重視します。一般的には、セキュリティOU、本番OU、非本番OU、サンドボックスOU等の機能別分類が推奨されます。各OUには目的に応じたSCPを適用し、適切なガバナンスを実現します。

SCPの適用レベルでは、主にOUレベルでの適用を推奨し、アカウントレベルでの適用は最小限に抑えます。これにより、管理の複雑さを軽減し、トラブルシューティングを容易にできます。階層の深さとポリシーの適用箇所を最小限にすることで、問題発生時の原因特定が効率化されます。

SCPトラブルシューティングの手法について

アクセス拒否問題の解決では、IAMポリシーシミュレーター、CloudTrail、AWS Config等のツールを活用して権限評価プロセスを詳細に分析します。SCPの適用状況は、Organizationsコンソールの「ポリシー」セクションで確認でき、各アカウントに適用されているSCPの一覧と内容を把握できます。

段階的なテストアプローチでは、テスト用アカウントでSCP変更の影響を事前検証し、本番環境への適用前にリスクを最小化します。SCP変更後は、CloudTrailログを監視して意図しない動作がないことを確認し、必要に応じて迅速にロールバックできる体制を整備します。

アーキテクチャ図の解説



SCPが組織階層に沿って継承され、最も制限的な子OUのポリシーが優先されることを示した図です。親OUのSCPは「すべてのAWS操作を許可」していますが、子OUのSCPは「DynamoDBとLambdaのみ許可し、それ以外を拒否」しています。評価は親OUと子OUの双方のSCPを重ね合わせ、両方で許可された操作だけが実行可能になります。supplier-dataアカウントのIAMユーザーはAdministrator Accessを持ちますが、子OUのSCPの許可リストにEC2が含まれないため、暗黙的な拒否となりEC2インスタンスを起動できません。この図の落とし穴は、IAM側の権限をいくら強めてもSCPで許可されていない操作は実行できない点です。対処は子OUのSCPへEC2アクションを追加するのが唯一の筋道です。
解くための考え方
現状は、親OU（全操作許可）→ 子OU（DynamoDB・Lambda以外拒否）→ supplier-dataアカウント（Administrator Access）という階層で、最も制限的な子OUのSCPが効いています。
問題の根本原因は、子OUのSCPが「DynamoDBとLambdaのみ許可、それ以外拒否」という設定になっていることです。このため、EC2操作は子OUのSCPの許可リストに含まれず拒否され、IAMユーザーがAdministrator Accessを持っていても実行できません。
解決策の選択では、変更の影響範囲と効果を考慮する必要があります。子OUのSCP修正は、直接的な原因に対する最小限の変更であり、他のアカウントへの影響も予測可能です。IAMポリシーの追加やアカウントレベルのSCP適用は、SCPの動作原理に反するため効果がありません。
実装の考慮事項
SCPを直す前に、配下の他アカウントへの影響を見てから段階的に展開します。EC2を許可したあとのリスクも評価し、必要ならインスタンスタイプやリージョンの制約を足します。変更後は継続的な監視により、意図しない動作がないことを確認する必要があります。

前提知識
Kubernetesスケーリング機能の特徴について

Horizontal Pod Autoscalerはポッドのレプリカ数を制御し、CPU使用率、メモリ使用率、またはカスタムメトリクスに基づいて動作します。デフォルトでは15秒間隔でメトリクスを評価し、スケールダウンには5分（300秒）の安定化ウィンドウがデフォルトで設定されています（スケールアップの安定化ウィンドウのデフォルトは0秒）。メトリクスサーバーが必要で、resource requestsが適切に設定されている必要があります。

Vertical Pod Autoscalerは個々のポッドのCPU・メモリリソース要求を動的に調整し、過去の使用パターンを分析して最適な設定を推奨します。更新モードにはAuto、Recreate、Initial、Offがあり、従来はいずれの適用時もポッドの再作成を伴うため一時的なサービス中断が発生していました。なお、Kubernetes 1.33でポッドのインプレースリサイズがベータ、1.35で正式機能となり、VPA 1.4以降ではポッドを再作成せずに要求値を変更するInPlaceOrRecreateモードも選択できます（対応していないリソース変更では従来どおり再作成にフォールバックします）。

クラスターレベルのスケーリングについて

Cluster Autoscalerはノードグループの設定に基づいてワーカーノード数を自動調整し、未スケジュールポッドの存在時にノードを追加します。スケールダウンは使用率が50%を下回るノードを10分後に削除する設定がデフォルトです。PodDisruptionBudgetやnode affinityの設定により、スケールダウンが制限される場合があります。

Karpenterは次世代のノードオートスケーラーで、より高速で効率的なノードプロビジョニングを提供し、多様なインスタンスタイプとアベイラビリティゾーンに対応します。

EKSとAWSサービス連携について

AWS Load Balancer ControllerはALB・NLBをKubernetesリソースとして管理し、IngressリソースやLoadBalancer型Serviceと連携します。ターゲットグループの作成、ヘルスチェック設定、SSL終端などを自動化し、EKSクラスター外からのトラフィック受信を効率的に処理します。

EBS CSI DriverやEFS CSI Driverにより、永続ストレージの動的プロビジョニングが可能で、ステートフルアプリケーションの運用に対応します。IAMロールとサービスアカウント（IRSA）を使用して、ポッドレベルでのAWSサービスアクセス制御が実現できます。

アーキテクチャ図の解説



受注処理アプリがトラフィック受信前に最大ポッド数へスケールアウトする原因は、リソース要求（resource requests）の過小設定にあり、VPAで是正します。①②トラフィックはALB経由で問題状態のPodへ到達します。resource requestsが実際の必要量より大幅に低いと、使用率が異常な高値として算出され、多数のPodが生成されます。③VPAが過去の使用パターンを分析し、④resource requestsを実際のニーズに合わせて最適化してPodを再作成します（まずOffモードで推奨値を確認しAutoモードへ移行します）。⑤最適化後は適切なポッド数で安定稼働します。HPAやCluster Autoscalerでは、リソース要求値の誤りを直せません。
解くための考え方
ポッドのスケーリングは通常、リソース使用率やトラフィック量に応じて段階的に進みます。トラフィック受信前に最大ポッド数まで一気にスケールアウトするのは、リソース要求の設定ミスを疑います。
最も可能性が高い原因は、アプリケーションのリソース要求（resource requests）が実際の必要量よりも大幅に低く設定されていることです。オートスケーリングにおける使用率は「実際の使用量÷リソース要求」で算出されるため、要求量が少なすぎると、アイドル状態でも使用率が目標値を大きく超える異常な高値となります。その結果、トラフィックを受信していなくても、デプロイ直後に最大ポッド数までスケールアウトするという本問のような挙動が発生します。
Vertical Pod Autoscalerを使用することで、過去のリソース使用パターンを分析し、CPU・メモリリソース要求を実際のニーズに合わせて自動調整できます。適切なリソース要求が設定されることで、不必要なポッドの生成が防止され、リソース効率が向上します。また、VPAの推奨機能により、アプリケーションの最適なリソース配分を継続的に維持できます。
実装の考慮事項
VPAはまずOffモードで推奨値を確認し、段階的にAutoモードへ移します。ポッドの再作成によるサービス中断を最小化するため、複数レプリカでの運用やPodDisruptionBudgetの設定、あるいはインプレースリサイズに対応したクラスターでのInPlaceOrRecreateモードの利用を検討します。また、HPAとVPAの同時使用は競合を避けるため、慎重な設計が必要です。

前提知識
CloudTrailイベントとEventBridgeの統合について

AWS CloudTrailは、AWSアカウント内でのAPI呼び出し、コンソール操作、AWSサービスアクションを自動的に記録し、これらのイベントをEventBridgeのデフォルトイベントバスへ配信します。OrganizationsのCreateAccount API呼び出しは、管理アカウントまたは委任された管理者アカウントのCloudTrailに記録され、対応するEventBridgeイベントが生成されます。なお、AWS Organizationsはグローバルサービスですが米国東部（バージニア北部）リージョンでホストされているため、そのCloudTrailイベントは同リージョンのデフォルトイベントバスへ配信されます。イベントを捕捉するEventBridgeルールも米国東部（バージニア北部）に作成する必要があります。

EventBridgeルールでCloudTrailイベントをフィルタリングし、特定のAPI呼び出し（例：organizations:CreateAccount）に対してだけアクションを実行できます。ルールの条件設定でイベントソース、詳細タイプ、特定のAPIアクションなどを指定し、精密なイベント処理を実現できます。

クロスアカウントEventBridge配信について

EventBridgeは、AWSアカウント間でのイベント共有をネイティブにサポートしており、ソースアカウントのEventBridgeルールから、ターゲットアカウントのイベントバスへ直接イベントを送信できます。クロスアカウント配信では、送信側のルール設定と受信側のリソースベースポリシー設定の両方が必要です。

ターゲットアカウントのイベントバスには、ソースアカウントからのイベント受信を明示的に許可するリソースベースポリシーを設定する必要があります。このポリシーにより、特定のAWSアカウント、特定のプリンシパル、または特定の条件下でのみイベント受信を許可でき、セキュリティと制御を確保できます。

デフォルトイベントバスとカスタムイベントバスについて

デフォルトイベントバスは、すべてのAWSアカウントに自動的に作成され、AWSサービスが生成するイベント（CloudTrail、Auto Scaling、EC2など）を受信します。AWS標準サービスとの統合が最適化されており、追加設定なしで即座に利用できます。CloudTrailイベント、AWS Config変更、Systems Managerアクションなどは、デフォルトイベントバスへ自動配信されます。

カスタムイベントバスは、アプリケーション固有のイベント、サードパーティ統合、特定のワークロード分離などの目的で作成されます。マルチテナント環境でのイベント分離、組織内の異なる部門間でのイベント管理、特定のコンプライアンス要件などに用いられます。ただし、AWSサービス生成のイベントを処理するなら、通常はデフォルトイベントバスで十分です。

AWS Organizations環境でのイベント管理について

大規模なOrganizations環境では、中央集約型のイベント管理戦略が重要です。管理アカウントまたは専用の監査アカウントでOrganizationsイベントを捕捉し、EventBridgeで関連する子アカウントへ配信することで、統一的なガバナンスと可視性を実現できます。

アカウント作成、OU変更、ポリシー適用などのOrganizationsイベントは、セキュリティ監視、コンプライアンス報告、自動化トリガーなど様々な用途で活用されます。EventBridgeによるリアルタイム配信で、迅速な対応と自動化されたワークフローを実現できます。

イベントが発生する場所と受け取る場所がアカウントをまたいでいるため、発生元である自動化アカウントのデフォルトイベントバスから、受信側のデフォルトイベントバスへ直接転送します。CI/CDパイプラインがCreateAccount APIを呼び出すと、CloudTrailが自動化アカウント内にイベントを記録し（①）、デフォルトイベントバスへ自動配信します（②）。ルールがそのイベントを捕捉し（③）、各サービスアカウントのデフォルトイベントバスへクロスアカウント転送します（④）。サービスアカウント側ではリソースベースポリシーで自動化アカウントからの受信を明示的に許可しており、これが無いと転送が拒否されます。サービスアカウント側でイベントを直接監視しようとしても、イベントは発生元アカウントでしか記録されないため成立しません。
解くための考え方
CreateAccount APIは自動化アカウントで実行されるため、関連するCloudTrailイベントも自動化アカウントで記録されます。
発生元のデフォルトイベントバスから、受信側アカウントのデフォルトイベントバスへ直接転送します。受信側ではリソースベースポリシーで自動化アカウントからの受信を許可しないと、転送は拒否されます。
実装の考慮事項
EventBridgeのフィルタ、クロスアカウントの最小権限、配信の監視を入れます。大量のアカウント作成時のイベント配信負荷、配信失敗時のリトライ機構、長期的なイベント保存とアーカイブ戦略も考慮する必要があります。

CodeDeployエージェントとインフラストラクチャ要件について

CodeDeployエージェントは各EC2インスタンス上で動作するデーモンプロセスで、CodeDeployサービスからの指示を受信してローカルでデプロイメント処理を実行します

エージェントはS3からアプリケーションリビジョンをダウンロードし、AppSpecファイルに従ってファイル配置、スクリプト実行、サービス制御を行います

Auto Scalingグループ環境では、起動テンプレート（Launch Template）でエージェント事前インストール済みAMIを指定することで、新規インスタンスでの自動設定を実現できます。なお起動設定（Launch Configuration）は非推奨で、2024年10月1日以降に作成されたアカウントではどの手段でも新規作成できないため、現行の構成では起動テンプレートを使用します

インスタンスのIAMロール（インスタンスプロファイル）には、リビジョン取得のためのs3:GetObjectなどのS3読み取り権限が最低限必要で、CloudWatch Logsへログを出力する場合はlogs:CreateLogStream、logs:PutLogEventsなどの権限も付与します

インプレースデプロイメントとBlue/Greenデプロイメントの比較について

インプレースデプロイメントは既存インスタンス上でアプリケーションを直接更新する方式で、リソースコストが低く、設定が簡単です

Blue/Greenデプロイメントは新しいインスタンス群を作成してトラフィックを切り替える方式で、ロールバックが迅速ですが、切り替え期間中は新旧2組の環境が並存するためリソースコストが一時的に増加します

RPMパッケージによるアプリケーション更新では、通常インプレースデプロイメントが選択され、yumコマンドなどによるパッケージ管理が活用されます

Auto Scalingグループでのインプレースデプロイメントでは、CodeDeployが自動的に全インスタンスに対してローリング更新を実行します

CodePipelineとCodeDeployの統合について

CodePipelineのデプロイアクションでCodeDeployプロバイダーを選択することで、ビルドアーティファクトを自動的にCodeDeployアプリケーションに渡せます

アーティファクトはS3に保存され、CodeDeployが各インスタンスにダウンロードして展開します

デプロイメント設定では、一度に更新するインスタンス数や最小健全性インスタンス数を制御でき、可用性を維持しながら更新できます

Amazon EventBridge（旧CloudWatch Events）によりデプロイメント状況をモニタリングし、失敗時の自動ロールバックも設定可能です

ガードレール（コントロール）の種類と特徴
なお、「ガードレール」は2022年以降のAWSドキュメントでは「コントロール」と呼ばれています。Control Towerのコントロールには、適用のされ方によって次の3つのカテゴリがあります。

必須（Mandatory）: 自動的に有効化され、無効化できない。基本的なセキュリティとコンプライアンスを確保する。

強く推奨（Strongly recommended）: ベストプラクティスに基づくコントロールで、必要に応じて有効化・無効化できる。

選択的（Elective）: 特定のコンプライアンス要件に応じて任意で有効化する。

RDSストレージ暗号化を検出するコントロールは「強く推奨」カテゴリの検出型コントロールとして提供されています。
検出型ガードレール（検出型コントロール）の仕組み
検出型コントロールは、AWS Configルールを基盤として動作します。

自動展開: 有効化したOU配下のすべてのアカウントに自動的に展開され、新規アカウントにも自動的に適用される

継続的な監視: リソースの設定変更を検出し、定期的な評価も実行する

コンプライアンス状態の集約: 監査アカウントで全アカウントの状態を一元管理し、ダッシュボードで可視化する

EventBridgeとの統合
検出型コントロールの実体はAWS Configルールであるため、非準拠の検出はAWS ConfigのコンプライアンスイベントとしてEventBridgeに送信されます。
イベントパターンの例:

{
  "source": ["aws.config"],
  "detail-type": ["Config Rules Compliance Change"],
  "detail": {
    "newEvaluationResult": {
      "complianceType": ["NON_COMPLIANT"]
    }
  }
}
イベントの流れ:

1. 検出型コントロール（Configルール）が非準拠を検出

2. EventBridgeにコンプライアンス変更イベントが送信

3. ルールに基づいてターゲット（SNSトピック）が実行

なお、Control Towerは監査アカウントに集約用のSNSトピック（aws-controltower-AggregateSecurityNotificationsなど）を標準で用意しており、コンプライアンス通知の受け口として利用できます。

評価内容: ストレージ暗号化（KMSキーによる暗号化）が有効になっているか

評価タイミング: リソースの作成・設定変更時に評価される

コスト効率: 追加のインフラストラクチャを最小限にし、運用人員の工数を削減します

これらの要素を総合的に評価すると、AWS Control Towerの検出型ガードレールを活用し、EventBridgeとSNSで通知を自動化する方法が最も効率的です。この方法により、追加の開発作業なしに、すべての要件を満たすことができます。

前提知識
AWS Service Catalogの特徴について

AWS Service Catalogは、組織が承認したAWSリソースのカタログを作成・管理するサービスで、エンドユーザーは事前定義されたプロダクトのみを起動できます。管理者は CloudFormation テンプレートをプロダクトとして登録し、バージョン管理、アクセス制御、制約設定を行えます。

ローンチ制約により、プロダクト起動時に特定のIAMロールの使用を強制でき、エンドユーザーに過度な権限を付与することなく、必要なリソースの作成が可能です。テンプレート制約により、特定のパラメータ値を制限し、リソース設定の標準化を図れます。また、通知制約により、プロダクトのライフサイクルイベントをSNSトピックに送信できます。

AWS Configの監視機能について

AWS Configは、AWSリソースの設定変更を継続的に記録・評価するサービスで、事前定義されたルールに基づいてコンプライアンス状態を自動評価できます。設定変更があるたびにルールが実行され、違反があれば即座にSNSやEventBridgeを通じて通知が送信されます。

マネージドルールとカスタムルールの両方をサポートし、組織固有の要件に応じたコンプライアンス評価が可能です。修復機能（Remediation）により、違反が検出された際の自動修復アクションも設定できます。設定履歴により、リソースの変更タイムラインを追跡し、コンプライアンス監査に活用できます。

CloudFormation監視機能の比較について

CloudFormationドリフト検出は、スタックテンプレートとリソースの実際の設定を比較する機能ですが、実行はコンソール・API・AWS Configのマネージドルールなどから明示的に起動するオンデマンド方式で、設定変更のたびに自動で評価されるわけではありません。検出処理の完了や結果はEventBridgeのドリフト検出ステータス変更イベントで受け取れますが、継続的な監視にするにはスケジュール実行の仕組みを自前で組む必要があります。

CloudFormationスタックイベントは、スタック操作（作成、更新、削除）の履歴を提供しますが、個別リソースの設定変更は検出できません。AWS Configと比較して、きめ細かい設定変更の監視には限界があります。

ガバナンスとコンプライアンス管理について

組織レベルでのクラウドガバナンスには、事前承認（予防統制）と継続監視（検出統制）の両方が必要です。Service Catalogによる事前承認とConfigによる継続監視を組み合わせます。

IAMポリシー、SCPs、リソースベースポリシーと組み合わせることで、多層防御によるセキュリティ体制を確立できます。コンプライアンスフレームワーク（SOC、PCI-DSS、HIPAA等）への対応も、適切なルール設定により自動化できます。

アーキテクチャ図の解説



予防統制と検出統制は、2つの層に分けて組み合わせます。開発者はAWS Service Catalogの事前承認済みプロダクトのみを選択して起動でき、任意のテンプレートを使った直接のスタック作成は封じられます（①）。起動時にはローンチ制約が指定のIAMロールを強制適用し、過度な権限を与えずにリソース作成を許可します（②③）。作成されたリソースはAWS Configルールが継続的に監視し（④⑤）、計画された状態からの逸脱を検出するとSNSを通じて自動アラートを送信します（⑥）。テンプレートを固定することと、できた後の変更を監視することは別の統制で、片方だけでは片手落ちです。事前承認だけでは事後の逸脱に気付けず、監視だけでは承認されていないテンプレートの利用を止められません。
解くための考え方
指定されたテンプレートのみを使う予防統制と、リソース状態の逸脱を自動検出する検出統制の、両方を満たす必要があります。
予防統制では、AWS Service Catalogを使います。Service Catalogにより、管理者が事前承認したCloudFormationテンプレートのみをカタログとして公開し、開発チームはそのカタログ内のプロダクトのみを起動できます。ローンチ制約により、プロダクト起動時に適切なIAMロールが自動的に適用され、権限管理も自動化されます。
検出統制の観点では、AWS Configルールが継続的な監視と自動アラートを提供します。Configルールは、リソースの設定変更を検出するたびに評価を実行し、コンプライアンス違反があれば即座に通知を送信します。これにより、リアルタイムな逸脱検出と迅速な対応が可能になります。
CloudFormationサービスロールやドリフト検出だけでは、事前承認の仕組みや継続的な監視が不十分であり、予防と検出の両方の要件を満たせません。Service CatalogとConfigの組み合わせにより、予防と検出の両方の統制を実現できます。
実装の考慮事項
Service Catalogでは、プロダクトのバージョン管理、ポートフォリオによるグループ化、アクセス権限の設定が必要です。Configルールでは、組織の要件に応じたカスタムルールの作成、適切な通知先の設定、必要に応じた修復アクションの自動化を検討する必要があります。また、両サービスの料金も見積もります。

前提知識
EC2 Image Builderの配布機能について

Image Builderの配布設定（Distribution Settings）は、AMI作成プロセスの最終段階で実行される自動化機能で、作成されたAMIを指定されたリージョンに配布し、関連するAWSリソースを自動更新できます。起動テンプレートの更新、AMI共有、タグ付与、SSMパラメータへのAMI ID書き込み等の後処理を一元管理できます。なおパイプライン実行結果のSNS通知は、配布設定ではなくインフラストラクチャ設定で指定します。

起動テンプレート更新では、新しいAMI IDを使用して新しいテンプレートバージョンを自動作成し、必要に応じてデフォルトバージョンの変更も可能です。この機能により、Image Builderパイプラインの実行完了と同時に、関連するEC2起動インフラが最新のAMIを使用する状態になります。バージョン管理により、ロールバックや段階的展開も容易になります。

Auto Scalingグループと起動テンプレートの統合について
Auto Scalingグループは、起動テンプレートに対して次のいずれかのバージョン指定方法で設定できます。

特定バージョン番号（例：1、2、3）：明示的に指定したバージョンを固定使用

$Default：明示的にデフォルトとして設定されたバージョンを使用

$Latest：常に最新バージョンを自動的に使用

また起動テンプレートのImageIdには、AMI IDそのものに加えてSystems Managerパラメータへの参照（resolve:ssm:形式）も指定できます。パラメータ名、バージョン番号付き、ラベル付き、他アカウントから共有されたパラメータのARNのいずれの形式にも対応しています。
インスタンス更新機能により、既存インスタンスを新しいAMIに基づいて段階的に入れ替えることも可能です。更新ポリシーの設定により、ローリング更新、一括更新、手動更新等の戦略を選択でき、サービス継続性を保ちながらAMI更新を適用できます。更新プロセスは、ヘルスチェック、ウォームアップ時間、最大置換率等のパラメータで制御できます。
Image Builderパイプラインのスケジューリング機能について

Image Builderパイプラインは、手動実行、cron式による定期実行、EventBridgeのスケジュールルールによる実行をサポートします。定期実行では、スケジュールどおり常に実行する方式と、ベースイメージやコンポーネントに更新がある場合のみ実行する依存関係更新方式を選択できます。これにより、セキュリティパッチの定期適用、ベースイメージの更新、コンプライアンス要件への対応等を自動化できます。

パイプライン実行時は、ソースイメージの取得、コンポーネント適用、テスト実行、AMI作成、配布の各段階が順次実行されます。各段階での成功・失敗状況は詳細にログ記録され、問題発生時の原因特定と対応が容易になります。インフラストラクチャ設定でSNSトピックを指定すれば、実行結果（AVAILABLEまたはFAILED）を関係者に自動通知できます。EventBridgeにもイメージ状態の変更イベントが発行されます。

代替アプローチの技術的制約について

EventBridgeとLambda/Systems Managerによる実装は、高度なカスタマイゼーションが可能ですが、開発・テスト・運用の工数が大幅に増加します。エラー処理、リトライ、監視、ログ記録等の非機能要件への対応も必要で、総合的な複雑性が高くなります。

Parameter Storeからの動的参照は、起動テンプレート側の機能としては実現可能です。ただしAuto Scalingとの併用には公式に明記された制約があり、SSMパラメータを指定した起動テンプレートを使うAuto Scalingグループでは、希望する設定やスキップマッチングを用いたインスタンスリフレッシュを開始できず、ウォームプールも利用できません。属性ベースのインスタンスタイプ選択を使う混在インスタンスグループの作成・更新にも非対応です。さらにAuto Scalingグループの作成・更新のたびにパラメータが解決されるため、GetParameters呼び出しに応じたSystems Managerの利用料金が発生します。

アーキテクチャ図の解説



Image Builderの配布設定は、AMI作成の完了を起点に起動テンプレートの新バージョン生成まで一手に引き受けます。スケジュールされたパイプラインが定期的にセキュアなAMIを作り（①）、その完了をトリガーに配布設定が動きます（②）。配布設定は最新のAMI IDを反映した起動テンプレートの新バージョンを自動で作り（③）、$Latest参照のAuto Scalingグループが常に最新のテンプレートを使うため、スケールアウト時に最新AMIのインスタンスが起動します（④⑤）。同じことをEventBridgeとLambdaで自前実装すると、イベント検知・書き換え・再試行・監視をすべて自分で持つことになり、運用負荷が増えます。標準機能の配布設定を迂回するほど複雑化するのが落とし穴です。
解くための考え方
「最も効率的」なので、動くだけでなく、実装が短く運用負荷も低い方法を選びます。
EC2 Image Builderは、AMI作成から配布までの完全なライフサイクルを管理するために設計されたサービスです。配布設定は、このライフサイクルの一部として起動テンプレート更新を自動化する標準機能であり、追加の開発や複雑な設定が不要です。
EventBridgeやLambdaによる実装は技術的に可能ですが、Image Builderが提供する標準機能を迂回して独自実装を行うことになります。これは、AWSサービスの設計思想に反し、不必要な複雑性を導入することになります。SSMパラメータを経由する構成も動作しますが、構成箇所が二重になるうえ、Auto Scaling側の機能制約も併せて引き受けることになります。
効率性の観点では、標準機能の活用により開発時間の短縮、バグの削減、メンテナンス負荷の軽減、AWS環境での統合性向上が実現されます。また、AWS側でのサービス改善やセキュリティ更新の恩恵を自動的に受けられるメリットもあります。
実装の考慮事項
Image Builderの配布設定では、起動テンプレートのバージョン管理、Auto Scalingグループの更新ポリシー、既存インスタンスの置換方法を先に決めます。バージョン指定については、検証前のバージョンが即座に本番へ反映される$Latestよりも、setDefaultVersionと組み合わせた$Defaultのほうが変更を制御しやすい場合があります。また、AMI作成失敗時の対応手順、ロールバック戦略、監視・アラート設定も併せて検討する必要があります。本番へ出す前に、テスト環境で検証します。

大手電子部品メーカーは、30 種類を超える製品に搭載する組み込みファームウェアやデバイス向けソフトウェアのビルド・パッケージングを、オンプレミスのカスタム CI/CD パイプラインで行っています。毎週数十件のパッケージが生成され、その依存関係の一部はパブリックリポジトリから取得しています。
同社は、これらのパッケージとパブリックリポジトリ由来の依存関係を、AWS CodeArtifact を使って AWS 内で利用可能にしたいと考えています。
運用負担を最小限に抑えつつこの要件を満たすには、どの手順を実行すべきですか？（2つ選択してください）

選択は不正解です
新しい Amazon S3 バケットを作成し、PutObject を許可する署名付き URL を発行します。オンプレミスの CI/CD パイプラインを、この URL でパッケージを S3 にアップロードするよう変更し、パッケージ追加のたびに起動する AWS Lambda 関数で CodeArtifact へ転送します。

説明
不正解 この方法は不必要に複雑で、運用負担を増やします。S3 を中間ストレージにして Lambda で転送する追加の手順は、CodeArtifact の直接統合を活かしていません。署名付き URL には有効期限があり、定期的な更新が必要になるため運用が煩雑になります。

選択は正解です
パブリックリポジトリごとに外部接続を持つ CodeArtifact リポジトリを用意し、依存関係を取得するメインのリポジトリから、それらをアップストリームとして参照できるよう設定します。

説明
正解 CodeArtifact の外部接続を使うと、npm、PyPI、Maven Central などのパブリックリポジトリから直接パッケージを取得できます。外部接続を設定したリポジトリはパブリックリポジトリのプロキシとして働き、必要なパッケージを自動キャッシュします。1 つのリポジトリに外部接続は 1 つしか設定できないため、公開リポジトリごとにプロキシ用リポジトリを分け、それをメインリポジトリのアップストリームに置く構成が一般的です。

複数の外部接続を持つ CodeArtifact リポジトリを作成し、これらの接続をリポジトリのダウンストリームとして設定します。

説明
不正解 用語の使い方と構成が誤っています。外部接続（パブリックリポジトリへの接続）は CodeArtifact リポジトリのアップストリーム側に設定すべきです。ダウンストリームは、現在のリポジトリからパッケージを取得する側を指します。また、1 つの CodeArtifact リポジトリには 1 つの外部接続しか設定できないという制限もあります。

正しい選択
AWS Identity and Access Management Roles Anywhere のトラストアンカーを設定します。CodeArtifact アクションを許可する IAM ロールを作成してトラストアンカーにリンクし、オンプレミスの CI/CD パイプラインをこのロールを使うよう更新して CodeArtifact へパッケージを公開します。

説明
正解 IAM Roles Anywhere は、オンプレミス環境から AWS サービスへ安全にアクセスするための仕組みです。PKI（公開鍵基盤）でオンプレミスのワークロードを認証し、一時的な AWS 認証情報を取得できます。長期的なアクセスキーを管理する必要がなく、セキュリティが向上し、運用負担も最小限に抑えられます。

新しいパッケージを含む仮想マシンイメージを生成するよう CI/CD パイプラインを変更します。VM Import/Export を使ってこのイメージを Amazon EC2 AMI として取り込み、IAM インスタンスプロファイルを付与して CodeArtifact アクションを許可します。その EC2 インスタンスから AWS CLI で CodeArtifact リポジトリにパッケージをアップロードします。

説明
不正解 手順が過剰で、運用負担を最小限に抑えるという要件から外れます。VM Import/Export は仮想マシンイメージを EC2 の AMI として取り込むためのサービスであり、パッケージを公開するたびにイメージの作成とインポートを繰り返す使い方は想定されていません。インポートには時間がかかるうえ、AMI の世代管理という新たな運用作業も生まれます。オンプレミスの CI/CD から CodeArtifact へ直接公開できる認証手段を用意すれば済むため、EC2 を経由させる必然性がありません。

全体的な説明
問われている要件

オンプレミスのCI/CDパイプラインからAWS CodeArtifactを使用すること

パブリックリポジトリからのソフトウェアパッケージと依存関係をAWS内で利用可能にすること

運用負担を最小限に抑えること

前提知識
AWS CodeArtifactとは
AWS CodeArtifactは、ソフトウェアパッケージを安全に保存、公開、共有するためのフルマネージドのアーティファクトリポジトリサービスです。以下の特徴があります：
複数のパッケージ形式をサポート

npm（JavaScript/Node.js）

PyPI（Python）

Maven/Gradle（Java）

NuGet（.NET）

Swift、Ruby（RubyGems）、Cargo（Rust）

Generic（汎用）

プライベートリポジトリの作成

組織内でのみアクセス可能なプライベートリポジトリを作成できます

IAMポリシーによるきめ細かなアクセス制御が可能です

パブリックリポジトリとの統合

外部接続を通じてパブリックリポジトリと連携できます

一度取得したパッケージは自動的にキャッシュされます

IAM Roles Anywhereの詳細
IAM Roles Anywhereは、AWS外部のワークロード（オンプレミスサーバー、他のクラウドプロバイダーなど）がAWSサービスにアクセスするための認証方法です：
PKIベースの認証

X.509証明書を使用して外部ワークロードを認証します

長期的なアクセスキーの管理が不要になります

トラストアンカーの設定

信頼する証明書発行機関（CA）を登録します

AWS Private Certificate Authority（AWS Private CA）または外部CAを使用できます

一時的な認証情報の取得

証明書を使用して一時的なAWS認証情報を取得します

通常のIAMロールと同様の権限管理が可能です

CodeArtifactの外部接続とアップストリーム/ダウンストリーム
外部接続

パブリックパッケージリポジトリ（npm registry、PyPI、Maven Centralなど）への接続設定です

1つのCodeArtifactリポジトリには1つの外部接続のみ設定可能です

外部接続を持つリポジトリは、パブリックリポジトリのプロキシとして機能します

アップストリームリポジトリ

パッケージの取得元となるリポジトリです

外部接続を持つリポジトリや他のCodeArtifactリポジトリを指定できます

パッケージが見つからない場合、アップストリームから自動的に取得されます

ダウンストリーム

現在のリポジトリからパッケージを取得する側のリポジトリやアプリケーションです

リポジトリチェーンを構築する際に使用されます

リポジトリチェーンの例

[npm公式リポジトリ] ← 外部接続 ← [npm-store（CodeArtifact）] ← アップストリーム ← [firmware-repo（CodeArtifact）]
この構成により：

firmware-repoでパッケージが見つからない場合、npm-storeから取得を試みます

npm-storeでも見つからない場合、外部接続を通じてnpm公式リポジトリから取得します

一度取得したパッケージは各リポジトリにキャッシュされます

アーキテクチャ図の解説



外部接続とアップストリームでは、向きが分かれます。1つのCodeArtifactリポジトリには外部接続を1つしか設定できないため、npmやPyPIなど公開リポジトリごとにプロキシ用リポジトリを用意し、それぞれに外部接続を設定します。オンプレミスのCI/CDパイプラインはメインリポジトリへパッケージを要求し（①）、見つからなければアップストリームのプロキシリポジトリを自動で参照します（②）。プロキシにも無ければ外部接続経由で公開リポジトリから取得してキャッシュします（③）。外部接続を「ダウンストリーム」と取り違えて逆向きに設定すると、公開リポジトリからパッケージを引き込めず、依存関係を解決できないままビルドが失敗してしまいます。



オンプレミスのCI/CDが長期的なアクセスキーを持たずにCodeArtifactへアクセスする仕組みです。あらかじめオンプレミスのCAをIAM Roles Anywhereにトラストアンカーとして登録し、CodeArtifactへの操作を許可するIAMロールをリンクしておきます。CI/CDパイプラインはX.509証明書で認証を要求し（①）、Roles Anywhereが証明書を検証してSTSにAssumeRoleを依頼します（②）。STSから一時認証情報を受け取り（③）、その情報でCodeArtifactへパッケージを公開します（④）。アクセスキーを設定ファイルなどに保存する方式は、鍵の漏えいとローテーションという運用負担を常に抱えます。証明書ベースに切り替えることで負担を解消しつつセキュリティも高められます。
解くための考え方
オンプレミスからの認証と、パブリックリポジトリのプロキシを両方満たす必要があります。
オンプレミスからの安全なアクセス

IAM Roles Anywhereを使用して、オンプレミスCI/CDパイプラインがCodeArtifactにアクセスできるようにします

証明書ベースの認証により、セキュアで管理しやすい接続を確立します

パブリックリポジトリとの効率的な統合

CodeArtifactの外部接続機能を使用して、必要なパブリックリポジトリと連携します

アップストリームリポジトリとして設定することで、自動的にパッケージをプロキシ・キャッシュします

これらの組み合わせにより、運用負担を最小限に抑えながら、要件を満たすことができます。
