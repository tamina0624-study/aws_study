IAM Identity Centerセキュリティモデルについて

統合アクセス管理: Single Sign-On機能により組織全体での統一認証を実現し、個別IAMユーザーの作成を不要にする設計思想。Active Directory、SAML、外部IDプロバイダーとの統合により、中央集権的なアクセス制御とライフサイクル管理を提供

CloudTrailとEventBridge統合機能の特徴

API監査ログ機能: CloudTrailは既定で管理イベント（コントロールプレーンのAPI呼び出し）を記録し、セキュリティ関連イベントの監査証跡を提供。IAM CreateUser、AttachUserPolicy等の権限関連操作を詳細に記録し、不正操作の検知基盤となる

イベント駆動自動化: EventBridgeによるCloudTrailイベントのリアルタイム処理により、セキュリティインシデントの即座検知と自動対応を実現。カスタムイベントパターン設定により、特定のIAM操作のみを対象とした精密な監視が可能

Lambda自動化処理機能について

IAM権限管理自動化: Lambda関数内でIAM APIを呼び出し、ユーザー削除、アクセスキー無効化、ポリシーデタッチ等の権限管理操作を自動実行。DeleteUser、DeleteAccessKey、DeleteLoginProfile等のAPIで認証情報を削除できる

エラーハンドリングと監査: Lambda実行ログによる処理結果の記録、DLQ（Dead Letter Queue）による失敗処理の管理、CloudWatchメトリクスによる実行状況の可視化により、確実な自動化処理を保証

セキュリティ通知アーキテクチャについて

多層通知システム: SNS、EventBridge、CloudWatchアラームを組み合わせた階層的通知により、重要度に応じたエスカレーション処理を実現。即時通知、時間差通知、管理者エスカレーション等の段階的対応をサポート

インシデント対応統合: PagerDuty、Slack、ServiceNow等の外部インシデント管理システムとの連携により、セキュリティイベントを外部のインシデント管理へ渡せる

アーキテクチャ図の解説



IAM Identity Centerの統合管理から外れたIAMユーザーを検知し、無効化と通知まで自動で進めます。作成されるとCreateUser APIがCloudTrailに記録され（①）、EventBridgeルールがイベントを捉えます（②）。EventBridgeはLambdaとSNSへ並行配信し、Lambdaがアクセスキーとログインプロファイルを削除して全認証経路を遮断します（③⑤）。SNSはセキュリティチームへ通知します（④⑥）。起きやすい誤りは、一方だけを無効化して「無効化済み」と判断することです。両者は別経路なので、一方では侵入の余地が残ります。通知をSQSに替える案も成立しません。SQSはポーリング型で、プッシュ配信やメールのサブスクライブ機能を持ちません。
解くための考え方
Identity Centerで統合している環境では、枠外のIAMユーザー作成は即時に止め、チームへ知らせる必要があります。検知は CreateUser、無効化はアクセスキーとログインプロファイルの両方です。
EventBridgeによるCreateUserイベント監視が検知の基盤となります。CloudTrailで記録されるCreateUserイベントをEventBridgeでリアルタイム監視し、不正なユーザー作成を即座に検知する仕組みが必要です。
Lambdaではアクセスキーとログインプロファイルの両方を無効化します。片方だけだと、コンソールかプログラムかの一方が残ります。SNSでセキュリティチームへ同時通知します。
実装の考慮事項
Lambda実行ロールには iam:DeleteAccessKey、iam:UpdateAccessKey、iam:DeleteLoginProfile など無効化に必要な操作だけを付けます。EventBridgeは CreateUser に絞り、許可された作成経路があればパターンから外します。IAM はグローバルサービスで、その API 呼び出しは米国東部（バージニア北部）リージョンの CloudTrail に記録されるため、EventBridge ルールも us-east-1 に作成します。処理結果はログに残し、Lambda失敗は DLQ へ送ります。

CI/CDパイプライン設計の基本原則について

AppSpecファイルはデプロイプロセスの各段階で実行するスクリプトやファイル配置を定義し、アプリケーション固有の処理を自動化できます

前提知識
CodePipelineクロスアカウントデプロイ機能について

クロスアカウントアーキテクチャ CodePipelineは単一のアーティファクトストアから複数の対象アカウントにデプロイを実行可能。各対象アカウントでCloudFormation実行用のIAMロールを作成し、そのロールの信頼ポリシーでパイプラインアカウントのCodePipelineサービスロールからのsts:AssumeRoleを許可したうえで、CodePipelineアクションからこのロールを引き受けることで、セキュアなクロスアカウント操作を実現

アーティファクトアクセス制御 S3バケットポリシーとKMSキーポリシーの両方でクロスアカウントアクセス権限を明示的に許可する必要があり、IAMロールの権限設定だけでは不十分。リソースベースポリシーによる明示的な許可が必須

KMS暗号化とクロスアカウントアクセスの特徴

カスタマーマネージドキー ユーザーが完全に制御できるKMSキーで、キーポリシーのカスタマイズにより特定のプリンシパルに対する暗号化・復号権限の細かい制御が可能。クロスアカウント環境では、対象アカウントのIAMロールに対してkms:Decrypt権限を付与

AWSマネージドキー AWSが自動作成・管理するキーで、キーポリシーの変更はできない。S3暗号化用のalias/aws/s3等が代表例で、基本的には同一アカウント内でのアクセスのみをサポート

CloudFormation実行権限とアクセス制御について

CloudFormation サービスロール CloudFormationスタックの作成・更新・削除を実行するためのIAMロールで、必要なAWSサービスへの権限を付与。クロスアカウントデプロイでは、対象アカウントで作成したロールをCodePipelineアクションで指定

アーティファクトアクセス権限 CloudFormationテンプレートやLambdaデプロイメントパッケージ等のアーティファクトにアクセスするため、s3:GetObject、s3:GetObjectVersion権限に加え、KMS復号権限も必要

S3バケットポリシーとクロスアカウント制御の特徴

リソースベースポリシー S3バケットに直接アタッチされるポリシーで、他アカウントのプリンシパルに対するアクセス許可を明示的に定義。IAMポリシーと組み合わせて、クロスアカウントアクセスの完全な権限チェーンを構成

プリンシパル指定 対象アカウントのIAMロールARNを Principal フィールドで指定し、必要なS3アクション（s3:GetObject、s3:GetObjectVersion等）を許可。条件ブロックによる追加のセキュリティ制約も設定可能

アーキテクチャ図の解説



クロスアカウントのCodePipelineでは、ビルドアカウントの成果物を開発・本番アカウントへ届けます。ビルドアカウントでLambdaパッケージをビルドし、カスタマーマネージドKMSキーで暗号化してS3へ保存します（①②）。デプロイ時、開発・本番のCloudFormation実行ロールがS3から成果物を取得し（⑤⑩）、KMSで復号して（⑥⑪）Lambdaをデプロイします。アクセス拒否になるのは、IAMロールの権限だけでなくS3バケットポリシーとKMSキーポリシーというリソース側の許可が不足している場合です。クロスアカウントでは両方の明示的な許可が必要で、片方だけでは解消されません。AWSマネージドキーはポリシーを変更できないため、カスタマーマネージドキーが必須です。
解くための考え方
アクセス拒否の原因は、KMS復号とS3取得の2層で、アイデンティティ側とリソース側の許可が揃っていないことです。
第一に、KMS暗号化レイヤーでの権限不備があります。アーティファクトがKMSで暗号化されている場合、CloudFormation実行ロールがアーティファクトを復号するためにはKMSキーポリシーでの明示的な権限付与が必要です。AWSマネージドキーではポリシーカスタマイズができないため、カスタマーマネージドキーを作成し、開発・本番アカウントのCloudFormation実行ロールに対してkms:Decrypt権限を付与する必要があります。
第二に、S3アクセスレイヤーでの権限不備があります。クロスアカウント環境では、IAMロールにs3:GetObject権限があっても、S3バケットポリシーで明示的にクロスアカウントアクセスを許可しなければアクセスは拒否されます。CodePipelineアカウントのS3バケットポリシーを更新し、開発・本番アカウントのCloudFormation実行ロールからのアクセスを許可する必要があります。
クロスアカウントでは、IAMロール（アイデンティティ）とS3バケットポリシー・KMSキーポリシー（リソース）の両方で許可が必要です。片方だけでは拒否されます。
実装の考慮事項
KMSキーポリシーとS3バケットポリシーは、開発・本番のCloudFormation実行ロールだけを許可する最小権限にします。付与するアクションは、S3側がs3:GetObject、s3:GetObjectVersion、s3:ListBucketなど、KMS側がkms:Decrypt、kms:DescribeKey、kms:GenerateDataKey*などが目安です。パイプラインのテスト段階で復号とGetObjectが通るかを確認し、失敗時はCloudWatchログで拒否理由を追います。

前提知識
CI/CDパイプライン・ワークフロー管理の特徴

AWS CodePipelineは、ソースからデプロイまでの完全なCI/CDワークフローを管理するサービスで、複数のステージ・アクションの構成と並列実行をサポートします。 手動承認アクションを任意のステージに挿入でき、承認者への通知、承認期限、条件付き実行を設定できます。 CodeCommit、GitHub、S3等の多様なソースと、CodeBuild、CodeDeploy、CloudFormation等のアクションを統合し、複雑なリリースプロセスの自動化に対応します。 手動承認を挟むマルチステージのリリース管理に使います。

AWS CodeBuildは、ソースコードのコンパイル、テスト、パッケージング等のビルドプロセスを実行するフルマネージドサービスで、最大8時間の連続実行をサポートします。 カスタムDockerイメージによる多様な言語・フレームワーク対応、並列ビルド実行、成果物のS3自動アップロード機能を提供します。 既に設定済みという前提により、ソースコード変更の自動検出とアーティファクト生成が可能で、後続のデプロイステージに必要な成果物を準備します。

デプロイメント自動化・管理の特徴

AWS CodeDeployは、EC2、Lambda、ECS等への自動デプロイメントを管理するサービスで、ローリング、ブルーグリーン、カナリアなどのデプロイ戦略をサポートします。 アプリケーション単位での論理的管理、デプロイメントグループによる対象インスタンス指定、自動ロールバック機能を提供します。 EC2インスタンス上のCodeDeployエージェントは、デプロイ指示の受信、アーティファクトダウンロード、アプリケーション停止・起動・検証を自動実行します。

CodeDeployエージェントは、EC2インスタンス上で動作する軽量サービスで、CodeDeployサービスとの通信、デプロイ指示の受信、ローカル実行を担当します。 Ruby実装により全Linux・Windows環境で動作し、IAM権限によるセキュアな通信、ログ出力による詳細な実行トレースを提供します。 アプリケーション固有のデプロイスクリプト実行、ヘルスチェック、検証プロセス等のカスタムロジックにも対応し、エージェントなしではCodeDeployの機能を利用できません。

インフラストラクチャ・リソース管理の特徴

AWS CloudFormationは、JSONまたはYAML形式でAWSリソースを宣言的に定義・管理するインフラストラクチャ・アズ・コードサービスです。 スタック単位でのリソース管理、依存関係の自動解決、ロールバック機能による安全な変更管理を提供し、最大500リソースまでの単一スタック作成が可能です。 バージョン管理システムとの統合により、インフラ変更履歴の追跡とコードレビューによる品質保証を実現します。 スタック単位の定義、依存関係の解決、ロールバックによる変更管理ができます。

CloudFormation変更セットは、スタック更新前に変更内容をプレビューする機能で、リソースの追加・変更・削除を詳細表示し、影響範囲を事前確認できます。 変更セット作成後に実際のリソース更新は発生せず、承認後の変更セット実行により初めてスタックが更新される安全な仕組みを提供します。 手動承認フローとの統合により、インフラ変更のガバナンス強化と意図しない変更の防止を実現します。

アーキテクチャ図の解説



CodePipelineがビルドからデプロイまでを一続きに自動化し、インフラ更新の直前に手動承認を挟みます。CodeCommitへの変更を検知するとCodeBuildがビルド・テストを実行し、その後に変更セットを作成します。変更セットはあくまで変更内容のプレビューであり、この段階ではリソースは更新されません。承認者が内容を確認して承認した後に初めて変更セットが実行され、インフラが更新されます。その完了を待ってCodeDeployが新バージョンをEC2へ展開します。落とし穴は、変更セットを作っただけで実行を忘れるとインフラが古いままアプリだけ更新されて失敗することと、EC2側にCodeDeployエージェントが無いと展開処理そのものが動かないことです。
解くための考え方
手元のビルド成果物アップロードとスタック更新をやめ、CodeCommit → CodeBuild → 変更セット → 手動承認 → 変更セット実行 → CodeDeploy の順に載せます。承認の前に変更内容をプレビューできない直接更新は使いません。
まず、デプロイメント自動化の基盤として、CodeDeployの適切な設定が必要です。アプリケーションとデプロイメントグループの作成により、論理的な管理単位と物理的なデプロイ対象を定義します。EC2インスタンス上のCodeDeployエージェントは、デプロイサービスとインスタンス間の通信を仲介し、実際のアプリケーション更新を自動実行するため、エージェントのインストールは必須条件となります。
次に、CI/CDパイプラインの設計では、CloudFormation変更セットの活用が重要です。直接的なスタック更新では変更内容の事前確認ができないため、予期しないリソース変更や削除のリスクがあります。変更セット作成により、インフラ変更の詳細を事前にプレビューでき、手動承認ステップで関係者が変更内容を十分に検証できます。
完全なワークフローでは、CodeCommitでの変更検出、CodeBuildによる自動ビルド、CloudFormation変更セット作成、手動承認待機、変更セット実行、CodeDeploy開始という順序で進行します。各ステップが適切に連携することで、自動化による効率向上と人的制御による安全性確保を両立できます。
変更セットを作っただけで実行しないと、インフラが古いままアプリだけ更新されて失敗します。EC2 に CodeDeploy エージェントが無いと、グループを定義しても展開処理は動きません。
実装の考慮事項
承認アクションには承認者と期限を付け、変更セットの追加・置換・削除を読んでから実行します。CodeDeployエージェントは更新し、失敗時はロールバックと通知を付けます。なお、AWS CodeCommitは2024年7月にいったん新規顧客の受付を停止しましたが、2025年11月に一般提供へ復帰し、現在は新規のAWSアカウントでもリポジトリを作成できます。CodePipelineはCodeCommitに加えGitHub等の外部リポジトリもソースとして扱えるため、既存の構成に合わせて選択します。

前提知識
S3でのデータ完全性検証メカニズムについて

Content-MD5ヘッダーは、RFC 1864で定義されたHTTP標準であり、S3がネイティブにサポートするデータ完全性検証方法です

S3は受信したデータのMD5を計算し、Content-MD5ヘッダーの値と比較して、不一致の場合は400 Bad Requestエラーを返します

この検証は転送中のデータ破損、ネットワーク障害、中間プロキシでの変更などを確実に検出できます

マルチパートアップロードの場合、Content-MD5 による照合はパート単位にとどまり、オブジェクト全体のMD5をS3が検証するわけではありません。全体の整合性まで確認したい場合は、パートごとにチェックサムを付けてCompleteMultipartUpload時に合成チェックサムを検証する追加チェックサム方式を使います

なお、S3は2022年のアップデートでSHA-1、SHA-256、CRC32、CRC32Cによる追加チェックサム検証に対応し、2025年にはCRC64NVMEの追加と既定のデータ整合性保護（AWS SDKがアップロード時にCRCベースのチェックサムを自動計算する仕組み）が導入されました。Content-MD5 は単一パートのアップロード向けのレガシーな方式として引き続き利用でき、この問題ではMD5チェックサムによる検証が要件として指定されています

ETagとMD5チェックサムの関係について

シンプルアップロード（5GB未満）では、ETagは通常オブジェクトのMD5チェックサムと一致します

マルチパートアップロードでは、ETagは各パートのMD5を組み合わせた値になり、単純なファイル全体のMD5とは異なります

ETagの形式（ハイフンの有無）により、アップロード方式を判別でき、適切な検証方法を選択できます

非暗号化またはSSE-S3で暗号化されたオブジェクトではETagはオブジェクトデータのMD5になりますが、SSE-KMSまたはSSE-Cで暗号化されたオブジェクトではETagはオブジェクトデータのMD5ではなくなるため、元ファイルのMD5との直接比較は適用されません

データ移行における完全性検証のベストプラクティスについて

二重検証（Content-MD5 + ETag比較）により、アップロード時とアップロード後の両方で完全性を確認できます

バッチ処理では、検証失敗時に自動リトライし、最大試行回数を決めます

大容量ファイルでは、マルチパートアップロードとContent-MD5の組み合わせにより、効率的かつ確実な転送を実現できます

CloudWatch Logsでの検証結果記録により、移行プロセスの監査証跡と問題診断を支援できます

アーキテクチャ図の解説



転送時の自動検証と転送後の事後確認を二段構えで行います。スクリプトはオンプレミスのサーバーから2か月以上前の検査データを読み出してMD5チェックサムを計算し、Content-MD5 ヘッダー付きでS3へ送信します。S3は受信データのMD5を再計算して照合し、不一致なら400 Bad Requestを返すため、転送中の破損をその場で検出できます（①〜③）。成功時はレスポンスのETagと事前計算したMD5を比較し、一致した場合にだけ元ファイルを削除します（④）。ETagを確認せずに削除してしまうと、アップロード自体は成功していても保存後のデータが別物にすり替わるリスクを検知できません。削除は検証の後段に置き、検査記録の消失を防ぎます。
解くための考え方
転送中の破損は Content-MD5 でS3側が拒否します。保存後のすり替わりは、レスポンスのETagと事前計算MD5を比べてから元ファイルを消すと防げます。どちらか一方だと、転送成功後の不一致や、ヘッダーなしの破損を見逃します。
マルチパートでは各パートのMD5と完了後の合成ETagの扱いが単一PUTと違うので、単一オブジェクトのETag比較と同じ手順にはしません。
実装の考慮事項
不一致なら削除せずリトライし、失敗はログに残します。大容量はマルチパートにし、パートごとにチェックサムを付けます。

KMS キーのローテーション間隔を AWS Config のカスタムルールで定期評価し、非準拠を SNS で通知します。Config が定期的に Lambda の評価関数を起動し（①）、Lambda が ListKeys・DescribeKey・ListKeyRotations でキーの作成日とローテーション履歴を取得して（②③）90 日経過を判定します。非準拠の結果を Config へ報告し（④）、Config が SNS へ通知して（⑤）セキュリティチームにメールで届きます（⑥）。KMS 単体にはローテーション間隔を監視して通知する機能がなく、Trusted Advisor や Security Hub にも手動ローテーションの経過日数を評価する機能はないため、カスタムロジックを置ける Config が要件を満たす手段になります。自動ローテーションを利用できるキーなら 90 日周期の自動化も可能ですが、手動ローテーションを前提とする場合はこの監視が有効です。
解くための考え方
KMS 自体にも Trusted Advisor にも Security Hub にも、手動ローテーションの経過日数を測って通知する機能はありません。経過日数の判定ロジックを置けるサービスを選ぶ必要があります。
AWS KMSはキー管理とアクセス制御に特化したサービスで、監視・アラート機能は提供していません。Trusted AdvisorやSecurity Hubも一般的なセキュリティチェックは提供しますが、KMS固有の詳細監視は対象外です。
AWS Configのカスタムルールは Lambda で評価ロジックを書けるため、ListKeys・DescribeKey・ListKeyRotations でキーの作成日とローテーション履歴を取り、90日経過を判定できます。なお、DescribeKeyが返すのは作成日などのキー属性で、最終ローテーション日そのものは返さないため、ローテーション履歴はListKeyRotationsやCloudTrailの記録から取得します。
具体的な実装では、Lambda関数でKMS APIを呼び出してキー情報を取得し、作成日または直近のローテーション日から90日経過を判定します。この評価ロジックをConfigカスタムルールとして実装し、定期実行することで継続的な監視を実現できます。
非準拠検出時には、ConfigからSNSへの通知により、セキュリティチームへの即座のアラートが可能です。このアプローチにより、手動プロセスの自動監視と確実な通知を両立できます。
なお、2024年4月のアップデートにより、カスタマーマネージドキーの自動ローテーション期間を90〜2560日で指定できるようになり、オンデマンドローテーションも可能になりました。自動ローテーションを利用できるキーであれば90日周期の自動化も選択肢になりますが、この問題のように手動ローテーションを前提とする場合（インポートしたキーマテリアルを使用するキーなど）は、Configカスタムルールによる監視が引き続き有効なアプローチです。
実装の考慮事項
評価用 Lambda には kms:ListKeys、kms:DescribeKey、kms:ListKeyRotations、kms:GetKeyRotationStatus といった参照系の権限だけを付けます。評価頻度と対象キーの範囲を決め、自動ローテーション済みのキーを誤って非準拠にしない条件を入れます。通知文にはキーIDと経過日数を含めます。

前提知識
AWS Organizations・マルチアカウント管理の特徴

AWS Organizationsは、複数のAWSアカウントを階層的に管理する組織管理サービスです（管理可能なアカウント数のクォータはService Quotasで確認・引き上げが可能）。 管理アカウント（旧マスターアカウント）による一元的な課金管理、Service Control Policies（SCP）による組織レベルのセキュリティ制御を提供します。 各メンバーアカウントは独立したセキュリティ境界を維持し、クロスアカウントアクセスには明示的なIAM設定が必要です。 部門別アカウントの課金集約と、SCPによる権限の上限設定に使います。

IAM・クロスアカウントアクセス管理の特徴

IAMロールは、一時的なセキュリティ認証情報を提供するAWSプリンシパルで、最大12時間のセッション持続時間をサポートします。 信頼ポリシー（Trust Policy）により引き受け可能なプリンシパルを定義し、権限ポリシーにより付与する具体的権限を指定します。 AssumeRoleによる一時認証情報取得、ロールチェーン、外部IDプロバイダ統合ができます。 クロスアカウントアクセスやサービス間連携で使います。

AWS Security Token Service（STS）は、一時的なセキュリティ認証情報を発行するサービスで、15分から12時間の有効期間を設定可能です。 AssumeRole、GetSessionToken、AssumeRoleWithWebIdentity等のAPIを通じて、異なる信頼レベルの認証情報を提供します。 一時認証情報による最小権限アクセス、認証情報の自動ローテーション、監査ログの詳細記録を実現します。

EC2・ネットワークセキュリティ管理の特徴

Amazon EC2セキュリティグループは、仮想ファイアウォール機能を提供するネットワークセキュリティ制御で、ステートフル接続追跡による双方向通信管理をサポートします。 デフォルトクォータでは各セキュリティグループに最大60のインバウンドルールと60のアウトバウンドルールを設定でき（上限緩和申請で引き上げ可能）、IPアドレス、CIDR、他のセキュリティグループを参照可能です。 デフォルトでインバウンドトラフィックを拒否し、アウトバウンドトラフィックを許可するホワイトリスト方式を採用します。

AmazonEC2ReadOnlyAccessマネージドポリシーは、EC2関連リソースの読み取り専用アクセス権限を提供するAWS管理ポリシーです。 ec2:Describe* と ec2:GetSecurityGroupsForVpc という参照系の権限を含み、インスタンス、セキュリティグループ、VPC等の設定情報取得を可能にします。 書き込み権限は一切含まれないため、監査・レポート用途での安全な権限付与に適しており、セキュリティグループルール分析での必須権限を提供します。

Lambda・サーバーレス実行環境の特徴

AWS Lambdaは、イベント駆動でコードを実行するサーバーレスコンピューティングサービスで、最大15分の実行時間と10GBのメモリをサポートします。 実行ロール（Execution Role）により必要なAWS権限を取得し、環境変数、レイヤー機能による外部ライブラリ管理を提供します。 boto3 SDKを使用したAWS API呼び出し、STS AssumeRoleによるクロスアカウントアクセス、並列実行による大規模処理が可能です。 定期的な監査処理、レポート生成、コンプライアンスチェックの自動化に使います。

アーキテクチャ図の解説



管理アカウントのLambda関数が、STS AssumeRoleで各メンバーアカウントのロールを引き受け、EC2セキュリティグループ情報を集めます。LambdaがIAM実行ロールを使い、STSのAssumeRole APIで各メンバーアカウントのロールを引き受けます。引き受ける先のロールにはAmazonEC2ReadOnlyAccessポリシーが付与され、DescribeSecurityGroupsでルール情報を読み取って管理アカウントへ返します。ここで重要なのは、メンバーアカウント側のロールが「管理アカウントを信頼する」信頼ポリシーを持っていることです。この信頼関係の方向を逆にしたり、管理アカウントに読み取り権限を付けるだけでは、アカウント境界を越えられず情報を取得できません。
解くための考え方
管理アカウントのLambdaからメンバーのセキュリティグループを読むには、向きの決まった AssumeRole が必要です。メンバー側ロールは管理アカウントを信頼し、AmazonEC2ReadOnlyAccess を持ちます。管理側の実行ロールは、それらロール ARN への sts:AssumeRole を許可します。
まず、各メンバーアカウントでの設定として、EC2セキュリティグループ情報を読み取るためのIAMロール作成とAmazonEC2ReadOnlyAccessポリシーの付与が必要です。このロールには、ec2:DescribeSecurityGroups、ec2:DescribeSecurityGroupRules等の権限が含まれ、実際のデータ取得を可能にします。
次に、クロスアカウントアクセスの実現には、メンバーアカウント側でのトラストポリシー設定が重要です。作成したIAMロールの信頼ポリシーで、管理アカウントの特定プリンシパル（Lambda実行ロールまたは管理アカウント全体）がこのロールを引き受けることを許可する設定を行います。これにより、管理アカウントからメンバーアカウントリソースへのアクセス経路が確立されます。
最後に、管理アカウント側では、Lambda実行ロールにsts:AssumeRoleアクションを許可し、対象となる全メンバーアカウントのIAMロールARNを指定します。Lambda関数内では、boto3のSTSクライアントを使用してAssumeRole APIを呼び出し、各メンバーアカウントの一時認証情報を取得後、EC2クライアントでセキュリティグループ情報を取得する実装が必要です。
信頼関係の方向性を間違えると、メンバーアカウントが管理アカウントにアクセスする逆方向の設定になり、要件を満たせません。また、管理アカウント内でのEC2権限付与だけでは、アカウント境界を越えられないため、クロスアカウントアクセス機能が動作しません。
実装の考慮事項
Lambda関数での実装では、大量のメンバーアカウントに対する並列処理とタイムアウト制御が重要です。各アカウントでのAssumeRole処理と情報取得を効率的に行うため、concurrent.futures等による並行処理と、適切なエラーハンドリング、リトライロジックの実装が必要です。取得結果の保存先（S3、DynamoDB等）への書き込み権限と、週次実行の EventBridge スケジュールを付けます。
