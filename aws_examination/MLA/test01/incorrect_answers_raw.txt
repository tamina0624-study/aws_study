不正解 FSx for Windows File Server は Windows ワークロード向けのフルマネージドファイルサーバーで、ネットワーク経由のアクセスには SMB プロトコルをネイティブに使用します。NFS プロトコルには対応しておらず、既存の NFS クライアントや NFSv4 のアドバイザリファイルロックをそのまま使うことはできません。SMB クライアント経由でアクセスできても、NFS 互換性とファイルロックが要件の本問には合致しません。

前提知識
Amazon EFSについて

Amazon EFSはNFSv4.0およびNFSv4.1プロトコルをサポートするフルマネージド型ファイルシステムです

NFSv4のアドバイザリファイルロック（バイトレンジロックを含む）をサポートし、1ファイルあたり最大512個のロックを扱えます

AWS Direct ConnectまたはVPN接続により、オンプレミスのLinuxクライアントからマウントできます

SageMaker AIノートブックインスタンスやSageMaker Studioから直接マウントできます

ストレージ容量はペタバイト規模まで自動スケーリングします

Amazon S3とMountpoint for Amazon S3について

Amazon S3はオブジェクトストレージであり、ファイルロックやディレクトリ操作などのファイルシステムのセマンティクスをネイティブに提供しません

Mountpoint for Amazon S3はS3をファイルシステムとしてマウントするツールですが、ファイルロック機能は提供しません

POSIXファイルシステムの完全な互換性は持ちません

Amazon FSx for Windows File Serverについて

Windowsワークロード向けのフルマネージドファイルサーバーで、SMBプロトコルをネイティブにサポートします

Microsoft Active Directoryと連携した認証やWindows ACLによるアクセス制御を提供します

NFSプロトコルには対応しておらず、NFSv4のアドバイザリファイルロックも提供しません

Windows中心の環境には適しますが、LinuxのNFSクライアントを前提とする本要件には合いません

Amazon EBSについて

単一のEC2インスタンスへアタッチして使用する設計のブロックストレージサービスです

マルチアタッチは同一AZ内のio1/io2ボリュームに限られ、オンプレミスからのアクセスはできません

ファイルシステムはインスタンス上で構成するものであり、共有ファイルシステムとしての機能は提供しません

図による解説



オンプレミスとAWS側は同じファイルシステムへ、Direct ConnectまたはVPNのプライベート接続でアクセスします。ユーザーが作業するオンプレミスのLinuxサーバーはNFSクライアントとして動作し、ファイルロック要件を抱えています。通信はプライベート接続を通ってAWS側のAmazon EFSへ届き、同じファイルシステムをSageMaker AIノートブックも直接マウントします。EFSがNFSv4をネイティブにサポートするため、既存のNFSワークフローを変更せずにハイブリッド共有ストレージを実現できます。オンプレミスとAWS側で別々のストレージを用意すると、ファイルロックが機能せず同時書き込みの競合が起きます。



要件（NFS互換・ハイブリッドアクセス・ファイルロック）に対する4つのストレージの合致度は異なります。Amazon EFSだけがNFSv4プロトコルとファイルロックの両方を備え、要件をすべて満たします。Amazon S3はオブジェクトストレージでNFSをネイティブに提供せず、Mountpointでマウントしてもファイルロック機能はありません。FSx for Windows File ServerはSMBプロトコルを使うため、NFSクライアントからはNFSとして直接マウントできません。Amazon EBSは単一インスタンス向けのブロックストレージで、複数システムからの共有アクセス自体ができません。NFSとファイルロックの両方を欠く候補を選ぶと、ユーザーのロック要件を満たせません。
解くための考え方
NFSプロトコル互換性、ハイブリッドアクセス（オンプレミス＋クラウド）、ファイルロックの3つを同時に満たす必要があります。
Amazon EFSはNFSv4プロトコルをネイティブにサポートするため、既存のNFSベースのワークフローをそのまま移行できます。さらに、Direct ConnectまたはVPN経由でオンプレミスサーバーからマウントでき、SageMaker AIノートブックからも直接マウントできるため、ハイブリッドアクセスの要件を満たします。ファイルロックについても、EFSはNFSv4のアドバイザリファイルロックをサポートするため、ユーザーのロック要件に対応できます。
一方、Amazon S3はオブジェクトストレージでファイルロックを提供しません。FSx for Windows File ServerはSMBプロトコルを採用しておりNFSではありません。EBSは単一インスタンス向けのブロックストレージで、共有アクセスやオンプレミスからの利用はできません。
したがって、NFS互換とファイルロックをハイブリッドでそろえるのは Amazon EFS だけです。

前提知識
Amazon Macieについて
Amazon Macieは、機械学習とパターンマッチングを使ってS3内の機密データを自動的に識別・分類・保護するマネージドサービスです。個人を特定できる情報（PII）、クレジットカード番号、AWS認証情報（アクセスキー等）などを自動検出し、S3バケットを継続的に監視して機密データの検出結果を通知します。データの内容を分析して検出するため、手動でパターンを定義する必要がなく、運用オーバーヘッドを最小限に抑えられます。マネージドデータ識別子でカバーされない契約番号のような独自の項目は、正規表現で記述するカスタムデータ識別子として定義すれば検出対象に加えられます。検出結果はAmazon EventBridgeへ自動的に発行されるため、後続の処理をイベント駆動で起動できます。AWS Organizationsと統合されており、複数アカウントにまたがる監視も可能です。
Amazon GuardDutyについて
Amazon GuardDutyは、AWS環境内のデータソースとログを継続的に監視し、悪意のあるIPアドレスやマルウェア、認証情報の漏洩といった脅威を検出するサービスです。S3 Protectionはバケット内のデータが不正に引き出される動きなどを識別しますが、契約番号や支払い情報といった機密データの内容そのものを分類・特定する機能は持っていません。S3内の機密データを識別するには、データの内容を分析するAmazon Macieが適切です。
AWS Lambdaについて
AWS Lambdaは、サーバーレスでコードを実行するコンピューティングサービスです。イベントに応じて自動実行され、スケーリングやインフラ管理が不要です。Macieが検出した機密データの情報を基に、自動削除処理を実装できます。Macieの検出結果をイベントとして受け取り、機密データの削除を自動化できます。
機密データの識別と削除の自動化について
機密データの識別と削除を自動化するには、自動検出できるサービスと、検出されたデータを削除する処理を組み合わせます。Amazon Macieが機密データを自動検出し、Lambda関数が検出結果を基に削除処理を自動化します。この組み合わせにより、最小限の運用オーバーヘッドで機密データの識別と削除を実現できます。
図による解説



機密データの検出と削除という2つの処理を、専用サービスで分担させます。オンプレミスのMLモデルはS3の顧客データを参照してパーソナライズされたアドバイスを提供しており、そのバケットには契約番号や支払い情報といった機密データが混在しています。Amazon MacieはS3バケットを継続的に監視し、機械学習とパターンマッチングで機密データを自動検出したうえで、検出結果をイベントとしてLambdaへ渡します。Lambdaはそのイベントを受けて該当オブジェクトを削除するため、手動でパターンを定義しなくても検出から削除までが自動化されます。検出の役割を脅威検出のGuardDutyや自前のスクリプトに置き換えると、S3内のオブジェクトの内容から機密データを特定することはできず、人手の運用負荷も残ります。
解くための考え方
この設問は、機密データを見つける工程と、見つけたデータを消す工程の2つに分解すると整理できます。要件で強調されているのは運用の手間を抑えることなので、それぞれの工程をどこまでマネージドサービスに任せられるかが判断の軸になります。
識別の工程を担えるのはAmazon Macieです。Macieは機械学習とパターンマッチングでS3オブジェクトの中身を走査し、個人を特定できる情報やクレジットカード番号、AWS認証情報といったマネージドデータ識別子の対象を自動で検出します。契約番号のような業務固有の項目も、正規表現で書いたカスタムデータ識別子を登録すれば検出できるため、検出ロジックを自前で作り込み続ける必要がありません。これを自作のスクリプトやLambda関数だけで代替しようとすると、検出パターンの定義とスキャン処理の実装・保守が丸ごと残り、運用オーバーヘッドという要件から外れます。
識別を別のサービスに置き換えられないかも確認します。Amazon GuardDutyは脅威検出のサービスで、S3 Protectionもバケットに対する不審なアクセスやデータ持ち出しの兆候を捉えるものであり、オブジェクトの中身を分類して機密データかどうかを判定する機能は持ちません。Amazon Rekognitionは画像・動画を対象としたコンピュータビジョンのサービスで、S3に置かれた構造化・非構造化のテキストデータから契約番号や支払い情報を洗い出す用途には使えません。
削除の工程は、Macieの検出結果をEventBridge経由で受け取るAWS Lambda関数で自動化できます。サーバーレスなのでインスタンスの起動やパッチ適用が不要で、検出から削除までがイベント駆動でつながります。削除処理をEC2インスタンスで動かす構成は、同じ結果を得るためにOS管理とスケーリングの負担を新たに抱えることになります。
したがって、機密データの識別はMacie、削除はLambda関数に任せると、運用の手間は小さく済みます。

データの準備と前処理に特化したビジュアルツールです

データのインポート、変換、分析、エクスポートを 1 つのインターフェイスで実行できます

データ品質とインサイトレポートを自動生成し、欠損値、重複行、データ型の問題を検出します

300 以上の組み込み変換機能を提供し、重複の削除、欠損値の補完、特徴量エンジニアリングなどを行えます

外れ値、クラスの不均衡、データリークなどの異常も検出できます

SageMaker Clarify について

バイアス検出とモデルの説明可能性に特化したサービスです

トレーニング前バイアス（Pre-training Bias）とトレーニング後バイアス（Post-training Bias）の両方を検出できます

クラスの不均衡（CI）、ラベルの比率の差（DPL）など複数のバイアスメトリクスを提供します

SHAP 値を用いた特徴量の重要度分析や部分依存プロットによるモデル説明機能も備えます

本番環境でのバイアスドリフトの監視にも対応します

SageMaker Model Monitor について

デプロイ済みモデルのエンドポイントを継続的に監視するサービスです

データ品質監視、モデル品質監視、バイアスドリフト監視、特徴量属性ドリフト監視の 4 種類を提供します

本番環境で入力データの分布変化（データドリフト）やモデル精度の劣化を検出します

トレーニング前のデータ準備には使用しません

Amazon CloudWatch について

メトリクスの収集・可視化、ログの保存、アラームの発報を担う監視サービスです

インフラやアプリケーションの稼働指標は監視できますが、重複・欠損値の処理といったデータ品質ルールは提供しません

データの準備・前処理とは役割が異なります

図による解説



データ準備は品質向上とバイアス検出の2段階に分かれ、それぞれに専用のサービスを割り当てます。会員データはまず SageMaker Data Wrangler に取り込まれ、重複削除や欠損値処理を経て品質レポートが生成され、クリーンなデータになります。続いて SageMaker Clarify が統計的バイアスを評価し、CI・DPL などの公平性メトリクスをまとめ、検証済みデータが SageMaker AI のトレーニングへ渡ります。この順序を誤って Model Monitor を前段に置くと、デプロイ後の監視しか担わないため、トレーニング前の重複・欠損値処理ができません。CloudWatch もメトリクス監視が専任で、品質と公平性の両立には Data Wrangler と Clarify の組み合わせが必須です。
解くための考え方
この問題は、データ準備の工程を「品質の改善」と「バイアスの検出」という 2 つの作業に分解し、それぞれに適したサービスを割り当てられるかを問うています。いずれもモデルをトレーニングする前の段階で行う作業である点が、絞り込みの起点になります。
重複と欠損を処理してデータ品質を上げるには、データ準備に特化した SageMaker Data Wrangler が必要です。Data Wrangler はデータ品質とインサイトのレポートを自動生成して重複行・欠損値・データ型の不整合を洗い出し、300 以上の組み込み変換によって重複の削除や欠損値の補完をそのまま適用できます。ML トレーニングに初めて使うデータでは、まずこのレポートで問題の所在を把握してから変換を組み立てる流れが自然です。
統計的バイアスの検出については、SageMaker Clarify がトレーニング前のデータにおけるバイアスを検出する機能を備えています。クラスの不均衡（CI）やラベルの比率の差（DPL）といった複数のメトリクスにより、年齢や性別のような属性への偏りを定量的に評価できます。
残る 2 つはいずれも監視を担うサービスである点が共通しています。SageMaker Model Monitor はデプロイ済みのエンドポイントを対象とする監視機能で、トレーニング前のデータ準備には使えません。Amazon CloudWatch はメトリクスの収集とアラーム発報を担う監視サービスであり、重複や欠損の処理といったデータ加工そのものは扱えません。
したがって、重複・欠損の処理には Data Wrangler、バイアス検出には Clarify を組み合わせる構成が要件を満たします。

前提知識
temperatureパラメータについて
temperatureパラメータは、LLMの出力のランダム性を制御する値です。値が高いほど出力のランダム性が増して創造性は上がりますが、一貫性は下がります。値が低いほどランダム性が下がって一貫性が上がりますが、創造性は下がります。Amazon BedrockのAnthropic Claude Messages APIでは0〜1の範囲で設定でき、デフォルトは1です。0に近いほど決定的な出力に近づき、1に近いほどランダムな出力に近づきます。一貫性を重視する場合は低い値を設定します。
top_kパラメータについて
top_kパラメータは、次のトークンを選ぶ際に考慮する候補トークンの数を制御する値です。値が高いほど多くの候補が考慮されてランダム性が増し、値が低いほど少数の候補に絞られてランダム性が下がります。Amazon BedrockのAnthropic Claude Messages APIでは0〜500の範囲で設定でき、デフォルトでは無効になっています。Converse APIから使う場合、top_kは全モデル共通のinferenceConfigではなくadditionalModelRequestFieldsで指定します。一貫性を重視する場合は小さい値を設定します。
top_pパラメータについて
top_pパラメータは核サンプリングとも呼ばれ、累積確率が指定値に達するまでのトークンを候補として考慮する値です。値が高いほど候補が増えてランダム性が増し、値が低いほど候補が減ってランダム性が下がります。Amazon BedrockのAnthropic Claude Messages APIでは0〜1の範囲で設定でき、デフォルトは0.999です。
LLMの出力の一貫性について
LLMの出力の一貫性とは、似た入力に対して似た出力を生成する能力を指します。一貫性を高めるには、temperatureやtop_kなどのサンプリングパラメータを低く設定します。ただし、一貫性を重視しすぎると創造性が下がり、多様性が失われます。
Amazon Bedrockについて
Amazon Bedrockは、複数のLLMをAPI経由で利用できるマネージドサービスです。Anthropic ClaudeやLlama、Titanなどのモデルを利用でき、モデルの学習やデプロイを自前で行う必要がありません。テキスト生成や要約、質問応答、コード生成などのタスクに対応し、サンプリングパラメータ（temperature、top_k、top_pなど）を調整して出力を制御できます。統一インターフェイスであるConverse APIでは、全モデル共通のtemperature・topP・maxTokens・stopSequencesをinferenceConfigで、top_kのようなモデル固有のパラメータをadditionalModelRequestFieldsで指定します。
図による解説



temperatureの値がLLMの出力のばらつきを左右します。低いtemperature（0.2）では特定のトークンに確率が集中し、同じ入力に対してほぼ同じ出力が選ばれるため、回答が安定します。高いtemperature（1.0）では複数のトークンに確率が分散し、多様な出力が選ばれやすくなります。一貫性を求める用途では低い値が適しますが、temperatureを下げるだけでは次に選ばれる候補トークンの「範囲」は狭まりません。候補の絞り込みはtop_kやtop_pが担うため、temperature単独の調整では要件を十分に満たせません。同じ問い合わせに毎回同じ回答を返したいカスタマーサポートのような場面では、temperatureを下げるだけで候補トークンの数を絞らないままだと、一貫性は十分に高まりません。



top_kは次のトークン候補として考慮する数を制御します。top_kが小さい（3）と上位の候補だけに絞られるため出力が安定し、大きい（10）と多くの候補が残るため出力が多様になります。temperatureと同様に、一貫性を求めるなら小さい値が適します。ただしtop_kだけを下げても、temperatureが高ければ残った候補の中から確率に応じてばらついた選択が行われるため、安定化は不十分です。逆にtop_kを下げすぎると表現が単調になり多様性が失われます。両者を同時に下げて初めて「確率分布の集中」と「候補の絞り込み」が揃い、回答のばらつきが抑えられます。この使い分けを理解していないと、片方だけ調整して要件を満たせずに終わってしまいます。
解くための考え方
temperatureを上げると出力のランダム性が増して一貫性が下がるため、temperatureを上げる対応は要件を満たしません。同様に、top_kを上げると候補トークンが増えてランダム性が増すため、top_kを上げる対応も要件を満たしません。
一方、temperatureを下げると出力のランダム性が下がって一貫性が向上し、top_kを下げると候補トークンが減ってランダム性が下がります。両方を同時に下げることで、回答のばらつきを最小限に抑えられます。
temperatureを下げてtop_kを上げる組み合わせは、top_kを上げる操作が一貫性を下げる方向に働き、temperatureを下げた効果を打ち消すため、一貫性は十分に改善されません。
したがって、回答の一貫性を高めるには、temperatureとtop_kの両方を下げるのが適切です。

前提知識
SageMaker Debuggerについて
SageMaker Debugger は、機械学習トレーニングの問題を自動検出し、リアルタイムでメトリクスを収集するサービスです。消失勾配（vanishing_gradient）や過学習（overfit）などを検出する組み込みルールに加え、GPU 使用率などのシステムメトリクスも監視します。ルールは設定するだけで利用でき、問題発生時にトレーニングの停止・CloudWatch へのアラート送信・SNS 通知といったアクションを実行できます。収集したメトリクスは TensorBoard や CloudWatch で可視化できます。
消失勾配について
消失勾配は、深いニューラルネットワークで勾配が小さくなりすぎて、ネットワークの浅い層の重みが更新されなくなる現象です。活性化関数や重みの初期化方法が原因となることがあります。消失勾配が起きると学習が停滞し、性能が向上しなくなります。SageMaker Debugger には勾配の大きさを監視して消失勾配を検出するルールが用意されています。
GPUの未使用について
GPU の未使用は、トレーニングジョブで GPU リソースが十分に活用されていない状態です。データの読み込みがボトルネックになっている場合やバッチサイズが小さすぎる場合などに発生します。GPU 未使用が続くとトレーニング時間が長くなり、コスト効率が低下します。SageMaker Debugger は GPU 使用率などのシステムメトリクスを監視しており、組み込みプロファイラールールの LowGPUUtilization が、GPU 使用率の 95 パーセンタイルがしきい値（既定 70%）を下回った場合などにこの状態を検出します。
過学習について
過学習は、モデルが訓練データに過度に適合し、新しいデータに対する性能が低下する現象です。モデルの複雑さが高すぎる場合や訓練データが少なすぎる場合などに発生します。過学習が起きると訓練データでは高い性能を示す一方、検証・テストデータでは性能が低下します。SageMaker Debugger には訓練損失と検証損失の差を監視して過学習を検出するルールが用意されています。
TensorBoardについて
TensorBoard は TensorFlow のトレーニングを可視化するツールで、損失・精度・勾配などのメトリクスをグラフ表示できます。ただし問題の自動検出機能はなく、検出して対応するには追加の実装が必要です。SageMaker でも TensorBoard を使えますが、消失勾配や過学習といった問題の自動検出には限界があります。
SageMaker Experimentsについて
Amazon SageMaker Experiments は、機械学習の実験の入力・パラメータ・設定・結果を実行（Run）として自動的に記録し、実行同士を比較する機能です。最も性能の高いモデルを特定する用途には便利ですが、消失勾配や過学習・GPU 未使用を自動検出する組み込みルールや、検出時に対応を起動する仕組みは持ちません。問題を検出して対応するには別途ロジックの実装が必要です。
CloudWatchメトリクスについて
Amazon CloudWatch は AWS リソースのメトリクスを収集・監視するサービスです。SageMaker トレーニングジョブでは CPU 使用率・メモリ使用率・GPU 使用率などの基本的なメトリクスが提供されます。ただし消失勾配や過学習のような機械学習特有の問題を検出する機能はなく、カスタムメトリクスの実装と問題検出ロジックの追加実装が必要になり、運用の手間が増えます。

SageMaker Debugger は、問題の検出から対応までを一元的に担います。SageMaker Studio で開始したトレーニングジョブから収集したテンソルと GPU のリソース情報を Debugger がリアルタイムに監視し、組み込みルール（消失勾配・GPU 未使用・過学習）を適用して問題を検出します。検出時にはあらかじめ定義したアクション（トレーニング停止やアラート送信）を自動で実行し、勾配や GPU 使用率・損失値などのメトリクスは CloudWatch や TensorBoard へ送って可視化します。TensorBoard・CloudWatch・SageMaker Experiments などで可視化・記録するだけの構成では、検出・対応の自動化がなく、Lambda で自前実装する分だけ運用の手間が増えます。



逆伝播のたびに勾配が層を遡りながら減衰していく「消失勾配」の様子を、対数目盛の折れ線で示しています。出力に近い層10では勾配が約0.5と十分に大きいのに対し、入力に近い層1では0.001程度まで小さくなり、重みの更新量がほぼゼロになります。こうなると浅い層の重みが更新されず、いくらエポックを重ねても学習が停滞してモデルの性能が頭打ちになります。原因はシグモイド関数の飽和や不適切な重み初期化にあることが多く、活性化関数の見直しや初期化の工夫が必要です。SageMaker Debugger の vanishing_gradient ルールは勾配の絶対値の平均がしきい値（既定 0.0000001）を下回ったことを検出するため、人手で確認するより早く対処へ移れます。



訓練損失（青）と検証損失（赤）の推移を重ねています。エポック15付近までは両方とも下がり続けますが、そこを境に訓練損失はさらに減少する一方、検証損失が上昇へ転じます。これは、モデルが訓練データの細かな特徴まで覚え込み、未知のデータへ一般化できなくなった状態、つまり過学習の典型です。訓練データが少ない場合やモデルが複雑すぎる場合に起きやすく、モデルの単純化も有効な対策になります。対策には正則化・ドロップアウト・データ拡張・早期停止があり、特に検証損失が最小となるエポックで学習を止める早期停止が有効です。SageMaker Debugger の overfit ルールは、検証損失と訓練損失の差が訓練損失に対して占める割合が比率のしきい値（既定 0.1）を超えたことでこの乖離を検出するため、早期停止などの手当てを自動化できます。



正常なケース（上）と問題のあるケース（下）の GPU 使用率を時間経過で並べています。上が85%前後で安定して高止まりしているのに対し、下は25%前後まで落ち込んでおり、GPU の演算能力を十分に引き出せていません。この差は、データの読み込みがボトルネックになっているか、バッチサイズが小さすぎて GPU が待ち状態になっていることを示します。GPU を活用できていないとトレーニング時間が延びてコスト効率が落ちるため、SageMaker Debugger のシステムメトリクス監視で早期に気付けます。データローダーの並列化やワーカー数の増加、バッチサイズの見直しへつなげられます。こうした監視を怠ると GPU の稼働率が低いままトレーニングを続けることになり、コストと時間の無駄が大きくなります。
解くための考え方
SageMaker Debugger は消失勾配・GPU 未使用・過学習を検出する組み込みルールを提供しており、設定するだけで利用できます。問題発生時には決められたアクションを開始でき、トレーニング中のリアルタイムメトリクス（勾配・GPU 使用率・損失など）も提供します。

したがって、運用の手間を増やさずに検出と対応を自動化するには、SageMaker Debugger の組み込みルールを使います。

前提知識
LightGBMについて
LightGBMは、勾配ブースティングフレームワークに基づくアルゴリズムで、決定木を組み合わせて強力な予測モデルを構築します。特徴量間の非線形な関係や複雑なパターンを捉える能力が高いため、不正利用検知のような複雑な分類問題に適しています。SageMakerの組み込みアルゴリズムとしては表形式の分類と回帰に対応し、Daskを使ったマルチインスタンスCPUの分散学習もサポートします。クラス不均衡に対しては、二項分類向けのハイパーパラメータとして、正のクラスのラベルに重みを与えるscale_pos_weight（既定値1.0）と、不均衡データであることをアルゴリズムに知らせるis_unbalance（既定値False）が用意されており、両者は併用できません。メモリバウンドなアルゴリズムのため、M5などの汎用インスタンスが推奨されます。
Linear Learner（線形学習器）について
Linear Learner（線形学習器）は、線形モデルに基づくアルゴリズムで、特徴量間の線形な関係を捉えることに適しています。ロジスティック回帰や線形サポートベクターマシンなどの手法を含み、シンプルで解釈しやすいモデルを構築できます。しかし、特徴量間の非線形な関係や複雑な相互依存関係を捉える能力は限定的です。不正利用のように複数の特徴量が組み合わさる問題では、非線形な関係を捉える能力が重要となります。
PCA（主成分分析）について
PCA（主成分分析）は、教師なし学習の次元削減アルゴリズムです。できるだけ情報を保ちながら、互いに相関のない「成分」と呼ばれる新しい特徴を見つけて特徴量の数を減らします。データの構造の把握や可視化には使えますが、ラベル付きデータを使って分類モデルを構築する教師あり学習の問題には適していません。不正利用検知は教師あり学習の問題であり、PCA（主成分分析）は適切なアルゴリズムではありません。
LDA（潜在的ディリクレ配分）について
LDA（潜在的ディリクレ配分）は、テキストコーパスからトピックを抽出するための教師なし学習アルゴリズムです。文書の集合から、ユーザーが指定した数のトピックを発見します。テキストマイニングや文書分析には適していますが、取引記録のような構造化データの予測や分類には適していません。不正利用検知は構造化データを使った分類問題であり、LDA（潜在的ディリクレ配分）のようなトピックモデリングは適切ではありません。
不正利用検知の特性について
不正利用検知は、クラス不均衡、特徴量間の相互依存関係、複雑なパターンなど、複数の課題を抱える分類問題です。不正利用は正常な取引に比べてはるかに少ないためクラス不均衡が発生します。また、複数の特徴量が組み合わさって不正パターンを形づくるため、特徴量間の相互依存関係を捉える能力が重要です。さらに、不正パターンは複雑で非線形な関係を持つことが多く、複雑なパターンを捉えられるアルゴリズムが必要です。
図による解説



線形モデルと非線形モデルの近似能力の差が、精度を左右します。実際のデータは特徴量と目的変数の間に緩やかな曲線を描く関係を持ちますが、線形モデルは一本の直線でしか近似できず、データから大きく外れてしまいます。その誤差は、学習範囲から離れた値ほど大きくなります。勾配ブースティングに基づくLightGBMは決定木を組み合わせて非線形な関係を柔軟に捉えるため、実際の分布に沿った予測が可能です。不正利用のように特徴量とリスクの関係が複雑で非線形な問題では、この差がそのまま検知精度の差になります。線形モデルは解釈しやすい反面、複雑なパターンを捉えきれないため、データの分布が曲線を描くほど非線形モデルを選ぶ価値が高まります。



一つの特徴量だけでは正常と不正利用を分けられず、特徴量同士の相互作用を捉えられるかどうかが検知精度を決めます。取引金額だけを見ても青い正常な取引と赤い不正な取引は重なり合いますが、深夜の取引回数と組み合わせた二次元で見ると、不正な取引だけが群れから離れた位置に現れます。線形モデルは特徴量間の線形な関係しか扱えませんが、LightGBMのような非線形モデルは特徴量同士の相互作用まで学習できます。教師なしの次元削減やテキスト向けのトピックモデルは、こうした構造化データの分類には向きません。複数の特徴量が組み合わさって初めて見えてくる境界を捉えることが、不正利用検知の要です。
解くための考え方
LightGBMは勾配ブースティングに基づくアルゴリズムで、決定木を組み合わせて非線形な関係を学習します。クラス不均衡にも強く、複数の特徴量が掛け合わさって現れる相互作用を捉えられるため、不正利用検知のような問題に適しています。
一方、Linear Learner（線形学習器）は線形の近似に留まり、非線形な相互作用を捉えられません。PCA（主成分分析）は教師なしの次元削減で、分類モデルそのものにはなりません。LDA（潜在的ディリクレ配分）はテキストのトピック抽出を目的とした手法で、構造化データの分類には向きません。
したがって、クラス不均衡と特徴量間の相互作用の両方を扱うなら、LightGBMを使います。

前提知識
二値分類の混同行列について

二値分類モデルの予測結果は、真陽性（TP）、偽陽性（FP）、真陰性（TN）、偽陰性（FN）の 4 つに分類されます

真陽性は実際に不正で不正と予測した件数、偽陰性は実際に不正だが正常と予測した（見逃した）件数を表します

不正検知では、偽陰性（見逃し）が金銭的被害と信用低下に直結します

再現率（Recall）について

再現率は TP÷（TP＋FN）で計算され、実際の陽性クラスのうち正しく検出できた割合を示します

例えば、100 件の不正取引のうち 95 件を検出できれば再現率は 95% となります

再現率が高いほど見逃しが少ないことを意味し、不正検知や疾病診断など見逃しのコストが非常に高い場面で重視されます

身近な例では、空港のセキュリティ検査は再現率を重視しています。危険物の持ち込みを 1 件でも見逃すと大事故になるため、誤検知で無害な荷物を再検査するコストを許容してでも見逃しを最小化します

適合率（Precision）について

適合率は TP÷（TP＋FP）で計算され、陽性と予測した件数のうち実際に陽性だった割合を示します

適合率が高いほど誤検知が少ないことを意味します

スパムフィルタなど誤検知のコストが高い場面で重視されます。重要なメールをスパムと誤判定すると業務に支障が出るためです

F1スコアとAUCについて

F1 スコアは適合率と再現率の調和平均で、2×適合率×再現率÷（適合率＋再現率）で計算されます

適合率と再現率のバランスを取りたい場合に使います

AUC は ROC 曲線の下の面積で、モデルの全体的な分類性能を 0 から 1 の範囲で評価する指標です

AUC は閾値に依存しないモデル全体の性能評価に使われます

図による解説



二値分類の予測結果は TP・FP・TN・FN の 4 つに分解され、不正検知では見逃しに当たる FN の扱いが最も重要になります。縦軸が実際のクラス、横軸が予測されたクラスで、真陽性（TP）は不正を正しく検出した件数、偽陰性（FN）は不正を見逃した件数です。真陰性（TN）は正常を正しく正常と判定し、偽陽性（FP）は正常を不正と誤判定します。図の例では不正 100 件のうち 10 件が FN、つまり 1 割を見逃しています。不正取引を 1 件でも見逃すと金銭的被害や信用低下に直結するため、FN をどれだけ減らせるかが評価の中心になります。誤検知（FP）だけを減らそうと適合率を追うと、確実な取引しか不正と判定しなくなり、かえって FN が増える恐れがあります。



再現率と適合率は同じ混同行列から計算されますが、分母の取り方が異なるため評価の軸が正反対になります。再現率は TP÷(TP+FN) で、実際の不正取引のうち検出できた割合を示し、図の例では 90÷(90+10)=90% です。適合率は TP÷(TP+FP) で、不正と判定した取引のうち実際に不正だった割合を示し、90÷(90+50)≒64% です。再現率を上げるには判定を甘くして広く拾い、適合率を上げるには判定を厳しくして確実なものだけ拾う、というトレードオフの関係にあります。そのため「できるだけ多くの不正取引を特定する」という要件では、見逃しを減らす再現率を指標として最大化することが適切です。



F1 スコアが高いモデルが、必ずしも「できるだけ多くの不正取引を特定する」目標に合うとは限りません。上段の再現率重視モデルは再現率 95% と高いものの適合率が 50% に落ち、F1 スコアは約 65.5% です。下段のバランス型モデルは再現率 75%・適合率 80% で F1 スコアは約 77.4% と上回ります。F1 スコアは調和平均なので、一方だけを伸ばすと値が下がりやすい性質があります。見逃しの代償が極めて大きい不正検知では、F1 スコアの高さを追うのではなく、再現率そのものを最大化するのが適切です。バランスを優先すると 4 件に 1 件を見逃す結果になり、要件を満たせません。AUC も閾値に依存しない全体性能の指標で、検出率の最大化には直接つながりません。
解くための考え方
「できるだけ多くの不正取引を特定する」とは、実際の不正取引の中から漏れなくすべてを検出することを意味します。例えば、ある企業に 100 件の不正取引があった場合、そのうち何件を正しく検出できたかという割合を最大化したいということです。
この「実際の陽性サンプルに対する検出率」を直接測定するのが再現率（Recall）です。再現率の計算式は TP÷（TP＋FN）です。TP は正しく不正と判定した数、FN は見逃した不正取引の数です。再現率を最大化するということは、FN（見逃し）をゼロに近づけることを意味します。
適合率は「不正と予測した中で本当に不正だった割合」を測る指標です。適合率を重視すると、確実に不正と判断できるものだけを検出するようになり、結果として不正取引の見逃しが増えます。
F1 スコアは適合率と再現率のバランスを取る指標であり、一方を犠牲にして他方を最大化するような場面には適していません。AUC はモデルの全体的な性能を示す指標であり、「できるだけ多くの不正取引を特定する」という具体的な要件に焦点を当てた評価には向いていません。
不正取引の検出では、1 件の見逃しが大きな金銭的損失や信用問題につながるため、再現率を最重視することが適切です。
