問題25
不正解
ある企業のデータサイエンティストが、受信メールを「スパム」と「正規メール」に振り分ける分類モデルを開発しました。訓練に使ったデータセットは不均衡で、正規メールが大多数を占め、スパムはごく一部しか含まれていません。
このサービスの運用では、正規メールを誤ってスパムと判定すると、利用者が請求書や認証コードなどの重要な連絡を見逃し、サポートへの問い合わせが急増して運用コストが増大します。このモデルの性能を最も正確に評価する指標はどれですか。

回答は不正解です
Recall（再現率）

説明
不正解 Recall（再現率）は、実際にスパムであるメールのうち、モデルが正しくスパムと判定した割合で、TP / (TP + FN) で計算されます。スパムの見逃し（FN）を減らすことに焦点を当てますが、本問で重視すべきは正規メールをスパムと誤判定するFalse Positive（FP）です。RecallはFPを直接評価しないため、FPが運用コストの増加要因となるこの要件には適していません。

正解
Precision（適合率）

説明
正解 Precision（適合率）は、モデルがスパムと判定したメールのうち実際にスパムだった割合で、TP / (TP + FP) で計算されます。分母に False Positive を含むため、正規メールをスパムへ回す誤りが増えるほど値が直接下がり、この誤りの多さを定量的に捉えられます。本問では正規メールの誤検出が重要な連絡の見逃しと問い合わせ増加という運用コストに直結するので、FP の抑制度合いをそのまま表す Precision がモデル性能を最も正確に評価する指標になります。

Accuracy（精度）

説明
不正解 Accuracy（精度）は全体の正解率で、(TP + TN) / (TP + TN + FP + FN) で計算されます。不均衡データでは多数派クラス（正規メール）の正解が支配的になり、少数派クラス（スパム）の判定精度を適切に反映しません。また、FPとFNを区別しないため、FPによるコスト増加を重視するこの要件には適していません。

F1 score（F1スコア）

説明
不正解 F1スコアは、Precision（適合率）とRecall（再現率）の調和平均で、両者を等しく重み付けします。本問では正規メールの誤検出（FP）を特に減らしたいため、Precisionに重点を置く必要があります。F1スコアはPrecisionとRecallを均等に扱うため、FPを最小化するという要件には不十分です。

全体的な説明
問われている要件

不均衡データセットで各評価指標がどのように振る舞うかを理解していること

False Positive（偽陽性）とFalse Negative（偽陰性）の違いと、それぞれの影響を理解していること

Precision／Recall／F1スコア／Accuracyの計算式と意味を理解していること

ビジネス要件（FPによるコスト増加）に合った指標を選択できること

前提知識
機械学習の評価指標について
分類モデルの評価には複数の指標が使われます。Accuracy（精度）は全体の正解率で、(TP + TN) / (TP + TN + FP + FN) で計算されますが、不均衡データでは多数派クラスに引きずられます。Precision（適合率）は「陽性と予測した中で実際に陽性だった割合」で、TP / (TP + FP) です。FP（偽陽性）を抑えたい場面に適します。Recall（再現率）は「実際に陽性のうち正しく陽性と予測した割合」で、TP / (TP + FN) です。FN（偽陰性）の見逃しを抑えたい場面に適します。F1スコアはPrecisionとRecallの調和平均で、2 × (Precision × Recall) / (Precision + Recall) です。両者のバランスを重視する場面に適します。
不均衡データセットについて
不均衡データセットは、クラス間のサンプル数に大きな偏りがあるデータです。本問のように正規メールが多数でスパムが少数の場合、モデルは多数派（正規メール）を優先して予測しがちです。不均衡データではAccuracyが多数派の正解に支配され、少数派の判定精度を反映しません。そのため、要件に応じてPrecisionやRecall、F1スコアなど、FP・FNのどちらを重視するかを踏まえた指標を選ぶ必要があります。
False PositiveとFalse Negativeについて
False Positive（FP、偽陽性）は、実際には陰性なのにモデルが陽性と誤って予測した場合です。本問では正規メールをスパムと誤判定するケースがFPで、重要な連絡の見逃しによる問い合わせ増加というコストを生みます。False Negative（FN、偽陰性）は、実際には陽性なのにモデルが陰性と誤って予測した場合で、本問ではスパムを見逃すケースです。要件に応じてFPとFNのどちらを重視するかを決め、指標を選びます。
図による解説



混同行列は、スパム判定モデルの予測結果を「実際のクラス×予測クラス」で整理します。左上がスパムを正しくスパムと判定したTrue Positive、右上がスパムを正規メールと判定して見逃したFalse Negative、左下が正規メールを誤ってスパムとしたFalse Positive、右下が正しく正規メールとしたTrue Negativeです。本問で重要なのは左下のFalse Positiveで、正規メールをスパムに回す誤りが増えるほど、利用者が重要な連絡を見逃して問い合わせが増え、運用コストが膨らみます。混同行列の4区分のうち、どのセルがコストに効くかを見極めるのが指標選びの第一歩です。FPを減らしたいなら、FPを分母に含むPrecisionがこの誤りを直接測ります。



同じ混同行列から算出したPrecision・Recall・F1スコアを並べると、Precisionは「スパムと判定した中で実際にスパムだった割合」、Recallは「実際のスパムをどれだけ検出できたか」、F1はその調和平均です。FPの増加はPrecisionを直接下げますが、Recallには影響しません。本問のように正規メールの誤検出がコストに直結する場面では、FPを分母に持つPrecisionが最も実態を反映します。Accuracyは正規メールが多数を占める不均衡データでは高止まりしやすく、FPの影響を覆い隠すため、指標選びを誤ると「一見高精度なのに運用コストが膨らむ」モデルを採用してしまいます。
解くための考え方
「正規メールを誤ってスパムと判定すると運用コストが増大する」という記述から、False Positive（FP、正規メールの誤検出）がコスト増加の原因だとわかります。
各指標がFPをどう評価するかを整理します。Accuracyは全体の正解率でFPとFNを区別せず、不均衡データでは多数派（正規メール）に引きずられて機能しません。RecallはFN（スパムの見逃し）を減らす指標で、FPを直接評価しません。F1スコアはPrecisionとRecallを均等に扱うため、Precisionに重点を置きたい本問には不十分です。
Precisionは、スパムと判定した中で実際にスパムだった割合で、FPを分母に含みます。FPが少ないほどPrecisionは高くなるため、正規メールの誤検出がコストに直結する本問のモデル性能を最も正確に評価します。

問題28
不正解
ある企業のデータサイエンスチームは、過去の取引履歴を使って、新規商品の価格を予測するモデルを作ろうとしています。学習に使うデータセットには、サイズ、経過年数、立地条件、構成数など 32 個の特徴量が含まれています。
価格を予測するという目的に対して、ビジネス要件を満たすモデルはどれですか。

K-means（K-means 法）

説明
不正解 K-means は、各データ点を n 次元空間の点として扱い、ユークリッド距離が近いもの同士をあらかじめ指定した数のクラスタへまとめる教師なし学習のクラスタリングアルゴリズムです。正解ラベルを与えずにデータ内の似たグループを見つけることが目的であり、出力として得られるのは各データが属するクラスタの番号だけです。過去の取引履歴という正解付きのデータから価格という連続値を推定する用途には使えません。

回答は不正解です
Logistic regression（ロジスティック回帰）

説明
不正解 ロジスティック回帰は名称に回帰と付きますが、特徴量の線形結合をシグモイド関数で 0 から 1 の確率へ変換し、閾値を境に 2 つのクラスへ振り分ける二項分類のアルゴリズムです。出力できるのは所属確率とクラスラベルであり、価格のような連続値をそのまま推定することはできません。本問で求められているのは連続値の予測であるため、分類ではなく回帰のアルゴリズムを選ぶ必要があります。

Principal component analysis (PCA)（主成分分析）

説明
不正解 PCA は、元の特徴量を組み合わせて互いに無相関な成分を作り、第 1 成分がデータの分散を最大限に説明するよう順に並べることで次元を削減する教師なし学習のアルゴリズムです。32 個の特徴量を圧縮する前処理としては有効ですが、目的変数を一切使わないため PCA 自体は価格を出力しません。価格を予測するには、次元削減の後に回帰アルゴリズムを適用する必要があります。

正解
Linear regression（線形回帰）

説明
正解 線形回帰は、特徴量の重み付き和として目的変数を表す教師あり学習の回帰アルゴリズムで、実数値の予測を行います。サイズや経過年数、立地条件といった 32 個の特徴量をすべて説明変数として取り込む重回帰として扱え、各特徴量の係数が価格へ与える影響の大きさを表すため、予測根拠の説明もしやすくなります。Amazon SageMaker AI の線形学習（Linear Learner）アルゴリズムも回帰と分類の両方の問題に対応しており、価格のような連続値の予測というビジネス要件を満たせます。

全体的な説明
問われている要件

履歴データに基づく価格予測という教師あり学習の問題であることを理解していること

価格という連続値を予測する回帰問題であることを理解していること

32 個の特徴量を扱えるモデルを選べること

回帰と分類、教師あり学習と教師なし学習を区別できること

前提知識
Linear Regression（線形回帰）について
線形回帰は、連続値を予測する回帰アルゴリズムです。1 つまたは複数の特徴量（独立変数）から目的変数（従属変数）を予測します。特徴量と目的変数の関係が線形である場合に効果的で、複数の特徴量を扱う場合は重回帰と呼ばれます。価格予測、売上予測、需要予測などの回帰問題に適用できます。
Logistic Regression（ロジスティック回帰）について
ロジスティック回帰は、2 つのクラスに分類する二項分類アルゴリズムです。確率を返し、閾値を設定してクラスラベルを予測します。離散的なクラスラベルを予測する分類問題に適用され、連続値を予測する回帰問題には適用できません。不正検出、スパム検出、疾患診断などの分類問題に使われます。
K-means（K-means 法）について
K-means はクラスタリングのアルゴリズムで、教師なし学習の手法です。データを類似したグループ（クラスタ）へ分類する用途であり、価格を予測する回帰問題には適用できません。クラスタリングはデータの構造を発見して似たもの同士をまとめるための手法であり、目的変数の値そのものを推定する用途には使われません。顧客セグメンテーションや異常検出などに適用されます。
Principal Component Analysis（PCA）（主成分分析）について
PCA は次元削減の手法で、教師なし学習のアルゴリズムです。高次元のデータを低次元へ変換し、分散を最大限に保つ主成分を抽出します。価格を予測する回帰問題には適用できず、特徴量抽出や次元削減の前処理として使われます。可視化、ノイズ除去、計算コスト削減などに適用されます。
回帰問題と分類問題の違いについて
回帰問題は連続値を予測する問題で、価格、売上、需要などの連続値を予測します。分類問題は離散的なクラスラベルを予測する問題で、不正か否か、スパムか否かなどのラベルを予測します。価格という連続値を予測する回帰問題であり、分類問題ではありません。
図による解説



線形回帰は、特徴量と目的変数の関係を 1 本の直線で近似します。散布図の各点は過去の取引事例を表し、横軸がサイズ、縦軸が価格です。回帰直線は、サイズから価格を最もよく予測できるよう誤差の二乗和を最小化して引かれています。新しい商品のサイズをこの直線に当てはめれば、対応する価格を推定できます。ただし直線で表せるのは線形の関係に限られるため、サイズと価格が曲線状に推移する場合や、価格を分類で決める場合はこのモデルをそのまま使えません。分類やクラスタリングを選ぶと連続値の推定自体ができません。



残差プロットは線形回帰の当てはまりを検証します。残差とは実測値と予測値の差のことで、横軸に予測価格、縦軸に残差をとります。理想的な回帰モデルでは、残差が 0 を中心に上下にランダムに散らばり、目立った規則性が現れません。一方、残差が曲線状に並んだり、予測価格が大きくなるほど上下に広がったりする場合は、線形性や等分散性といった回帰の前提が崩れており、モデルがデータに十分適合していません。残差プロットは予測を行うのではなく、回帰の前提が満たされているかを確認するためのものです。価格予測そのものと、その妥当性の検証を混同しません。
解くための考え方
過去の取引履歴データをもとに、新規商品の価格を予測します。価格は連続値であり、サイズや経過年数などの複数の特徴量から価格を予測する回帰問題として扱えます。
履歴データに基づいて価格を予測するため、教師あり学習の回帰問題です。
線形回帰は連続値を予測する回帰アルゴリズムで、複数の特徴量を扱えます。32 個の特徴量があっても重回帰として扱えます。特徴量と価格の関係が線形に近い場合、線形回帰はシンプルで効果的です。線形回帰がビジネス要件を満たします。
ロジスティック回帰は二項分類アルゴリズムであり、連続値を予測する回帰問題には適用できません。K-means はクラスタリング、PCA は次元削減の手法で、いずれも教師なし学習であり、価格を予測する回帰問題には適用できません。
ビジネス要件を満たすモデルは線形回帰（Linear Regression）です。

前提知識
予測（フォーキャスティング）について
予測は、時間の順に並んだ過去の値からパターンを学び、まだ観測されていない将来の値を推定するタスクです。出力は数値であり、水準（ベースライン）・トレンド（長期的な増減）・季節性（週次や年次の周期）といった成分を履歴から捉えます。売上予測・需要予測・在庫計画などに使われます。Amazon SageMaker AI の Autopilot および Canvas の時系列予測では、CNN-QR、DeepAR+、Prophet、NPTS、ARIMA、ETS の6つのアルゴリズムを訓練し、それらをスタッキングアンサンブルで組み合わせて精度を高められます。DeepAR は多数の関連する時系列をまとめて学習する SageMaker AI の組み込みアルゴリズムとしても提供されています。
分類について
分類は、個々のデータポイントを事前に定義したカテゴリへ振り分けるタスクで、出力はカテゴリのラベル（または各カテゴリへの所属確率）です。訓練には、入力となる特徴量と確定した正解ラベルの組が必要になります。個々の予約をキャンセル理由のカテゴリに割り当てることはできても、カテゴリごとの件数が将来の各月にどれだけ発生するかを求める用途には向きません。時間軸そのものを学習対象にしていないためです。
強化学習について
強化学習は、エージェントが環境に対して行動を選び、返ってくる報酬を手がかりに累積報酬を最大化する方策を試行錯誤で学ぶ手法です。ゲームのプレイ、ロボット制御、レコメンドの出し分けなど、行動が次の状態に影響する意思決定問題に向きます。報酬関数と環境の設計が前提となるため、過去の履歴だけから将来の値を推定する用途には適しません。
時系列データについて
時系列データは、時間の経過に沿って並んだ値の列です。分析にあたっては、粒度（日次・月次など）を揃えた等間隔の系列に集計しておく必要があります。予約IDで記録を一意に数え、結果が確定した日付を月単位に丸めてキャンセル理由カテゴリごとに集計すれば、200本の月次時系列が得られます。過去3年分あればカテゴリごとに36点の観測が並び、年次の季節性を判断できるだけの周期数を確保できます。
図による解説



1枚目は、過去の実績値（青い点）の推移からパターンを学習し、その先の将来値を予測線（赤い線）として伸ばす時系列予測です。求められるのは、個々の予約をキャンセル理由へ振り分けることではなく、各カテゴリに属する予約の件数を月単位の時系列とみなし、数か月先までその数を予測することです。過去3年分の記録をカテゴリ別に集計して月次の件数へ変換すれば、DeepARやProphetといった予測アルゴリズムで将来の件数を推定できます。ここで分類を選ぶと、カテゴリのラベルは得られても「将来どれだけ発生するか」という件数の問いに答えられません。履歴が短いと予測線が不安定になるため、過去3年分の十分な履歴を活かすことが精度の前提になります。



2枚目では、上段の分類は個々の予約を200のキャンセル理由カテゴリのいずれかに振り分け、下段の予測はカテゴリごとの件数を時系列で追って将来の件数を推定します。要件が「各カテゴリに属する予約の数を毎月予測する」ことである以上、必要なのは上段のラベル付けではなく下段の件数予測です。分類を選ぶと、個々の予約がどのカテゴリに入るかは分かっても、将来の月ごとの件数という問いには答えられません。部分情報しかない記録を分類に使おうとすると候補が絞れず精度も落ちるため、件数集計と時系列予測に徹するのが妥当です。分類と予測を混在させる構成は一貫性を欠き、運用を複雑にするだけです。
解くための考え方
まず、求められている出力の形を確認します。要件は「各キャンセル理由カテゴリに属する予約の件数を、数か月先まで毎月」求めることであり、答えとして返すべきものは個々の予約に付くラベルではなく、カテゴリごと・月ごとの数値です。将来の月にはまだ予約の記録自体が存在しないため、既存のデータに何かを割り当てる発想では答えが出ません。ここで時系列予測が必要だと判断できます。
次に、手元のデータがその形に集計できるかを見ます。各記録は予約ID、キャンセル理由、結果が確定した日付を持つため、日付を月単位に丸めてカテゴリごとに件数を数えれば、200本の月次時系列に変換できます。各カテゴリに数百件、過去3年分の履歴があるので、カテゴリあたり36点の観測が並び、水準・トレンド・季節性を学習するだけの材料がそろいます。部分的な情報しか持たない記録は候補が3つか4つに絞られているだけで確定した理由が分からないため、そのまま件数へ算入せず、除外するか候補として別扱いにします。
この視点で各案を評価します。毎月分類を実行する案は、既に発生した予約にラベルを付けるだけで、将来の月の件数という問いには答えません。強化学習を使う案は、報酬設計を伴う意思決定問題向けの手法であるうえ、担当者が毎月手作業で件数を算出する部分が残るため自動化されたソリューションになりません。一部のカテゴリを分類、残りを予測とする案は、同じ問いに二つのタスクを併走させることになり、前処理も評価指標も分かれて運用が複雑になるうえ、確定ラベルのない記録では分類器を訓練できません。
残る、予約IDと日付を使って予測を実行する案が、月次の件数へ集計した時系列から将来の件数を推定するという要件どおりの構成であり、正解です。

Amazon Data Firehoseは、ストリーミングデータをS3、Redshift、OpenSearch Serviceなどの宛先へ自動配信するフルマネージドサービスです。なお本サービスは2024年2月にAmazon Kinesis Data FirehoseからAmazon Data Firehoseへ改称されており、現行のAWSドキュメントとコンソールではこの名称が使われています。バッファリング、圧縮、変換を自動で処理し、運用の手間を抑えられます。S3を宛先とする場合のバッファリングヒントは、バッファサイズが1〜128MB（既定5MB）、バッファ間隔が0〜900秒（既定300秒）の範囲で設定でき、要件のレイテンシに合わせて調整できます。バッファ間隔を0秒に設定するとバッファリングせず数秒以内に配信でき、60秒未満に設定した場合はマルチパートアップロードが使われます。Lambda関数によるデータ変換を統合でき、Kinesis Data Streamsから自動でデータを消費して変換後に宛先へ配信します。
AWS Lambda関数によるデータ変換について
AWS Lambda関数は、サーバーレスでコードを実行できるサービスです。Firehoseと統合すると、ストリーミングデータの変換をレコード単位で実行できます。フィールドの追加・削除・形式変換といった基本的な変換に適しており、変換ロジックの変更も関数を更新するだけで反映できます。
Amazon S3について
Amazon S3は、耐久性と可用性に優れたオブジェクトストレージサービスです。データレイクやデータウェアハウスでの分析処理における標準的な格納先として使われます。Firehoseは変換済みデータをS3へ自動保存するため、後続の機械学習モデルの再学習などでそのまま利用できます。
AWS Glueジョブについて
AWS Glueジョブは、ETL処理を実行するためのサーバーレスサービスです。バッチ処理や、Kinesis Data Streams・KafkaをソースとするストリーミングETLに使えます。ただし、Amazon Data Firehoseをソースとして読み取ることはできません。また、バッチジョブの起動には時間がかかり、短いレイテンシが求められる取り込みには向きません。
Amazon SageMaker Processingについて
Amazon SageMaker Processingは、データの前処理や特徴量エンジニアリング、モデル評価をバッチの処理ジョブとして実行する機能です。入力はS3（またはAthena・Redshift）に置かれたデータを前提とし、ジョブを送信するとコンピューティングを起動して処理し、完了後にリソースを解放します。連続的に流れ込むストリーミングデータを取り込む仕組みではないため、高スループットの取り込み経路には使えません。
図による解説



センサーからのテレメトリデータはまずKinesis Data Streamsが高スループットで受け止めて耐久性を確保し、Firehoseが自動で消費します。FirehoseはバッファリングしたレコードをLambdaへ渡して変換し、変換済みデータをS3へ配信します。Lambdaはレコード単位の変換だけを担うため、ロジックを変更しても他層へ影響しません。入り口にS3を置いたり、FirehoseにGlueジョブを直接接続したりすると、レイテンシが5分を超えたり、そもそもソースとして読めなかったりして要件を満たせません。
解くための考え方
Kinesis Data Streams、Amazon Data Firehose、Lambda、S3を組み合わせた構成は、高スループットの取り込みに向いており、Firehoseがバッファリングと変換を自動化して変換済みデータをS3へ配信します。S3宛先のバッファ間隔は既定が300秒（5分）で、そこから最短0秒まで下げられるため、5分以内のレイテンシ要件にも余裕をもって対応でき、運用の手間も最小限です。
IoTセンサーをS3へ直接送信し、Lambdaで変換してストリームへ流し、FirehoseでS3へ戻す構成は、同じデータをS3に二重保存する冗長な経路になり、ストレージ費用とレイテンシが増えます。
S3へ送信してSageMaker Processingジョブで変換する構成は、S3がストリーミング取り込みの入り口に適しておらず、バッチの処理ジョブでは5分以内のレイテンシ要件を満たすのが困難です。
Firehoseへ送信してGlueジョブで変換する構成は、GlueジョブがFirehoseを直接読み取れないため成立しません。

前提知識
VPCインターフェイスエンドポイントについて
VPC インターフェイスエンドポイントは、AWS PrivateLink の仕組みで、VPC 内から AWS サービスや VPC エンドポイントサービスへプライベート接続を提供します。指定したサブネット内に Elastic Network Interface（ENI）を作成してプライベート IP アドレスを割り当てるため、インターネットゲートウェイや NAT デバイス、VPN、Direct Connect を経由せずに AWS サービスへ到達できます。SageMaker Service API はインターフェイスエンドポイントに対応しています。
VPCエンドポイントポリシーについて
VPC エンドポイントポリシーは、エンドポイントを通じたアクセスを制御するリソースベースのポリシーです。デフォルトではすべてのプリンシパルによるすべてのアクションを許可しますが、カスタマイズすることで特定の IAM ユーザー、ロール、アカウントからのアクセスだけを許可できます。IAM ポリシーと組み合わせて、認証・認可レベルとネットワークレベルの両方で制御します。
セキュリティグループについて
セキュリティグループは、インスタンスや ENI 単位で動作するステートフルな仮想ファイアウォールです。VPC インターフェイスエンドポイントの ENI にも関連付けることができ、インバウンドとアウトバウンドのトラフィックを制御できます。ルールは許可のみをサポートし、拒否は設定できません。デフォルトではすべて拒否され、明示的に許可したトラフィックだけが通過します。
ネットワークACLとセキュリティグループの違いについて
ネットワーク ACL（NACL）はサブネット単位で動作するステートレスなファイアウォールで、許可と拒否の両方のルールを持てます。ただし、適用対象はサブネット単位であり、エンドポイントの ENI に直接関連付けることはできません。エンドポイントのネットワークインターフェイスと VPC 内のリソースとの間の通信が、そのサブネットのネットワーク ACL で許可されている必要はありますが、書けるのは IP 範囲とポートの許可・拒否までで、送信元を特定のインスタンスへ絞り込む用途には向きません。一方、セキュリティグループはインスタンスや ENI 単位で動作し、送信元に別のセキュリティグループを指定できるため、より細かな制御を提供します。
VPCフローログについて
VPC フローログは、VPC 内のネットワークインターフェイスを出入りする IP トラフィックの情報をキャプチャし、CloudWatch Logs や S3 などへ記録する機能です。制限が厳しすぎるセキュリティグループの診断やトラフィックの監視には役立ちますが、アクセスを許可・拒否する制御は行いません。あくまで監視・記録のための機能であり、トラフィックの保護には別の仕組みが必要です。
IAMポリシーとVPCエンドポイントポリシーの関係について
IAM ポリシーはユーザーやロールがどのサービスやリソースへアクセスできるかを制御します。VPC エンドポイントポリシーはエンドポイントを通じたアクセスを制御するリソースベースのポリシーです。両方が許可した場合にのみアクセスが成立するため、IAM ポリシーで許可していてもエンドポイントポリシーで拒否されれば到達できません。この二重の制御がセキュリティを強化します。
図による解説



EC2 インスタンスから SageMaker Service API へ至る経路は、セキュリティグループと VPC エンドポイントポリシーという異なる層で二重に制御します。インターフェイスエンドポイントの ENI は EC2 インスタンスと同じパブリックサブネット内に作られ、そこに関連付けたセキュリティグループが、インバウンドルールで許可した特定のインスタンスからのトラフィックだけを通過させます。あわせて VPC エンドポイントポリシーが IAM ユーザー単位でアクセス可否を判定し、両方の条件を満たした呼び出しだけが AWS PrivateLink 経由で SageMaker Service API へ到達します。IAM ポリシーの変更だけでは認可を絞るだけで経路を閉じられず、NACL はサブネット単位で ENI に直接適用できないため、この二層の制御が欠けると許可すべきでないインスタンスやユーザーまで到達してしまいます。
解くための考え方
「トラフィックを保護する」には、ネットワークレベルと認証・認可レベルの両方の制御が必要です。
IAM ユーザーへのアクセス制御には VPC エンドポイントポリシーを使います。ポリシーで特定の IAM ユーザーやロールだけを許可することで、認証・認可レベルで制御できます。
インスタンスへのアクセス制限には、エンドポイントの ENI に設定したセキュリティグループを使います。インバウンドルールで特定のインスタンスだけを許可することで、ネットワークレベルで制御できます。
IAM ポリシーを変更して SageMaker Service API 呼び出しだけを許可する案は、認可を絞るだけでトラフィックそのものを保護しません。エンドポイントの ENI に ACL を適用する案は、NACL がサブネット単位で ENI に直接適用できないため不適切です。VPC フローログで監視する案は、トラフィックを記録するだけで許可・拒否の制御にはならず、特定のインスタンスや IAM ユーザー以外を遮断できません。
エンドポイントに VPC エンドポイントポリシーを付与して IAM ユーザーへのアクセスを限定し、エンドポイントのネットワークインターフェイスにセキュリティグループを設定してインスタンスからの接続を制限すると、両層の制御が揃います。

前提知識
層化サンプリングについて
層化サンプリングは、データセットをクラスなどの属性ごとの層に分けたうえで、各層の内部で決められた割合を抽出する手法です。分割後の訓練用・検証用の双方で、各クラスが元のデータセットとほぼ同じ比率で現れます。全体の0.3%しかないクラスであっても、その層から一定割合が必ず検証側へ回るため、少数派クラスが片方の分割から完全に消えることがありません。scikit-learnではtrain_test_splitのstratify引数やStratifiedKFoldがこの分割方式を実装しています。
不均衡なデータセットについて
不均衡なデータセットは、一部のクラスのデータが他よりも極端に多い状態を指します。そのまま訓練するとモデルが多数派クラスを予測するだけで高い正解率を得られてしまい、少数派クラスの予測精度が低下します。全体の0.3%しかないクラスの場合、すべてを多数派と予測しても正解率は99.7%に達するため、正解率だけでは性能を判断できず、適合率・再現率やF1スコアといった指標での評価が必要になります。対処には、層化サンプリングやクラス重み付け、少数派クラスのオーバーサンプリングなどの手法が用いられます。
ランダムサンプリングと系統的サンプリングについて
ランダムサンプリングはデータを無作為に選び、系統的サンプリングは並んだデータから一定の間隔でn件おきに選びます。いずれもクラスラベルを参照しないため、不均衡なデータセットをそのまま分割すると、訓練側と検証側の双方で不均衡が維持されるうえ、少数派クラスの絶対数が小さい場合は分割の偶然によって比率が大きくぶれる恐れがあります。系統的サンプリングは、元データの並び順に抽出間隔と同じ周期性があると偏りがさらに強まります。
モデルの汎化について
モデルの汎化とは、訓練データで学習したパターンを未見のデータへ適用する能力です。訓練精度が高いのに検証精度が低い状態は、訓練データ特有のパターンに適合しすぎているか、検証データの構成が訓練データと異なっていることを示します。不均衡なデータセットを比率を考えずに分割すると後者が起こりやすく、層化サンプリングで各クラスを双方へ適切に配分することで、この偏りを抑えられます。
解くための考え方
不均衡なデータセットをランダムに分割すると、各クラスの比率が維持されず、稀な不良種別が検証側に適切に含まれません。訓練時は高い精度を示しても検証時に汎化が崩れるのは、この偏りが原因です。
層化サンプリングは、各クラスの比率を維持しながら分割するため、訓練用・検証用の双方で各不良種別が元の比率どおりに表現されます。これにより少数派クラスも学習・評価の対象に残り、検証精度が改善します。
残る3つの案は、いずれも分割方法そのものに手を入れていない点で共通しています。多数派の良品データを追加収集する方法は、データ量は増えるものの少数派の占める割合をさらに押し下げるため、不均衡を悪化させます。訓練データを無作為に間引く方法は、各クラスをおおむね同じ割合で減らすだけなので比率は変わらず、少数派の絶対数だけが減って学習が難しくなります。系統的サンプリングは一定間隔で機械的に抽出する手法で、クラスラベルを参照しないため比率の保証がなく、元データの並び順に周期性があると偏りがさらに強まります。
したがって、クラスラベルを見て層を分けたうえで各層から所定の割合を抽出する層化サンプリングが、要件に直接対応する唯一の選択肢になります。実装面でも、scikit-learnのtrain_test_splitにstratify引数としてラベル列を渡すか、交差検証でStratifiedKFoldを使うことで実現でき、追加の作り込みはほとんど必要ありません。

問題31
正解
ある企業の ML エンジニアが、各拠点の1日当たりの貸出台数を予測する線形回帰モデルを訓練しています。検証データに対する予測精度が下がってきたため過学習を疑い、L1正則化パラメータを導入して再度訓練しました。
すると、今度はすべての特徴量の重みがゼロになり、モデルがデータに適合できなくなりました。モデルの予測精度を改善するには、どのように対処すべきでしょうか。

回答は正解です
L1 正則化の係数を小さくし、それ以外の訓練パラメータは据え置きます。

説明
正解 L1 正則化は重みの絶対値の合計にペナルティを課すため、係数を大きくすると重みがちょうどゼロに落ちます。すべての重みがゼロになったのは係数が強すぎてモデルがデータに適合できなくなった未学習の状態であり、原因は L1 の係数そのものです。係数を小さくするとペナルティが弱まり、目的変数への寄与が大きい特徴量から順に重みが非ゼロへ戻って適合が回復します。他のパラメータを動かさずに係数だけを下げれば、過学習と未学習の中間へ調整でき、検証データでの予測精度が改善します。

現在の L1 正則化はそのままに、L2 正則化を小さな係数で新たに導入します。

説明
不正解 L2 正則化は重みの二乗の合計にペナルティを課す手法で、重みをゼロへ近づけはしますが、ゼロになった重みを非ゼロへ押し戻す働きは持ちません。係数を小さくして追加しても、L1 の強いペナルティによって重みがゼロに張り付いた状態は変わらず、モデルはデータに適合できないままです。対処すべきなのは追加する正則化の種類ではなく、未学習を招いている L1 の係数の大きさそのものです。

現在の L1 正則化はそのままに、L2 正則化を大きな係数で新たに導入します。

説明
不正解 全重みがゼロになっている原因は L1 の係数が過大なことであり、その係数を据え置いたまま別の正則化を追加してもゼロの状態は解消しません。むしろ大きな係数の L2 を重ねるとペナルティの総量が増え、重みをゼロ付近へ抑え込む力がさらに強まります。L1 と L2 を併用する構成そのものは Elastic Net として成り立ちますが、根本原因である L1 の係数に手を付けていないため未学習は解消せず、予測精度は改善しません。

L1 正則化の係数をさらに大きくし、それ以外の訓練パラメータは据え置きます。

説明
不正解 L1 正則化では係数を大きくするほど重みをゼロへ落とす力が強まり、非ゼロで残る特徴量の数が減っていきます。すでにすべての重みがゼロで、モデルが実質的に定数しか出力できない未学習の状態にあるため、係数をさらに大きくしても状況は変わらないか悪化するだけで、データへの適合は回復しません。過学習を抑えつつ適合を取り戻すには、正則化を強める方向ではなく弱める方向へ調整する必要があります。

全体的な説明
問われている要件

線形回帰モデルに過学習が起きていることを認識できること

L1正則化を導入した結果、すべての重みがゼロになった原因を特定できること

正則化係数の強弱と未学習・過学習の関係を理解していること

適切な対処としてL1正則化の係数を下げることを選択できること

前提知識
線形回帰モデルについて
線形回帰モデルは、説明変数と目的変数の間の線形関係を仮定するモデルです。最小二乗法などでパラメータを推定し、計算コストが低く解釈しやすいという利点があります。一方で、特徴量が多い場合などは訓練データへ過度に適合する過学習が起きやすく、その対策として正則化が用いられます。
過学習と未学習について
過学習は、モデルが訓練データに過剰適合して新しいデータへの予測性能が下がる現象です。逆に未学習は、モデルがデータに十分適合できず、訓練データと新しいデータの両方で性能が下がる現象です。正則化が弱すぎると過学習、強すぎると未学習に傾くため、両者のバランスを取ります。
L1正則化について
L1正則化（Lasso）は、重みの絶対値の合計にペナルティを課す手法です。不要な特徴量の重みをちょうどゼロに落とす特徴量選択の効果があり、係数が大きいほど多くの重みがゼロになります。係数が大きすぎると、すべての重みがゼロになり、モデルがデータに適合できなくなります。
L2正則化について
L2正則化（Ridge）は、重みの二乗の合計にペナルティを課す手法です。重みをゼロに近づけますが、完全にゼロにすることはありません。L1とL2を組み合わせたElastic Netも存在します。
図による解説



L1正則化（Lasso）の係数λを大きくしていくと、各特徴量の重みが次々とゼロに落ちていきます。λが小さいうちは重みが正負にばらついて残りますが、λを上げるにつれて絶対値の小さい重みから順にゼロへ収束し、最終的にすべての重みがゼロになります。L1は重みの絶対値にペナルティを課すため、解がちょうどゼロになりやすい（スパース化）のが特徴です。本問で全重みがゼロになったのはλが強すぎる証拠であり、λをさらに増やせば状況は悪化し、λを下げて初めて重みが非ゼロに戻ってモデルがデータに適合できるようになります。λを下げる方向へ調整すれば、不要な特徴量だけをゼロに保ちながら重要な特徴量の重みを回復できます。L2を足しても、このゼロの状態は変わりません。



正則化係数λに対する訓練誤差と検証誤差の推移では、λが小さすぎると訓練誤差は低いのに検証誤差が高く、訓練データへ過剰適合する過学習の領域になります。逆にλが大きすぎると両方の誤差が高止まりし、モデルがデータに十分適合できない未学習の領域になります。2つの誤差の差が最も縮まる中間のλが、過学習と未学習のバランスを取る適切な値です。本問の状況はλが右側に寄りすぎて未学習に陥った状態なので、λを下げる方向へ戻すのが正しい対処です。ここで訓練誤差だけを見てλを小さくしすぎると過学習へ戻り、検証誤差だけを追うと過度な正則化で未学習へ傾くため、両者を同時に見る必要があります。本問はλが大きすぎる側に寄っているため、λを下げて検証誤差が最小になる点へ戻すのが正解です。
解くための考え方
線形回帰モデルが過学習したためL1正則化を導入したところ、今度はすべての特徴量の重みがゼロになりました。これはL1正則化の係数が大きすぎて、モデルがデータに適合できなくなった（未学習の）状態です。
L1正則化の係数を増やす方法は、ペナルティをさらに強めるため、すでに全重みがゼロの状況を悪化させるだけです。
L1正則化の係数を減らす方法は、正則化を弱めて一部の重みを非ゼロに戻し、モデルの適合を回復させます。これにより過学習と未学習の中間を取り戻せ、予測精度が改善します。
大きなL2や小さなL2を追加する方法は、L1を残したまま正則化を足すため、重みゼロの状態から抜け出せず、根本原因のL1係数の過大さに対処できません。L2は重みの二乗にペナルティを課しますが、ゼロの重みに対する勾配はゼロです。

SageMaker Clarifyについて
SageMaker Clarifyは、機械学習モデルのバイアスを検出・説明するためのサービスです。訓練前のデータセットを対象に、クラス不均衡（CI）やラベルの比率差（DPL）などの統計的なバイアス指標を適用し、ファセット間の偏りを定量化します。SageMaker Studioと統合されており、コードを書かずにバイアス分析を実行して、結果を視覚的でインタラクティブなレポートとして表示できます。
SageMaker Data Wranglerについて
SageMaker Data Wranglerは、データのインポート、準備、変換、特徴量エンジニアリング、分析をノーコードで実行する機能です。データフローに追加できる「分析」の種類の一つとしてバイアスレポートが用意されており、予測対象のラベル列と調査したいファセット列（地域や商品カテゴリなど）を指定するだけで、訓練前データのバイアス指標を計算して視覚的なレポートとして表示できます。この機能は Data Wrangler の「分析と可視化」のドキュメントに記載されているものです。なお、データ準備機能自体は現在 SageMaker Canvas のデータ準備（旧 Data Wrangler）へ引き継がれていますが、Canvas 側のドキュメントで案内されている分析はデータ品質とインサイトのレポート、ターゲットリーケージ、クイックモデルなどで、バイアスレポートの提供は Data Wrangler のドキュメントで確認できます。
SageMaker Ground Truthについて
SageMaker Ground Truthは、データラベリングのためのサービスです。人間のラベラーを使って画像分類や物体検出、テキスト分類などのデータにラベルを付け、アクティブラーニングや自動ラベリングでラベル品質を高めます。ただし、データのバイアスを分析する機能はありません。

Amazon CloudWatch はメトリクス・ログの収集とダッシュボードによる可視化を行う監視サービスです。アラームやログ検索は提供しますが、クラス不均衡（CI）やラベルの比率差（DPL）といった統計的バイアス指標を算出してデータの偏りを定量化する機能はありません。

解くための考え方
まず、要件が「訓練を開始する前」の「データそのもの」の偏りを定量化してレポート化することだと押さえます。訓練後のモデル挙動の監視でも、インフラの稼働監視でもありません。この時点で、対象が推論結果や実行基盤である機能は候補から外れます。
訓練前データの偏りを数値で示す手段として用意されているのが、SageMaker Clarify の訓練前バイアス指標です。地域や商品カテゴリのような属性をファセットとして指定すると、クラス不均衡（CI）やラベルの比率差（DPL）といった指標を計算し、どの属性にどの程度の偏りがあるかを視覚的なレポートとして提示します。分析用のコードを自前で書く必要がないため、運用オーバーヘッドを小さく保てます。
もう一つの経路が、ノーコードでデータ準備を行う SageMaker Data Wrangler です。クレンジング済みデータの準備フローの中から Clarify を呼び出してバイアスレポートを生成できるため、既存のデータ準備作業の延長線上で偏りを可視化し、そのまま社内共有に使えます。
残る候補を見ると、Ground Truth はデータラベリングを支援するサービスで、ラベル品質は高められてもデータの偏りを測る機能はありません。CloudWatch はメトリクスとログを収集して稼働状況を可視化する監視サービスであり、データセットの属性別分布から統計的バイアス指標を算出することはできません。Experiments は試行ごとのメトリクスやパラメータを記録して比較する実験管理の機能で、やはりバイアス検出は担いません。したがって、SageMaker Clarify と SageMaker Data Wrangler の組み合わせが要件を満たします。
