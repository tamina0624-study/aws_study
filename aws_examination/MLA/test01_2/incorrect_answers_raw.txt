前提知識
クラス不均衡について
クラス不均衡とは、データセット内のクラスの分布が偏っている状態を指します。不良ロット予測のように、少数派のクラスが多数派に比べて極端に少ない場合に発生します。クラス不均衡が生じると、モデルは多数派に偏って学習し、少数派のクラスを適切に予測できなくなります。解消する主な手法には、オーバーサンプリング（少数クラスのサンプルを増やす）、アンダーサンプリング（多数クラスのサンプルを減らす）、合成サンプルの生成（SMOTEなど）があります。
Amazon SageMaker Data Wranglerについて
Amazon SageMaker Data Wranglerは、データの前処理、特徴量エンジニアリング、データバランシングを統合的に実行できるサービスです。クラス不均衡を解消するバランスデータ操作を提供しており、少数クラスをオーバーサンプリングしてクラス間の比率を揃えられます。視覚的なインターフェースで設定を調整でき、オペレータとしてランダムオーバーサンプリング、ランダムアンダーサンプリング、合成マイノリティオーバーサンプリング手法（SMOTE）を選択できます。SMOTEは数値特徴量の距離をもとに合成サンプルを内挿する手法で、列ベクトルを含むデータセットにはバランスデータ操作を適用できないという制約があります。現在このデータ準備機能はAmazon SageMaker Canvasに統合されており、Canvas上のData Wranglerとしてバランスデータ操作を含む変換を利用します。
Amazon QuickSightについて
Amazon QuickSightは、データをグラフやダッシュボードで可視化して分析するビジネスインテリジェンス（BI）サービスです。不良ロットと良品ロットの分布を可視化して状況を把握することはできますが、クラス不均衡を解消するオーバーサンプリング機能は備えていません。可視化や分析はあくまで現状把握のためのもので、少数クラスを増やして比率を揃える前処理ではありません。
Amazon SageMaker AIの組み込みアルゴリズムについて
Amazon SageMaker AIの組み込みアルゴリズムは、XGBoostや線形学習者（Linear Learner）など、代表的な機械学習タスク向けに最適化された実装をあらかじめ用意したものです。学習データを指定するだけでモデルを作成できますが、データそのものの不均衡を解消する前処理機能は提供していません。なお、組み込みのXGBoostには正例と負例の重みのバランスを制御するscale_pos_weightハイパーパラメータがあり、学習時の重み付けで不均衡に対処する余地はありますが、これはデータセットの比率を揃える前処理ではありません。学習前にデータ側で不均衡を解消したいという要件には、データ準備段階の機能が必要です。
AWS Glue DataBrewについて
AWS Glue DataBrewは、データのクリーニングと正規化を視覚的なインターフェースで実行するサービスです。欠損値の処理や形式の統一などに適していますが、クラス不均衡を解消するオーバーサンプリング機能はありません。データの品質向上や特徴量の作成には向いていますが、少数クラスを増やす専用の機能は提供していません。
図による解説



クラス不均衡の解消はモデル学習の前に行うデータ準備であり、専用のバランス機能によって初めて手間なく実現できます。変換前は少数クラス（不良ロット）が100件、多数クラス（良品ロット）が500件と大きく偏っており、このまま学習するとモデルは多数派の良品に寄って不良を見逃します。オーバーサンプリングでは少数クラスのサンプルを複製して500件へ増やし、クラス間の比率を揃えることで、モデルが少数派のパターンも学習できるようにします。可視化ツールで分布を眺めたり、学習アルゴリズムをそのまま使ったりしても少数クラスは自動的には増えません。比率の調整を手作業で行う運用は再現性に欠け、再実行や監査の面でも負担になります。
解くための考え方
少数クラスが極端に少ないまま学習すると、モデルは多数派に寄って不良を見逃します。少数クラスのオーバーサンプリングか、多数クラスのアンダーサンプリングで比率を揃えます。オーバーサンプリングは、少数クラスのサンプルを増やしてクラス間の比率を揃える手法です。
Amazon SageMaker Data Wranglerは、クラス不均衡を解消するバランスデータ操作を提供しています。少数クラスをオーバーサンプリングして比率を揃えられ、視覚的なインターフェースで設定を調整でき、SMOTEやランダムオーバーサンプリングなどの手法も選べるため、運用の手間が小さく済みます。
一方、Amazon QuickSightで分布を可視化・分析する方法は、状況の把握にはなってもクラス不均衡そのものは解消されません。SageMaker AIの組み込みアルゴリズムは前処理機能を持たず、AWS Glue DataBrewもオーバーサンプリング機能を提供していません。
したがって、学習前に少数クラスを手間なく増やすなら、Amazon SageMaker Data Wranglerのバランスデータ操作でオーバーサンプリングします。

前提知識
Amazon SageMaker Autopilotについて
Amazon SageMaker Autopilotは、機械学習モデルの構築を自動化するAutoML機能です。データセットを指定するだけで、データの前処理、特徴量エンジニアリング、アルゴリズムの選択とトレーニング、ハイパーパラメータの最適化を自動で実行します。複数のアルゴリズムを試行して最適なモデルを選び、完了後は精度、再現率、F1スコア、AUCなどのパフォーマンスメトリクスを自動で報告します。構造化データセットからターゲット変数を予測する分類・回帰タスクに適しており、最小限の開発作業で予測可能性を評価できます。入力データはAmazon S3上のCSVまたはParquetファイルとして指定します。新しいStudio体験ではAutopilotのUIはAmazon SageMaker Canvasに統合されており、APIやSDKからAutoMLジョブを直接実行することもできます。
カスタムスクリプトとEC2インスタンスについて
カスタムスクリプトで機械学習モデルを構築する場合、前処理、モデルの選択とトレーニング、評価までのコードを自前で開発する必要があります。EC2インスタンスの管理やスケーリング、セキュリティパッチの適用といった運用作業も加わり、開発工数が大きくなります。最小限の開発作業という要件を満たさず、同じ結果はSageMaker Autopilotで自動化できます。
AWS Glue DataBrewについて
AWS Glue DataBrewは、コードを書かずにデータをクリーニングし、正規化するためのビジュアルなデータ準備ツールです。異常値のフィルタリングや無効値の修正など250を超える変換を選んで、機械学習や分析に使える形へデータを整えます。ただしデータ準備が目的であり、予測モデルの構築やパフォーマンス評価を行う機能は持っていません。
Amazon Bedrockについて
Amazon Bedrockは、大規模言語モデル（LLM）や基盤モデル（FM）へアクセスするサービスです。複数の基盤モデルへアクセスでき、テキスト生成、要約、質問応答などに適しています。主に自然言語処理向けであり、構造化データセットからターゲット変数を予測する分類・回帰タスクには適していません。データでのチューニングにも追加の開発作業が必要です。
モデルの予測可能性評価について
モデルの予測可能性を評価するには、データセットでモデルをトレーニングし、パフォーマンスメトリクスを測定する必要があります。メトリクスには精度、再現率、F1スコア、AUCなどがあります。これらを測定して初めて、モデルがターゲット変数を予測できるかを判断できます。SageMaker Autopilotはこれらの処理を自動で実行し、メトリクスを報告します。
図による解説



予測可能性の判断に必要な前処理から評価までの一連の工程をAutopilotが実行し、利用者はデータセットの指定だけで済みます。AthenaでクエリしていたS3の予約データは、CSVまたはParquetのままSageMaker Autopilotの入力として指定されます。Athenaはデータの中身を確認するためのクエリ手段であり、Autopilotはその同じS3のデータセットを直接読み込みます。前処理、特徴量エンジニアリング、アルゴリズムの選択とトレーニング、ハイパーパラメータの最適化を経て候補モデルが自動的に試行され、最後に精度やF1スコアなどのメトリクスが自動で報告されます。その出力を見て、予約のキャンセル有無が予測できるかを判断できます。同じ流れをカスタムスクリプトとEC2で置き換える構成は、コードとインフラ管理がすべて自前になり工数が見合いません。全工程をマネージドに任せるかどうかが、AutoML採用の分岐点です。
解くための考え方
この問題で問われているのは、モデルを本格的に作り込むことではなく、宿泊予約がキャンセルされるかどうかというターゲット変数がそもそも予測可能かを見極める材料を、最小限の開発作業で手に入れることです。判断材料になるのは学習済みモデルの評価指標なので、モデルを一度は作る必要があります。そのうえで、コードとインフラをどれだけ自前で抱えるかが選択肢を分ける軸になります。

したがって、ターゲット変数の予測可能性を最小限の開発で見るなら、SageMaker Autopilotでモデルを作り、報告されたパフォーマンスを確認します。

AWS Glueについて
AWS Glueは、データの抽出・変換・読み込み（ETL）を実行するマネージドサービスです。S3、RDS、Redshiftなどのデータソースからデータを抽出し、変換して別のデータストアへ読み込みます。サーバーレスで動作し自動スケーリングされます。PythonやScalaでETLジョブを記述でき、Glue Data Catalogでメタデータを管理します。データのクリーニング・変換・構造化を実行してデータインジェスションパイプラインを構築するのに適しています。
Amazon Kinesis Data Streamsについて
Amazon Kinesis Data Streams は、ストリーミングデータをリアルタイムで収集・処理するサービスです。ログやクリックストリームなどを取り込み、複数のコンシューマーへ配信します。リアルタイムの取り込みが主目的で、既にS3へ集約済みの生データを変換・クリーニング・構造化するバッチ的なETLには適していません。
Amazon Redshift MLについて

Amazon Athenaについて
Amazon Athenaは、S3内のデータへ標準SQLクエリを実行するサーバーレスなインタラクティブクエリサービスです。分析やクエリには適していますが、データの変換・クリーニング・構造化を実行するデータインジェスションパイプラインの作成には適していません。既に構造化されたデータへクエリを実行するサービスであり、ETLを実行するサービスではありません。
Amazon SageMaker Studioについて
Amazon SageMaker Studio（新体験）は、MLモデルの開発・トレーニング・デプロイを一元的に行う統合開発環境（IDE）です。SageMaker PipelinesとModel Registryを組み込んで、バージョン管理と承認ワークフローを備えたデプロイパイプラインを作成できます。モデルの開発からデプロイまでMLライフサイクル全体をサポートします。2023年11月30日以降に作成されたアカウントでは新体験のStudioが既定となり、従来のSageMaker Studio ClassicはJupyterLab 3ベースのノートブックについて2024年12月31日でメンテナンスが終了しています。新規に構築するパイプラインの基盤としては、AWSも移行を推奨している新体験のStudioを選びます。
Amazon SageMaker notebookについて
Amazon SageMaker notebookは、Jupyter notebook環境を提供するサービスです。モデルの開発や実験には適していますが、毎回手動で起動する運用になりがちで、承認ワークフローを備えたデプロイパイプラインの基盤としては弱い位置づけです。デプロイパイプラインの作成には、SageMaker PipelinesとModel Registryを組み込めるSageMaker Studioのような統合環境が適切です。
データインジェスションパイプラインとモデルデプロイパイプラインについて
データインジェスションパイプラインは、生データを処理してMLモデルの学習に適した形式へ変換するパイプラインです。データの抽出・変換・クリーニング・構造化が必要で、AWS GlueのようなETLサービスが適切です。
モデルデプロイパイプラインは、学習済みモデルを本番環境へデプロイするパイプラインです。モデルのバージョン管理、承認ワークフロー、デプロイメントが必要で、SageMaker PipelinesとModel Registryを組み込めるSageMaker Studioが適切です。

生データ（利用記録や気象情報など）はS3に集約されており、AWS Glueが抽出・変換・読み込み（ETL）を実行して、学習に使える処理済みデータへ整えます。その処理済みデータをSageMaker Studioが取り込み、SageMaker PipelinesとModel Registryによる承認とバージョン管理を伴うデプロイパイプラインで本番エンドポイントへ展開します。インジェスションをKinesis Data StreamsやAthenaに任せると、既にS3にある生データのETLを担えず、デプロイをノートブック単体で回すと承認とバージョン管理が欠落します。前段のETLと後段のデプロイは、それぞれ役割の合うサービスへ分けます。
解くための考え方
この設問は、データインジェスションパイプラインとMLモデルデプロイパイプラインという2つの成果物を同時に求めており、選択肢もその2つの組み合わせで構成されています。したがって、前半のサービスと後半のサービスをそれぞれ役割に照らして評価し、両方が要件に合うものだけを残すという読み方になります。
S3内の生データを処理して学習に適した形式へ変換するには、抽出・変換・クリーニング・構造化が必要で、AWS GlueのようなETLサービスが適しています。GlueはサーバーレスのETLサービスで、クローラーがS3のデータからスキーマを推論してGlue Data Catalogに登録し、PythonまたはScalaで記述したジョブが変換処理を実行します。毎晩S3へ集約されるバッチデータを定期的に整形する用途に合致します。Amazon Kinesis Data Streams はストリーミングデータの収集サービスで、既にS3にある生データのETL変換には適していません。Amazon Redshift MLはインジェスションパイプラインを作るサービスではありません。Amazon Athenaはクエリには適していますが、ETLを実行するサービスではありません。
モデルデプロイ側では、バージョン管理、承認ワークフロー、デプロイメントが必要です。Amazon SageMaker Studio（新体験）はSageMaker PipelinesとModel Registryを組み込み、承認付きのデプロイパイプラインを構築できる統合環境として適しています。ノートブックインスタンスは開発や実験向けで手動運用になりがちであり、承認ワークフロー付きパイプラインの基盤としては弱いです。
したがって、インジェスションはAWS Glue、デプロイはSageMaker Studioに分けます。

ネットワークACLについて
ネットワークACLは、サブネットレベルでトラフィックを制御する機能です。許可ルールと拒否ルールの両方を作成でき、送信元IPアドレス、宛先IPアドレス、ポート番号、プロトコルなどに基づいてトラフィックを制御します。サブネット単位で動作するため、サブネット内の全リソースに適用されます。ステートレスであり、リクエストとレスポンスを別々に評価します。ルールはルール番号の小さいものから順に評価され、最初に一致したルールが適用されます。VPCのデフォルトネットワークACLはルール番号100ですべてのインバウンド／アウトバウンドトラフィックを許可しているため、特定の送信元IPを止めるにはそれより小さい番号で拒否ルールを追加します。
セキュリティグループについて
セキュリティグループは、インスタンスレベルでトラフィックを制御する機能です。許可ルールのみをサポートし、拒否ルールは作成できません。デフォルトですべてのトラフィックを拒否し、明示的に許可したトラフィックだけを通過させます。ステートフルで、リクエストを許可すると対応するレスポンスも自動許可されます。インスタンスレベルで動作するため、各リソースへ個別に割り当てる必要があります。
VPCフローログについて
VPCフローログは、ネットワークインターフェイスを通過するIPトラフィックの情報をキャプチャする機能です。送信元IP・宛先IP・ポートなどのメタデータを記録して分析に使いますが、トラフィックを拒否・遮断する機能はありません。フィルタリングにはネットワークACLやセキュリティグループを使用する必要があります。
AWS WAFについて
AWS WAFは、保護対象のウェブアプリケーションリソースへ転送されるHTTP(S)リクエストを監視するレイヤー7のファイアウォールです。CloudFrontディストリビューション、Application Load Balancer、API Gateway REST API、AppSync GraphQL API、Cognitoユーザープール、App Runnerサービス、Verified Accessインスタンス、Amplifyといったリソースを保護対象とし、IPセットに登録した送信元IPからのリクエストをブロックできます。ただし、パブリックサブネットで稼働するSageMakerドメインのネットワークインターフェイスは保護対象に含まれないため、このドメインへのトラフィックを送信元IPで遮断する用途には使えません。VPC内のリソースをソースIPでブロックするには、サブネットレベルのネットワークACLを使用します。
ネットワークレベルでのトラフィック制御について
特定のIPアドレスからのトラフィックをブロックするには、ネットワークレベルの制御が必要です。ネットワークACLはサブネットレベルでトラフィックを制御し、許可ルールと拒否ルールの両方を作成できます。特定のIPを拒否するインバウンドルールを作成し、サブネットのデフォルトネットワークACLへ割り当てることで、そのIPからのトラフィックをブロックできます。
図による解説



不審なIPからのトラフィックは、サブネット境界のネットワークACLの拒否ルールで遮断します。インターネット側の許可されたトラフィックだけがネットワークACLを通過してSageMakerドメインへ到達し、ブロック対象の特定IPからのトラフィックは拒否ルールで止められます。ネットワークACLはサブネットレベルで動作し、許可と拒否の両方を記述できるため、送信元IPを指定した明示的な拒否を表現できます。一方、セキュリティグループは許可ルールしか持てず拒否を記述できませんし、VPCフローログは通過したトラフィックを記録するだけで遮断は行いません。特定のIPを確実に止めるには、サブネット内の全リソースへ一律に適用されるネットワークACLのインバウンド拒否ルールを使うことが要件に合います。
解くための考え方
ネットワークACLはサブネットレベルでトラフィックを制御し、許可ルールと拒否ルールの両方を作成できます。特定のIPを拒否するインバウンドルールを作成し、サブネットのデフォルトネットワークACLへ割り当てると、SageMakerドメインへのそのIPからのトラフィックを止められます。
セキュリティグループは許可ルールのみをサポートし、拒否ルールを作成できません。特定のIPをブロックするには、そのIPを許可ルールから除外する必要があります。
AWS WAFはHTTP(S)リクエストを検査するレイヤー7のファイアウォールですが、SageMakerドメインのネットワークインターフェイスは保護対象に含まれず、IPセットによるブロックルールを適用できません。
VPCフローログは通過するトラフィックを記録する機能で、トラフィックを拒否する機能は提供していません。
したがって、特定IPの拒否は、サブネットのデフォルトネットワークACLへインバウンド拒否ルールを割り当てます。
