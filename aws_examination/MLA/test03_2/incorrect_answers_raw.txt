ベンダーワークフォースについて

ベンダーワークフォースは、データラベリング事業者をAWS Marketplaceでサブスクライブし、その事業者が管理するワーカーへ作業を委託する方式です。ワーカー数や稼働時間などの条件はベンダーの詳細ページで確認します。作業するのは組織外のワーカーであるため、機密データを送る前にベンダーのセキュリティ・コンプライアンス対策とEULAを確認する責任が利用者側にあります。

教師あり学習では、学習を始める前に正解ラベルを付けたデータが必要です。モデルの精度は学習データのラベルの質に大きく依存します。ラベルの無いデータをそのまま与えて学習させることはできません。教師なし学習とは異なり、教師あり学習では正確なラベル付きデータが欠かせません。

前提知識
SageMakerの入力モードについて

SageMaker訓練ジョブは、Amazon S3のほかEFSやFSx for Lustreからデータを読み込めます。S3から読む場合、AWSはデータセット全体が50〜100GB未満で収まるならファイルモード（全データをインスタンスのボリュームへダウンロードしてから訓練を開始する方式）を、それより大きいデータならファイルモードのダウンロード待ち時間を避けられる高速ファイルモード（fast file mode）を推奨しています。

高速ファイルモード（fast file mode）について

高速ファイルモードは、S3上のオブジェクトをPOSIXのファイルインターフェイス経由でストリーミング読み出しする入力モードです。全データのダウンロード完了を待たずに訓練を開始できるため、大規模データで起動時間を短縮できます。AWSは1ファイルあたり150MB超を理想、最低でも50MB超を目安として案内しており、それより小さいファイルが多数ある場合はTFRecordやWebDatasetなどへ150MB程度にまとめ直すことを勧めています。ファイルシステムの作成やVPCへの接続は不要で、入力チャネルに input_mode='FastFile' を指定するだけで切り替えられます。

Amazon EFSについて

Amazon EFSは複数のEC2インスタンスから同時にアクセスできる共有ファイルシステムです。すでにEFS上にデータがある場合は訓練ジョブから直接マウントできますが、S3にあるデータのために新たにファイルシステムを作る場合は、保存するデータ量に応じたストレージ料金が別途発生します。複数の訓練ジョブで同じデータを共有し続ける用途では有効です。

Amazon FSx for Lustreについて

Amazon FSx for Lustreは高性能コンピューティング向けの並列ファイルシステムで、S3バケットとリンクして自動でデータを取り込めます。スループットは秒あたり数百ギガバイト規模まで拡張でき、ファイルモードで扱いきれないほど大きなデータや、まとめにくい小さなファイルが大量にあるケース、ランダムアクセスが中心のワークロードに向きます。一方でプロビジョニングした容量に応じて料金がかかり、遅延読み込みによるコールドスタートやファイルシステム構築のオーバーヘッドも生じます。

Amazon EBSについて

Amazon EBSはEC2インスタンスにアタッチするブロックストレージです。あらかじめ容量を確保してデータをコピーする必要があり、確保した容量に対して料金がかかります。なおSageMaker訓練ジョブが入力データソースとして受け付けるのはAmazon S3、Amazon EFS、Amazon FSx for Lustreの3種類で、利用者が作成したEBSボリュームを入力として指定する仕組みはありません。訓練インスタンスのEBSボリュームは、ダウンロードしたデータやチェックポイントを置くローカル領域として使われます。

解くための考え方
まず、このシナリオで固定されている条件を整理します。データは合計300GB超、1ファイルあたり200MB、
保存先はすでにS3 Standardで、しかも経営向けダッシュボードへの供給元としても使われています。
評価軸は「追加のストレージ費用を抑えること」と「効率よく訓練ジョブへ取り込むこと」の2つです。
既存のS3にデータがあるという前提が明示されている以上、
データを別のストレージへ移したり複製したりする案は、その時点でストレージ料金が二重にかかります。
次に入力方式の当てはめです。データセット全体が50〜100GBを大きく超えているため、
全量をダウンロードし終えてから訓練を始めるファイルモードは起動待ちが長くなり不利です。
一方、1ファイル200MBという構成は、AWSが高速ファイルモードの理想として挙げる150MB超を満たしており、
このデータは高速ファイルモードが最も力を発揮する形状だと判断できます。
高速ファイルモードはファイルシステムの作成もVPCへの接続も不要で、
入力チャネルのモード指定を変えるだけで既存のS3 Standardをそのまま読めるため、追加のストレージ料金が一切発生しません。
残りの案はいずれも追加ストレージを前提とします。
EFSにファイルシステムを作る案も、EBSボリュームへコピーする案も、300GB分の保存領域を新たに確保する費用が発生し、
EBSではさらにダッシュボード供給元のS3とは別にコピーを維持管理する負担も生まれます。
FSx for Lustreは大量の小さなファイルやランダム読み取りが中心の場面では強力ですが、
200MBのファイルが並ぶ本件ではその強みが効かず、プロビジョニング容量に対する料金だけが上乗せされます。
したがって、既存のS3 Standardを高速ファイルモードで直接読む構成が最もコスト効率に優れます。

前提知識
SageMaker のカスタムコンテナについて
SageMaker は、利用者が用意した Docker コンテナイメージでジョブを実行する「持ち込みコンテナ」方式に対応しています。必要なライブラリや依存関係を Dockerfile に記述してイメージをビルドし、Amazon ECR にプッシュしておけば、処理ジョブ・トレーニングジョブ・パイプラインのいずれからもそのイメージ URI を指定して起動できます。処理ジョブのコンテナは、入力データが /opt/ml/processing/input/ に配置され、出力を /opt/ml/processing/output/ に書き出すという規約に従って動作し、ジョブ設定は /opt/ml/config/processingjobconfig.json などのファイル経由でコンテナに渡されます。
Amazon ECR について
Amazon ECR は Docker コンテナイメージを保存・管理するフルマネージドのコンテナレジストリです。プッシュしたイメージは IAM でアクセス制御でき、SageMaker のジョブやパイプラインからはリポジトリ名とタグを含むイメージ URI で参照します。タグやイメージダイジェストを指定して特定バージョンに固定できるため、工程をまたいで同一の実行環境を保証する用途に適しています。
SageMaker ノートブックインスタンスについて
SageMaker ノートブックインスタンスは Jupyter ノートブックを実行するマネージドな EC2 インスタンスです。起動時の環境準備にはライフサイクル設定スクリプトを使いますが、このスクリプトの実行が 5 分を超えるとインスタンスの作成・起動自体が失敗します。またノートブックはあくまで開発と操作のための環境であり、処理ジョブやトレーニングジョブ、パイプラインのステップはノートブックとは別に確保されたマネージドなコンピューティング上で実行されます。
SageMaker の組み込みアルゴリズムについて
SageMaker の組み込みアルゴリズムは、AWS が提供する固定のコンテナイメージ上で動作します。XGBoost や線形学習者などの汎用的なアルゴリズムを、データ形式とハイパーパラメータを指定するだけで利用できる手軽さが利点ですが、イメージの中身を利用者が差し替えたり、独自ライブラリを組み込んだりすることは想定されていません。独自の前処理ロジックを持ち込む場合はカスタムコンテナ、またはフレームワークコンテナへのスクリプト持ち込みが必要になります。
解くための考え方
この問題の要件は 2 つあります。処理ジョブ・トレーニングジョブ・パイプラインという複数の工程で同じ社内ライブラリを使えること、
そしてそのための実装作業を最小限に抑えることです。
着眼点になるのは、SageMaker のこれら 3 つの工程がいずれも「実行するコンテナイメージを ECR の URI で指定する」
という共通のインターフェイスを持っている、という点です。
つまり環境の実体をコンテナイメージという 1 つの成果物にまとめてしまえば、
あとは各工程で同じ URI を指すだけで環境の同一性が自動的に担保されます。
この観点で各案を見ていきます。組み込みアルゴリズムのコンテナをそのまま使う案は、
イメージが固定されていて社内ライブラリを差し込む余地がないため、そもそも要件の入口に立てません。
標準コンテナに実行時ごとにインストールする案は、動くには動きますが、
インストール手順を工程の数だけ書いて維持することになり、
パッケージのバージョンが取得タイミングで変わればトレーニング時と処理時で環境がずれる余地も残ります。
ノートブックインスタンスを実行基盤にする案は前提そのものが誤りで、
ジョブとパイプラインはノートブックとは別のマネージド環境で動くため、
ノートブックに入れたライブラリはジョブ側には届きません。
加えてライフサイクル設定スクリプトの 5 分制限や Lambda 関数の開発という余計な作業が増えます。
残る、必要なライブラリを同梱したカスタム Docker イメージを ECR に置く案だけが、
一度のビルドで全工程に同じ環境を配れるという条件を満たします。
依存関係の解決がビルド時に完了しているためジョブ起動時の追加処理も不要で、
イメージタグでバージョンを固定できるので再現性の面でも最も堅い構成になります。

前提知識
マルチコンテナエンドポイントについて
マルチコンテナエンドポイントは、1つのSageMakerエンドポイントへ異なるモデル・異なるフレームワークの推論コンテナを最大15個までデプロイできる方式です。コンテナを推論パイプラインとして順次実行することも、直接呼び出しモードでTargetContainerHostnameを指定して各コンテナへ個別にアクセスすることもできます。1つのエンドポイントに集約できるため、管理コストを抑えながらエンドポイントの稼働率を高められます。なお各コンテナは同じインスタンスを共有し、自動スケーリングはエンドポイントのバリアント単位で働くため、コンテナごとに独立してスケールするわけではありません。
マルチモデルエンドポイントについて
マルチモデルエンドポイントは、複数のモデルを1つのエンドポイントでホストする方式です。ただし、すべてのモデルが同じ推論コンテナを共有するため、同じフレームワークで構築されたモデルに限られます。モデルはリクエストに応じてストレージから動的にロードされるため、最初のリクエストではロード時間がかかります。同一フレームワークのモデルを多数まとめて効率的にホストする用途に適しています。
単一モデルエンドポイントについて
単一モデルエンドポイントは、1つのモデルをホストする方式です。複数のモデルをデプロイする場合、モデルごとにエンドポイントを管理する必要があり、台数が増えるほど管理コストと複雑さが増します。モデルを1つだけデプロイする場合には適していますが、複数モデルのデプロイにはコスト効率の面で向きません。
推論パイプラインについて
推論パイプラインは、複数のモデルを順次実行して最終的な推論結果を生成するワークフローです。前処理、特徴量エンジニアリング、モデル推論、後処理といったステップを順番に実行できます。マルチコンテナエンドポイントを使うと、フレームワークの異なる複数モデルを1つのエンドポイントでホストでき、推論パイプラインを効率的に実装できます。
AWS Glueについて
AWS Glueは、複数のソースからデータを検出・変換・統合するサーバーレスのETLサービスです。データの前処理や取り込みには適していますが、モデルをホストしてクライアントからinvoke_endpoint呼び出しで即時に推論を実行するエンドポイントは提供しません。モデルのデプロイにはSageMakerのエンドポイント機能を使います。
コスト効率性について
エンドポイントの管理コストは、エンドポイントの台数にほぼ比例して増えます。モデルごとに単一エンドポイントを立てると台数分の管理コストがかかります。マルチコンテナエンドポイントなら1つのエンドポイントへ集約でき、管理コストと複雑さの両方を抑えられます。
図による解説



フレームワークの異なる4つのモデルは、1つのSageMakerエンドポイント上の独立コンテナに同居します。クライアントは単一のinvoke_endpoint呼び出しを送り、エンドポイントが対象コンテナへルーティングして推論結果を返します。コンテナごとに別々のフレームワークを載せられるため、音声認識・物体検出・異常検知・電力予測のように技術スタックの異なるモデルをまとめられます。ここでマルチモデルエンドポイントを選ぶと全モデルが同じ推論コンテナを共有する制約にぶつかり、モデルごとに単一エンドポイントを立てると台数分の管理コストがかかります。1エンドポイントへ集約すると稼働率が上がり、管理コストを抑えられます。
解くための考え方
この問題は2つの条件を同時に満たす構成を選ばせるものです。1つはフレームワークの異なる4つのモデルを単一のinvoke_endpoint呼び出しから利用できること、もう1つは運用コストを抑えることです。どちらか一方だけを満たす選択肢が並んでいるため、両方を満たすものを見極めるのが要点になります。
まずデプロイ手段として成立するかを確認します。AWS Glueは複数のソースからデータを検出・変換・統合するサーバーレスのETLサービスであり、モデルをホストしてクライアントへ即時応答する常設エンドポイントを提供しません。推論結果をS3へ書き出す方式ではinvoke_endpointで呼び出すという前提そのものが成り立たないため、この時点で候補から外れます。
次にモデルの同居方法を見ます。マルチモデルエンドポイントも複数モデルを1つのエンドポイントでホストする方式ですが、これは同じ推論コンテナを共有して多数のモデルをホストする仕組みであり、全モデルが同一のMLフレームワークである必要があります。モデルはリクエストに応じてS3から動的にロードされるため、利用頻度の低いモデルではコールドスタートの遅延も生じます。4つのモデルがそれぞれ異なる深層学習フレームワークで構築されている今回の前提とは噛み合いません。
これに対しマルチコンテナエンドポイントは、1つのエンドポイントへ最大15個までの推論コンテナをデプロイでき、コンテナごとに別のフレームワークを載せられます。直接呼び出しモードを構成すればTargetContainerHostnameで対象コンテナを指定して個別に推論を実行できるため、単一のinvoke_endpoint呼び出しという要件を満たします。
最後にコスト面を比較します。モデルごとに単一モデルエンドポイントを4つ立てる構成も要件自体は満たしますが、作成・監視・スケーリングの対象が台数分に増え、各エンドポイントの稼働率も下がります。マルチコンテナエンドポイントへ集約すれば管理対象は1つで済み、エンドポイントの稼働率を高められるため、コスト効率の面で優れます。
