前提知識
Amazon SageMakerサーバーレスエンドポイントについて
Amazon SageMaker サーバーレスエンドポイントはトラフィックに応じて自動でスケールするエンドポイントです。リクエストが無い間はモデルインスタンスが停止され、リクエストが来ると起動とモデルの読み込みが行われます。この起動に時間がかかるため、初回リクエストのレイテンシーが高くなることがあります。この起動時間は ModelSetupTime メトリクスで測定できます。
Amazon CloudWatchメトリクスについて
Amazon CloudWatch は AWS リソースのパフォーマンスメトリクスを監視するサービスです。SageMaker エンドポイントのメトリクスは AWS/SageMaker 名前空間に含まれ、ModelSetupTime、ModelLatency、ModelLoadingWaitTime、Invocations などを観察できます。
ModelSetupTimeメトリクスについて
ModelSetupTime は、サーバーレスエンドポイントで新しいコンピューティングリソースを起動するのにかかる時間を表すメトリクスです。モデルのサイズ・ダウンロード時間・コンテナ起動時間によって値が変わります。この値が高い場合、起動時間がレイテンシー増加の原因になります。
ModelLatencyメトリクスについて
ModelLatency は、モデルがリクエストに応答するまでにかかる時間間隔を表すメトリクスです。コンテナ内の推論処理時間を含みますが、起動時間そのものを測るものではないため、起動が原因か推論が原因かを切り分けるには ModelSetupTime を見る必要があります。
ModelLoadingWaitTimeメトリクスについて
ModelLoadingWaitTime はマルチモデルエンドポイント向けのメトリクスで、呼び出しリクエストが対象モデルのダウンロード・ロードを待った時間を表します。サーバーレスエンドポイントの起動時間の全体像を測るものではありません。
AWS CloudTrailについて
AWS CloudTrail は AWS アカウント内の API 呼び出しを記録する監査サービスです。InvokeEndpoint の呼び出し主体や時刻、送信元 IP などの履歴は残しますが、起動時間やレイテンシーといったパフォーマンスメトリクスは提供しません。
レイテンシーの原因分析について
レイテンシー増加の原因を特定するには、仮説に合ったメトリクスを観察します。起動時間が原因と疑う場合、ModelSetupTime メトリクスを観察することで仮説を確認または否定できます。
解くための考え方
サーバーレスエンドポイントの起動時間は、ModelSetupTime で直接測れます。
CloudTrail の案は API 呼び出しの監査記録にしかならず、起動時間やレイテンシーの原因は分かりません。ModelLatency は推論処理時間であり、ModelLoadingWaitTime はマルチモデルエンドポイント向けのメトリクスなので、いずれも起動時間の全体像を測るものではありません。
ModelSetupTime はサーバーレスエンドポイントのコンピューティングリソース起動時間を測るメトリクスであり、値の高低で起動時間が原因かどうかを切り分けられます。

前提知識
SageMaker Model Monitorについて

SageMaker Model Monitorは、本番稼働中のモデルの品質を継続的に監視するサービスです。データ品質、モデル品質、バイアスドリフト、特徴量アトリビューションドリフトの4種類の監視を提供します。データ品質監視では、入力データの統計的特性（平均、標準偏差、分布など）を訓練データから作ったベースラインと比較し、逸脱を検出します。ベースラインからの逸脱は、2つの分布の累積分布関数の最大絶対差として計算した距離が比較しきい値（既定値0.1）を超えたかどうかで判定されます。監視結果はCloudWatchメトリクスとして出力されるため、CloudWatchアラームを設定すれば、しきい値を超えた際にSNS通知を送れます。

CloudWatch Syntheticsについて

Amazon CloudWatch Synthetics のカナリアは、スケジュールに沿って実行されるスクリプトで、エンドポイントやAPIの可用性とレイテンシーを監視します。顧客と同じ経路をたどって稼働状況を検証しますが、入力データの分布のずれ（データ品質ドリフト）を検出する機能はありません。

SageMaker Data Wranglerについて

SageMaker Data Wranglerは、視覚的なインターフェースでデータの取り込み・変換・特徴量エンジニアリングを行う訓練前のデータ準備ツールです。訓練データを作成する段階で使用するものであり、本番エンドポイントへの入力データを継続的に監視する機能は提供しません。

Amazon CloudWatchについて

Amazon CloudWatchは、メトリクスの収集・監視、ログの収集・分析、アラームの設定と通知を提供する監視サービスです。Model Monitorが監視結果をCloudWatchメトリクスとして出力するため、CloudWatchアラームを設定することで、データ品質の問題を検出した際にSNS通知などのアクションを実行できます。

図による解説



データ品質監視は、本番エンドポイントに届く入力データの統計的な性質が訓練時のデータからずれていないかを判定する仕組みです。図はある特徴量の分布を訓練時のベースライン（平均50・標準偏差10）と本番の現在値で比較しており、本番では平均が60付近へ動き、ばらつきも15へ広がって分布が右に寄っています。Model Monitorはこのような平均・標準偏差・分布の変化をベースラインと照合して逸脱を検出し、結果をCloudWatchメトリクスとして出力します。ここで「データの中身が少し変わっただけ」と軽視すると、モデルが想定外の入力を処理し続け、精度が静かに劣化します。しきい値を超えた逸脱をアラームで拾い、再訓練や入力経路の調査へつなぎます。



特徴量ドリフトとは、本番で受け取る特徴量の分布が、訓練時に使った分布から時間の経過とともにずれていく現象です。たとえばセンサーの経年変化や計測環境の違いによって、同じ特徴量の値域が徐々に変わります。図は同一の特徴量について訓練時の分布（上段）と本番の分布（下段）を並べ、本番では平均が65付近まで動き、分布の形も変わったことを示しています。Model Monitorは2つの分布の累積分布関数の最大絶対差（linf_simple、サンプル数が少ない場合は2標本コルモゴロフ・スミルノフ検定に基づくlinf_robust）で分布距離を計算し、比較しきい値を超えた場合にドリフトとして検出します。ドリフトを「予測値がまだ安定しているから」と放置すると、外れ値の増加や入力カラムの欠落など根本原因が見えないまま性能が劣化します。検出されたら再訓練やデータ収集の見直しを検討します。
解くための考え方
この問題では、アラートを飛ばす仕組みそのものではなく、アラートの根拠となる「データ品質のずれ」を誰が測るのかが問われています。
通知は監視の最終工程にすぎず、その手前には必ず、本番エンドポイントに届いた入力データをキャプチャし、訓練時のベースラインと統計的に突き合わせて逸脱を数値化する処理が要ります。
したがって選択肢を絞る基準は、その測定役を備えているかどうかの一点になります。
この基準で見ると、CloudWatchアラームとSNS通知を設定するだけの構成は、通知役はいるのに測定役がいません。
エンドポイントが標準で発行するのは呼び出し回数やレイテンシーなどの稼働系メトリクスであり、入力データの分布のずれを表す値はどこからも出てこないため、しきい値を設定する対象がありません。
CloudWatch Syntheticsのカナリアも同様で、定期的にリクエストを投げてエンドポイントが応答するかどうかを確かめる合成監視であり、実際に流れてくる入力データの中身までは見ていません。可用性とレイテンシーは正常なまま、精度だけが静かに落ちていく状況を捉えられません。
SageMaker Data Wranglerは訓練前のデータ準備を担うツールで、訓練データセットを作る工程で使うものです。本番エンドポイントに届き続けるデータを継続的に評価する役割は持ちません。
残るSageMaker Model Monitorが、まさにこの測定役として用意された機能です。
エンドポイントのデータキャプチャで入力を保存し、訓練データから作成したベースラインの統計値と比較して、平均や標準偏差、分布の変化を定期実行の監視ジョブで評価します。
逸脱の判定には2つの分布の累積分布関数の最大絶対差を用い、比較しきい値を超えた項目を違反として報告します。
その結果はCloudWatchメトリクスとして出力されるため、CloudWatchアラームでしきい値を設定してSNSへつなげば、データ品質の問題を検出した時点で自動的に通知が届きます。
測定と通知が標準機能どうしの連携で完結する点が、この構成を選ぶ決め手になります。

前提知識
ラベルの比率の差（DPL）について
ラベルの比率の差（Difference in Proportions of Labels、DPL）は、データセット内の特定のグループ（この場合は年齢範囲）で、特定のクラス（この場合は正例クラス）がどの程度過剰または不足しているかを示す指標です。DPL値が正の値（+0.9など）の場合はそのグループで正例クラスが過剰に表現されていることを、負の値の場合は不足していることを示します。0に近い場合はクラス分布がバランスしていることを示します。
オーバーサンプリングについて
オーバーサンプリングは、少数派クラスのサンプル数を増やしてデータセットのバランスを取る手法です。SMOTE（Synthetic Minority Oversampling Technique）などで既存のサンプルから新しい合成サンプルを生成できます。少数派クラスが不足している場合は有効ですが、過剰に表現されているクラスへ適用すると不均衡がさらに悪化します。
アンダーサンプリングについて
アンダーサンプリングは、多数派クラスのサンプル数を減らしてデータセットのバランスを取る手法です。ランダムにサンプルを削除する方法や、クラスタリングで代表的なサンプルを選ぶ方法などがあります。多数派クラスが過剰な場合に有効ですが、データセット全体が小さくなるため情報が失われます。
データ不均衡の影響について
データ不均衡があると、モデルは多数派クラスに偏って学習し、少数派クラスの予測性能が低下します。また、特定の特徴量（この場合は年齢）の特定の値（この場合は40歳から45歳）へ過学習する恐れがあります。データ不均衡を是正すれば、モデルは全体的にバランスの取れた学習を行い、すべてのクラスと特徴量の値に対して適切に予測できるようになります。
図による解説



年齢範囲ごとの正例・負例クラスのサンプル数とDPL値を並べると、40歳から45歳だけ正例クラスが突出して過剰に表現されています。DPLは正の値が大きいほど、そのグループで正例の割合が他より高いことを示します。40〜45歳のDPL +0.9 は、他の年齢範囲の負の値と対照的です。この不均衡を放置するとモデルがこの年齢範囲に過学習し、年齢そのものが予測の手がかりになってしまいます。是正には、過剰な側を減らす方向、すなわちこの範囲の正例クラスのアンダーサンプリングを選ぶ必要があります。



アンダーサンプリングの前後でクラス分布が変わります。処理前は40〜45歳だけ正例クラスが突出し、この年齢範囲のサンプルの大半が正例で占められています。処理後はこの範囲の正例サンプル数を他の年齢範囲と同程度まで減らすことで、特定の年齢範囲にだけ正例が偏った状態が解消され、DPLは0へ大きく近づきます。逆に、他の年齢範囲の正例を減らしたり負例を増やしたりしても、過剰な40〜45歳の正例は残ったままなので不均衡は解消されません。過剰な部分を直接減らすことだけが是正の方向として成立します。
解くための考え方
DPL値が+0.9であることは、40歳から45歳の年齢範囲で正例クラスが過剰に表現されていることを示します。
データ不均衡を是正するには、過剰に表現されている部分を削減する必要があります。40歳から45歳の年齢範囲で正例クラスをアンダーサンプリングすれば、この年齢範囲の正例クラスのサンプル数を削減し、他の年齢範囲とのバランスを取れます。これにより、モデルが特定の年齢範囲に過学習するのを防ぎ、全体的な性能を向上させられます。
一方、40歳から45歳の年齢範囲で正例クラスをオーバーサンプリングすると不均衡がさらに悪化し、この年齢範囲へ過学習する恐れがあります。40歳から45歳を除くすべての年齢範囲で正例クラスをアンダーサンプリングしたり、負例クラスをオーバーサンプリングしたりする方式では、40歳から45歳の年齢範囲の正例クラスが過剰なまま残り、データ不均衡は是正されません。
過剰に表現されている40歳から45歳の正例クラスをアンダーサンプリングすると、他の年齢範囲とのバランスが取れます。

高次元スパースデータについて
高次元スパースデータは、特徴量の数が多く、各データ点ではほとんどの値が0になるデータです。ユーザーとアイテムの相互作用では、各ユーザーが触れるアイテムはごく一部のため、行列の大部分が空になります。こうしたデータでは、スパースな特徴量の組み合わせを効率的に学習できるアルゴリズムが必要です。
図による解説



レコメンデーションの学習データは、行をユーザー、列をアイテムとする「ユーザー×アイテム行列」として表せます。各セルは閲覧や保存などの相互作用の強さを表し、ほとんどのセルが未観測の0で埋まる高次元スパースな構造になっています。緑の枠で囲んだセルは、まだ評価が無いユーザー×アイテムの組み合わせであり、モデルがスコアを予測して推薦候補にする対象です。大半が0の疎な行列を直接扱うと計算が非効率になるため、レコメンデーション向けのアルゴリズムには、スパース性を活かして潜在因子を学習する仕組みが求められます。疎な行列をそのまま近傍探索や次元削減で処理しようとすると、相互作用の情報を十分に活かせません。



因数分解機は「どの特徴量の組み合わせが推薦に効くか」を重みとして学習します。ユーザーID×アイテムID、年齢×カテゴリといった特徴量ペアごとに相互作用の重みが求まり、正の重みは推薦スコアを押し上げ、負の重みは押し下げる方向に働きます。因数分解機は高次元スパースな行列をそのまま扱うのではなく、潜在因子分解を通じて特徴量間の交互作用を学習するため、ほとんどが空の行列でも予測に必要な関係を取り出せます。単純な線形モデルでは特徴量単独の寄与しか捉えられず、ユーザーとアイテムの組み合わせに潜む相性を表現できません。因数分解機はこの交互作用を効率よく学習するため、レコメンデーションに適しています。
解くための考え方
高次元スパースなユーザー×アイテム行列から推薦スコアを出すには、特徴量間の相互作用を潜在因子で学習するアルゴリズムが必要です。因数分解機は高次元スパースデータにおける特徴量間の相互作用を効率的に学習でき、クリック予測や項目推薦に向きます。
一方、k-NNは近傍探索に基づく手法で、ユーザーとアイテムの相互作用を潜在因子としてモデル化しません。PCAは次元削減の手法で予測を行うアルゴリズムではありません。seq2seqは系列変換に特化しており、レコメンデーションとは目的が異なります。
高次元スパースデータからのレコメンデーションには、Factorization Machines（因数分解機）を使います。

ライフサイクル設定について
ライフサイクル設定は、ノートブックインスタンスの作成時や起動時にシェルスクリプトを実行するための仕組みです。Create Notebookセクションはインスタンスの作成時に1回だけ、Start Notebookセクションはインスタンスが起動するたびに実行されます。パッケージの導入や初期設定、自動化タスクに使えます。スクリプトは1つあたり16,384文字までで、実行が5分を超えると失敗しインスタンスが作成または起動されないため、常駐監視のような処理はバックグラウンドへ逃がす作りにします。
auto-stop-idleスクリプトについて
auto-stop-idleスクリプトは、ノートブックがアイドル状態になったことを検知してインスタンスを自動停止するスクリプトです。AWSのサンプルリポジトリで公開されており、ライフサイクル設定から利用できます。Jupyterのセッション情報をもとにノートブックのアクティビティを監視し、指定したアイドル時間を経過するとStopNotebookInstance APIでインスタンスを停止します。既定のアイドル時間は3600秒（1時間）で、判定処理はcronで5分間隔に実行される形で組み込まれるため、ライフサイクル設定スクリプト自体の実行は短時間で完了します。
Start NotebookとCreate Notebookの違いについて
Start Notebookセクションはインスタンスが起動するたびに実行されます。停止後に再起動した場合も実行されるため、アイドル監視を継続的に行うスクリプトに向いています。Create Notebookセクションは作成時に1回だけ実行されるため、継続的な監視には向きません。
CloudWatch LogsとCloudWatch Metricsの違いについて
CloudWatch Logsはログデータを収集・保存して検索や分析を行うサービスです。CloudWatch MetricsはCPU使用率やメモリ使用率などのメトリクスを収集・保存するサービスです。ノートブックのリソース使用率を追跡するにはCloudWatch Metricsを使います。

Amazon EventBridge Schedulerは、cron式やレート式でスケジュールを定義し、指定した時刻や間隔でAWSサービスやAPIを呼び出すサーバーレスのスケジューラです。経過時間に基づいてタスクを起動する仕組みのため、ノートブックがアイドルかどうかを判定する機能はありません。
アイドル状態の判定について
アイドル状態の判定は、単にCPU使用率やメモリ使用率がゼロかどうかでは不十分です。ノートブックの実利用状況を監視する必要があります。auto-stop-idleスクリプトはノートブックのアクティビティを監視し、指定したアイドル時間を経過するとインスタンスを停止します。この方法の方が正確にアイドル状態を検出できます。
解くための考え方
閉じ忘れによる料金を防ぐには、1時間のアイドルを正確に検知したうえで、インスタンスを再起動するたびに監視も再開される仕組みが必要です。
アイドル検知では、CPU使用率を追跡する方法もありますが、ゼロという条件だけではアイドル状態を正確に判定できず、メトリクスの収集にはログ保存が役割のCloudWatch LogsではなくCloudWatch Metricsを使うべきです。EventBridge Schedulerで起動から1時間後に停止する方法は、経過時間だけで発火するため作業中でも停止してしまい、アイドル検知にはなりません。
残る選択肢はライフサイクル設定を使う2つで、判断の分かれ目はスクリプトをどちらのセクションへ置くかだけです。Start Notebookセクションにauto-stop-idleスクリプトを配置すると、インスタンスが起動するたびにスクリプトが実行され、そのつどアイドル監視が始まります。このスクリプトはJupyterのセッション情報からノートブックの利用状況を判定するため、CPU使用率のような間接的な指標より正確にアイドルを検知でき、既定の3600秒すなわち1時間を超えるとインスタンスを自動停止します。一方、Create Notebookセクションは作成時に1回だけ実行されるセクションです。毎日作業を終えて停止し、翌日また起動するという使い方では、2回目以降の起動でスクリプトが実行されず監視が再開されないため、今回の用途には向きません。したがって、Start Notebookセクションへauto-stop-idleスクリプトを配置する構成が要件を満たします。

RMSEは回帰モデルの予測誤差を、元データと同じ単位で表すメトリクスです。図は実際の需要（青い丸）と予測値（赤い菱形）をサンプルごとに並べ、灰色の破線で各サンプルの予測誤差（残差）を示しています。RMSEはこれら誤差の二乗平均の平方根で、値が小さいほど予測が実測に近いことを意味します。誤差を二乗するため、サンプルのように大きく外れた予測が1つでもあるとRMSE全体が押し上げられ、大きな予測ミスをより重く評価する特徴があります。需要計画では大幅な読み違いが調達の無駄につながるため、大きな誤差を重く見るRMSEはMAEと比べて外れ値へのペナルティが強く、需要予測の評価に向いています。計画チームはこの値をもとにモデルの改善を進められます。

値の単位が元のデータと揃うため誤差の大きさをそのまま解釈でき、二乗を経由する分だけ大きな外れをより重く評価します。

前提知識
Amazon Managed Service for Apache Flink について
Amazon Managed Service for Apache Flink は、Apache Flink ベースのマネージドなストリーミングデータ処理サービスです。Java・Scala・Python・SQL でストリーミングデータを処理・分析でき、リアルタイムダッシュボードやメトリクスへデータを供給できます。Studio のノートブックを使うと、標準 SQL や Python でストリームを対話的にクエリし、アプリケーションを容易に構築できます。MSK や Kinesis Data Streams などのストリーミングソースと統合できます。
Amazon MSK について
Amazon MSK は Apache Kafka ベースのマネージドなストリーミングデータサービスです。高スループットの取り込みに適し、複数のコンシューマーが同じストリームを読めます。クラスターの管理・スケーリング・セキュリティを自動化し、運用負荷を抑えます。
Amazon Kinesis Data Streams と Amazon Data Firehose について
Amazon Kinesis Data Streams はリアルタイムのストリーミングデータを取り込むサービスです。Amazon Data Firehose はストリーミングデータを S3 などの宛先へ配信するサービスで、Lambda による変換はできますが、ストリームに対して SQL を直接実行することはできません。SQL 処理とノートブックの要件を満たすには別のサービスが必要です。
Amazon Athena について
Amazon Athena は S3 上のデータに SQL でクエリできるサーバーレスサービスです。スキーマオンリードで標準 SQL を実行でき、Apache Spark を使ったノートブックも利用できますが、いずれも対象は S3 に保存済みのデータであり、流れているストリームをほぼリアルタイムに処理する用途には向きません。
Amazon EMR について
Amazon EMR は Hadoop や Spark を実行するためのマネージドなクラスタープラットフォームです。Spark ストリーミングでストリーミング処理を行うことはできますが、クラスターの管理が必要で、SQL で対話的にクエリできるマネージドなノートブックや組み込みダッシュボードは提供しません。
図による解説



取り込み（MSK）・処理（Flink）・可視化（ダッシュボード）は分離され、SQL とノートブックの両方が同じ Flink の上に載ります。アプリの行動ログはまず MSK に流し込み、高スループットで取り込みます（①）。Flink は MSK からログを消費し、Flink SQL でデータを処理するとともに、Studio のノートブックから標準 SQL や Python でストリームを対話的にクエリできます（②③④）。処理結果は組み込みのダッシュボードへ送り、ほぼリアルタイムで可視化します（⑤）。Lambda・Athena・EMR のようなコード型・バッチ型の処理に置き換えると、SQL かノートブックのいずれかの要件が抜け落ち、リアルタイム性も失われます。
解くための考え方
クリックストリームはリアルタイムで処理し、SQL による処理とノートブックによる対話的な分析を同じ基盤で両立します。
リアルタイム処理にはストリーミング処理サービスが不可欠です。Managed Service for Apache Flink はストリーミングデータに SQL を実行でき、Studio のノートブックで対話的な分析もできます。
MSK は高スループットの取り込みに適し、Flink と組み合わせることでほぼリアルタイムの処理を実現できます。組み込みのダッシュボードで結果を可視化できます。
Firehose と Lambda を使う方式は SQL に対応せず、ノートブックによる対話的な分析もできません。S3 上のデータをノートブックで分析するには別のツールが必要です。
Kinesis Data Streams・Firehose・Athena を使う方式は SQL に対応しますが、Athena が扱うのは S3 に保存済みのデータであり、ストリームをそのまま処理するリアルタイム性の要件を満たせません。
MSK・EMR を使う方式は、Spark ストリーミングがコードベースで、SQL による対話的なノートブックを提供しません。クラスター管理も加わります。
MSK で取り込み、Managed Service for Apache Flink で SQL 処理とノートブック分析を行い、組み込みのダッシュボードで可視化します。

前提知識
AWS Glue DataBrewについて

AWS Glue DataBrewは、コードを書かずにデータをクリーニングして正規化できるビジュアルなデータ準備サービスです。Amazon S3、AWS Glueデータカタログ、JDBCで接続するデータベース、Amazon AppFlow、AWS Data Exchangeからデータを読み込み、異常値のフィルタリングや標準形式への変換など250種類以上の既製の変換を、グリッド状の画面から選ぶだけで適用できます。サーバーレスで動作するためクラスターの作成やインフラの管理は不要で、エンジニア以外の担当者でもデータ準備の作業を進められます。適用した変換の手順はレシピとして保存でき、再利用やバージョン管理ができます。

DataBrewデータセットについて

DataBrewデータセットは、分析や変換の対象となるデータソースを定義するものです。Amazon S3、AWS Glueデータカタログ、JDBC接続、Amazon AppFlow、AWS Data Exchangeからデータセットを作成できます。S3バケットの場合はs3://で始まるパスを直接指定してデータセットを作成し、DataBrewがスキーマを自動で検出してプレビューを表示します。フォルダーを指定すれば配下の複数ファイルをまとめて1つのデータセットとして扱えます。作成したデータセットは、プロファイルジョブやレシピジョブの入力として使われます。

DataBrewプロファイルジョブについて

DataBrewプロファイルジョブは、データセットの統計や品質を評価するためのものです。列ごとの値の分布や欠損値、重複、相関などを算出してデータプロファイルとしてS3へ出力し、コンソール上でも可視化するため、データの問題点を洗い出して適切な変換を設計する助けになります。ただし、プロファイルジョブ自体はデータの値を書き換える変換を実行しません。クリーニングや正規化などの加工を実際に行うには、レシピジョブを使う必要があります。

DataBrewレシピジョブについて

DataBrewレシピジョブは、データセット内のデータをクリーニングして正規化し、その結果を選んだ出力先へ書き出すためのものです。レシピには変換の手順を定義し、視覚的なインターフェースで組み立てられます。出力先としてAmazon S3のほか、Amazon Redshift、JDBC接続先、Snowflakeのテーブルなどを選べます。ジョブは元データを読み取り専用で参照するため、実行してもデータセットや元のデータは変更されません。レシピは再利用やバージョン管理が可能で、欠損値の処理や型変換、異常値の除去などの一般的なデータ準備作業をこなせます。

JDBC接続について

JDBC（Java Database Connectivity）は、Javaアプリケーションがリレーショナルデータベースへ接続するための標準的なAPIです。DataBrewがJDBC接続のデータソースとして検証済みと明記しているのは、Microsoft SQL Server、MySQL、Oracle、PostgreSQL、Amazon Redshift、Snowflakeです。S3バケットはオブジェクトストレージでありリレーショナルデータベースではないため、JDBCドライバーで接続することはできません。S3のデータはs3://で始まるパスを直接指定してデータセットを作成します。

解くための考え方
この問題は、DataBrewを使う手順を「データをどう取り込むか」と「取り込んだデータをどのジョブで加工するか」という2つの軸で見ると整理できます。選択肢はこの2軸の組み合わせになっており、両方が正しいものだけが答えになります。
まず取り込みの軸を見ます。S3はオブジェクトストレージであり、テーブルとスキーマを持つリレーショナルデータベースではありません。DataBrewがJDBC接続のデータソースとして検証済みと明記しているのはMicrosoft SQL Server、MySQL、Oracle、PostgreSQL、Amazon Redshift、Snowflakeで、S3はここに含まれません。S3上の検針データは、s3://で始まるパスやAWS Glueデータカタログのテーブルを指定してデータセットを作成します。この時点で、JDBCドライバーでS3へ接続するとしている選択肢は接続方法が成立せず、後段のジョブの種類にかかわらず除外できます。
次に加工の軸を見ます。今回必要なのは単位の表記揺れの統一と欠損値の処理であり、いずれも値そのものを書き換える変換です。プロファイルジョブは列ごとの値の分布や欠損値、重複、相関といった統計を算出してデータプロファイルを出力するもので、データの状態を把握して必要な変換を設計する助けにはなりますが、値を書き換えることはありません。変換を実際に適用してS3へ結果を書き出すのはレシピジョブです。したがってプロファイルジョブを加工に使うとしている選択肢も要件を満たしません。
両方の軸を満たすのは、S3のパスを指定してデータセットを作成し、レシピジョブでクリーニングと正規化を実行する手順です。レシピは250種類以上の既製の変換から選んで視覚的に組み立てられるため、コードを書かずに学習用データの準備を進められます。

前提知識
バイナリエンコーディングについて
バイナリエンコーディングは、2つの状態を0と1の1列に変換する方法です。「合格」を1、「不合格」を0にするなど、2値カテゴリカルデータを次元数を増やさずに数値化できます。モデルがそのまま学習に使える形式になります。
ラベルエンコーディングについて
ラベルエンコーディングは、各カテゴリに一意の整数を割り当てる方法です。2値カテゴリカルデータでは「合格」を1、「不合格」を0に割り当てるため、結果はバイナリエンコーディングと一致し、次元数も増えません。ただし3値以上で順序の無いカテゴリに適用すると、本来存在しない大小関係をモデルに与える恐れがある点には注意が必要です。
ワンホットエンコーディングについて
ワンホットエンコーディングは、カテゴリごとに1列を作る方法です。「合格」と「不合格」の2値では2列に増えるため、次元数を増やせないという要件に反します。カテゴリ間に順序が無い多値データに向く手法です。
標準化とトークン化について
標準化は数値特徴量を平均0・分散1へスケーリングする手法で、トークン化はテキストを分割する前処理です。どちらもカテゴリカルデータを数値の特徴量へ変換するための手法ではありません。今回の目的には該当しません。
次元数が増えることの影響について
次元数が増えるとモデルが複雑になり、過学習のリスクや計算コストが高まります。2値のカテゴリカルデータは1列のまま数値化できるため、次元数を増やさない変換が適切です。
解くための考え方
2値の「合格／不合格」は、1列のまま0と1へ直せば次元数は増えません。バイナリエンコーディングは「合格」を1、「不合格」を0に変換し、ラベルエンコーディングも2値では同じ結果になるため、いずれも次元数を増やしません。
ワンホットエンコーディングは2値でも2列に増えるため、次元数を増やしてはならないという要件に合いません。
標準化は数値のスケーリング、トークン化はテキストの分割であり、いずれもカテゴリカルデータの数値化には該当しません。

Amazon SageMaker Feature Storeについて
Amazon SageMaker Feature Storeは、特徴量をまとめて管理・保存するマネージドサービスです。オンラインストアとオフラインストアの2種類の保存先を提供します。オンラインストアはリアルタイム推論でミリ秒単位の低レイテンシアクセスに使われ、オフラインストアはバッチ処理やモデル学習で大量の特徴量へアクセスするために使われます。あわせて特徴量のバージョン管理、メタデータの保存、検索・再利用の機能も備えています。
Feature Store Spark connectorについて
Feature Store Spark connectorは、Spark DataFramesをFeature Storeへ取り込むためのコネクタです。Sparkの並列処理をそのまま使えるため、大規模データを効率的に取り込めます。特徴量グループでオンラインストアとオフラインストアを有効にすると、同じDataFrameを両方のストアへ書き込めます。Amazon EMRをはじめとするSpark環境で動作し、履歴データとストリーミングデータの両方を処理できます。
Feature Store Runtime APIについて
Feature Store Runtime APIは、個別のレコードを同期的に書き込むためのAPIです。PutRecord APIを呼び出すと、レコードをリアルタイムに反映できます。書き込み先はTargetStoresパラメータで指定でき、省略した場合は特徴量グループで有効になっているストアすべてが対象になります。ただし1回の呼び出しで扱えるのは少量のレコードのため、数億件規模のデータを一括で取り込む用途には向かず、KafkaやKinesisからのストリーミング取り込みなど、更新の鮮度を保ちたい場合に使います。
Amazon Athenaについて
Amazon Athenaは、S3上のデータを標準SQLでその場で分析するサーバーレスのクエリサービスです。インフラの管理なしにアドホックな集計や分析を実行できますが、Feature Storeのオンラインストアが提供する低レイテンシの特徴量参照や即時更新の仕組みはありません。
オンラインストアとオフラインストアの違いについて
オンラインストアは、リアルタイム推論向けに低レイテンシで特徴量へアクセスするための保存先で、高速なストレージを使ってミリ秒単位の応答を実現します。オフラインストアは、バッチ処理やモデル学習向けの保存先で、オブジェクトストレージ上に大量のデータを保存して効率的に読み出せます。両方のストアを維持することで、リアルタイム推論とバッチ学習の両方の要件を満たせます。
Amazon EMRとApache Sparkについて
Amazon EMRは、Apache Sparkなどの分散処理フレームワークを実行するためのマネージドサービスです。Sparkは大量のデータをクラスター上で並列処理するフレームワークで、Spark DataFramesを使うと構造化データを効率的に扱えます。Feature Store Spark connectorを使えば、Spark DataFramesから直接Feature Storeへデータを取り込めます。

解くための考え方
EMR上のSparkで処理した大規模データは、オンラインストアの即時更新とオフラインストアの維持の両方へ載せる必要があります。
取り込み手段を見ると、PutRecord APIはレコードを同期的に書き込むストリーミング取り込み向けのAPIで、1回の呼び出しで扱えるのは少量のレコードです。数億件規模の履歴データを1件ずつ取り込むには呼び出し回数が膨大になり、規模の面で現実的ではありません。Amazon Athenaで都度クエリして分析する方法も、オンラインストアを構築しないため即時更新の要件を満たせません。一方、Spark connectorはSpark DataFramesをそのままFeature Storeへ渡せるため、Sparkの並列処理で大規模データを効率的に取り込めます。

以上から、Amazon EMR上のSparkで処理したDataFrameをFeature Store Spark connectorへ渡し、オンラインストアとオフラインストアの両方を有効にして取り込む構成が、数億件規模の処理性能と2種類のストアの要件を同時に満たす唯一の選択肢になります。

前提知識
L1正則化（Lasso回帰）について

L1正則化は、損失関数に係数の絶対値の合計をペナルティとして加える手法です

最適化の過程で一部の係数が完全にゼロになり、スパース（疎な）解を生成します

不要な特徴量の自動的な排除（特徴量選択）に優れています

L2正則化（Ridge回帰）について

L2正則化は、損失関数に係数の二乗の合計をペナルティとして加える手法です

すべての係数をゼロに近づけますが、完全にはゼロにしません

特徴量間に高い相関（多重共線性）がある場合の係数安定化に有効です

早期停止について

早期停止は、モデルのトレーニング中に検証データの損失が改善しなくなった時点でトレーニングを停止する手法です

過学習の防止に有効ですが、特定の特徴量や項を選択的に削除する機能は持ちません

ニューラルネットワークや勾配ブースティングなどの反復学習アルゴリズムで主に使用されます

図による解説



L1 と L2 では、係数の縮小の仕方が根本的に異なります。正則化なしの係数（上段）に対し、L2正則化（Ridge）は係数の二乗にペナルティを課すため、すべての係数をゼロへ近づけますが完全にはゼロにしません。一方、L1正則化（Lasso）は係数の絶対値にペナルティを課すため、重要度の低い特徴量の係数がちょうどゼロになり、スパース解が得られます。この差が判別軸です。「係数を残しつつ縮小したい」線形回帰には L2 を、「不要な項・変数を完全に落としたい」多項式回帰・ロジスティック回帰には L1 を選びます。この違いを逆に捉えると、線形回帰に L1 を選んで必要な変数まで消してしまい、要件を満たせなくなります。



早期停止は過学習を抑える「反復の打ち切り」であり、特徴量の選択とは別の手段です。訓練損失はエポックを重ねるほど下がり続けますが、検証損失はある時点（図ではエポック15付近）を境に上昇へ転じます。この両者の乖離が、モデルが訓練データを暗記し始めた目安であり、この転換点で学習を止めるのが早期停止です。ただし、早期停止はどの特徴量や項を残すかを選ぶ機能を持ちません。不要な多項式項や冗長な予測変数を「係数をゼロにして排除する」という要件には、L1正則化が適切です。早期停止を特徴選択の代わりに使うと、モデルは過学習を抑えられても、不要な変数が残ったままになります。
解くための考え方
係数をゼロにせず縮小するなら L2、係数をゼロにして項や変数を落とすなら L1 です。早期停止は特徴量の選択ではありません。
線形回帰モデルでは「係数が縮小するがゼロにはならない」ことが求められています。L2正則化は係数の二乗にペナルティを課すため、すべての係数をゼロに近づけますが、完全にはゼロにしません。一方、L1正則化は一部の係数を完全にゼロにするため、この要件には合いません。早期停止は係数の縮小を制御する機能を持たないため不適切です。線形回帰モデルには L2正則化が適切です。
多項式回帰モデルでは「不要な多項式項を削除する」ことが求められています。「削除する」とは、不要な項の係数を完全にゼロにすることを意味します。L1正則化はスパース解を生成し、不要な係数をゼロにすることで自動的に特徴量選択を行うため、この要件に合致します。L2正則化は係数をゼロにしないため削除効果がなく、早期停止も特定の項を選択的に削除する機能はありません。
ロジスティック回帰モデルでは「冗長な予測変数を削除する」ことが求められています。高度に相関する特徴量が存在する場合、冗長な予測変数の係数をゼロにして排除する必要があります。L1正則化は相関の高い特徴量群の中から重要なものを残し、冗長なものの係数をゼロにするため、この要件にも適しています。
正しい組み合わせは、線形回帰モデルに L2正則化、多項式回帰モデルとロジスティック回帰モデルの両方に L1正則化です。

入れ子JSONを表形式へ直す作業では、標準の変換機能があるかどうかで運用オーバーヘッドが決まります。独自コードが増えるほど、開発・テスト・エラー処理の工数が残ります。
Scalaコードを自作してEMR Serverlessで実行する方法は、入れ子のJSONを表形式へ変換するロジックを一から実装する必要があり、開発と保守の工数がかかります。
Lambda関数を使う方法は、実行時間やリソースの制限により大量のデータ処理には向きません。独自コードの開発も必要です。
DynamoDBに保存する方法は、JSONをそのまま格納するだけで入れ子構造をフラットな列へ展開する変換を行わないため、XGBoostが扱う表形式の学習データにはなりません。
AWS GlueのRelationalize変換は、入れ子のJSONをフラットな表形式へ変換する専用の標準機能です。GlueのPySparkジョブはサーバーレスのマネージドサービスであり、クラスターの構築や管理が不要で実行時だけ課金されます。
Relationalize変換を使うAWS GlueのPySparkジョブなら、標準機能をサーバーレスで実行できるため、運用オーバーヘッドが小さくなります。
