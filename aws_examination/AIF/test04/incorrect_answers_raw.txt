前提知識
4つのサービスの入力と出力について

Amazon Transcribe: 音声を入力し、テキストを出力します（音声認識、ASR）。バッチの文字起こしジョブではWebVTT（.vtt）とSubRip（.srt）の字幕ファイルを直接出力する設定があり、発話に合わせた表示タイミングも付与されます。音声が含まれない場合、字幕ファイルは作成されません。

Amazon Polly: テキストを入力し、音声を出力します（音声合成、Text-to-Speech）。言語と話者の声を指定して読み上げ音声を生成します。

Amazon Translate: テキストを入力し、別の言語のテキストを出力します。入出力ともテキストで完結します。

Amazon Textract: 画像やPDFなどの書類を入力し、そこに書かれた印刷文字・手書き文字をテキストとして出力します。扱うのは紙面であって音声ではありません。

字幕・吹き替えを作る処理の流れについて

字幕は「音声 → テキスト → 別言語のテキスト」という2段階で作ります。

吹き替えは、翻訳済みのテキストからさらに「テキスト → 音声」という3段階目が必要になります。

Amazon Textractの守備範囲について

Amazon Textractが入力として受け取れるのは、JPEG、PNG、PDF、TIFFといった書類のファイルです。動画や音声のファイルは入力の形式として受け付けません。

抽出できるのは、紙面に印刷された文字や手書き文字、フォームのキーと値の組、表のセルといった要素です。文字を読み取る方向にしか働かず、テキストから音声を作る機能は持ちません。

動画の音声トラックを文字にする処理は音声認識であり、書類の画像から文字を読み取る光学文字認識（OCR）とは、入力の形式も内部の仕組みも異なります。

解くための考え方

Amazon Bedrockのカスタマイズ手法の違いについて

Fine-tuning（微調整）は、プロンプトと理想的な応答を対にしたラベル付きデータを教材にして、特定のタスクでの回答の質を引き上げる手法です。教材には「この入力にはこの回答」という対応関係が含まれています。

Continued pre-training（継続的事前学習）は、正解を付けていないラベルなしの文書をそのまま読み込ませて、特定分野の語彙や背景知識への馴染みを深める手法です。ゼロからモデルを作るのではなく、既存モデルへの追加学習です。

両者はどちらもモデルの重みを更新して専用のカスタムモデルを作る点は共通しており、教材に正解が付いているかどうかが分かれ目になります。

教材の種類について

ラベル付きデータは、入力と正しい答えがセットになったデータです。用意には人手の作業が伴うため、量を増やしにくい性質があります。

ラベルなしデータは、正解の付いていない生のテキストです。業務の中で自然に溜まっていくため、時間とともに増えるデータはこちらに該当します。

どちらの手法でも、学習データはAmazon S3に置いたJSON Lines形式のファイルとして渡し、エポック数や学習率などのハイパーパラメータを指定してカスタマイズジョブを実行します。

Fine-tuningのデータは1行が入力と期待する出力の対、Continued pre-trainingのデータは1行が本文テキストだけ、という形になります。求められる教材の形の違いが、そのまま両者の使い分けの基準です。

ジョブが完了すると元の基盤モデルとは別に専用のカスタムモデルが作られ、以降はそのモデルを呼び出して推論します。データが増えたときは、あらためてジョブを実行して作り直します。

正解の要る工程はFine-tuning、正解を付けない工程はContinued pre-trainingです。3つの対応がすべて噛み合う組み合わせは1つに絞られ、どこか1つでも担当が入れ替わると必要な教材が用意できずに破綻します。

説明
不正解 偏りの無いデータで学習し直すという方向は正しいものの、工程の規模が要件と見合いません。事前学習は数千億語規模のテキストを多数のGPUで長期間回して重みを一から作る工程で、専門の技術者と大規模な計算基盤を長く占有する必要があります。すでに使える基盤モデルが手元にある場面でこれを選ぶと、最も費用をかけずにという条件から大きく外れます。

回答は不正解です
ファインチューニング済みのモデルに、検索拡張生成（RAG）を併用します。

説明
不正解 RAGが働くのは回答を生成する段階で、質問に関係する文書を検索して入力に添えるまでが役目です。モデルの重みは更新しないため、追加学習で身に付いた選考の癖はそのまま残ります。参照先に公平な選考基準の文書を置いたとしても、すでに重みへ刻まれた判断の傾向を上書きできる保証はなく、手を入れるべき層がずれています。

説明
不正解 Configが追跡するのは、AWSリソースの設定値がいつどう変わったかという構成の履歴です。インスタンスの種類や暗号化の有無といった設定を記録し、定めたルールに沿っているかを判定します。追跡の対象はあくまでインフラの構成であり、選考モデルが出した結果を評価する機能は備えていません。通過率の偏りは、このサービスの検知範囲の外にあります。

説明
正解 通過のペースに差が出たのは、追加学習に使った応募データの属性グループごとの件数や内容に偏りがあり、モデルがそれを判定の手がかりとして覚えたためです。不足していたグループのデータを補って学び直せば、この手がかり自体を修正できます。土台の基盤モデルは流用できるので、費用は追加データの用意と再学習の分だけで済みます。

全体的な説明
問われている要件

ファインチューニング済みのLLMが、特定の属性グループを他より速いペースで通過させている状態を是正する。

監査で指摘された属性グループ間の偏り（バイアス）を、モデルの判断そのものから取り除く。

取りうる手段のうち、最も費用をかけずに済むものを選ぶ。

モデルの重みに手を入れる対策と、推論時に情報を足すだけの対策、AWSリソースを記録する仕組みを区別する。

前提知識
モデルに手を入れる工程と規模について

事前学習（Pre-training）: 基盤モデルを白紙の状態から大量のテキストで学習させる工程です。数千億語規模のデータと、多数のGPUを長期間占有する計算基盤を要します。

ファインチューニング（Fine-tuning、追加学習）: 学習済みの基盤モデルに目的に沿ったデータを追加で学習させ、重みを調整する工程です。土台を流用するため、事前学習に比べて必要なデータ量も計算量も桁違いに小さくなります。

どちらも重みを更新する点は同じで、費用の差は「どこから始めるか」から生まれます。

RAGについて

RAG（Retrieval Augmented Generation、検索拡張生成）は、質問に関連する文書を外部から検索し、その内容を入力に添えてから回答を生成させる手法です。

働くのは推論のときで、モデルの重みは変わりません。社内規程や最新の情報を回答に反映させたい場面に向きます。

バイアスについて

バイアス（偏り）とは、モデルの出力が特定のグループに対して系統的に不利または有利になる状態を指します。

原因の多くは学習データの側にあります。ある属性グループの件数が少ない、過去の判断そのものに偏りがあったといった場合、モデルはその傾向を再現します。

したがって是正の基本は、データの構成を直してから学習をやり直すことです。監査で発覚した偏りは、通過率などの指標をグループ別に比較して確認します。

図解



解くための考え方
偏りが入ったのは、ファインチューニングによってモデルの重みに判断の癖が刻まれた時点です。重みに触れない対策では直りません。RAGは回答の際に参考文書を差し挟むだけで、学習済みの癖には手を付けません。AWS Configが見ているのはAWSリソースの設定であって、モデルの出力ではありません。
残るのは、多様なデータを足してもう一度ファインチューニングする方法と、基盤モデルを白紙から事前学習し直す方法です。両者とも重みを更新するので偏りには届きますが、事前学習はゼロから作り直す工程で、必要なデータと計算時間が桁違いに大きくなります。既に動いている基盤モデルを土台にできる以上、ファインチューニングの方が費用を抑えられます。
バイアス是正では、まずモデルの重みを更新するかを見ます。更新する手段が複数あるときは、学習済みの土台を使うか、ゼロから始めるかでコストが決まります。

説明

前提知識
回答の正しさを測る指標について

適合率(Precision): モデルが正しいと判断して出力した内容のうち、実際に正解と一致していた割合です。誤りをどれだけ混ぜていないかを表しますが、答えるべき内容の取りこぼしは値に現れません。

再現率(Recall): 本来正解として含まれるべき内容のうち、モデルが実際に出力できた割合です。漏れの少なさを表しますが、余計な出力の多さは値に現れません。

F1スコア: 適合率と再現率の調和平均です。片方だけが高くても値は伸びないため、2つのつり合いを1つの数値で見たいときに使います。Amazon Bedrockの自動評価では、質問応答タスクの正確性を測る指標としてNLP-F1が採用されています。

そのほかの観点を測る指標について

単語誤り率(Word Error Rate): 2つの文章を突き合わせ、単語の置換・削除・挿入がどれだけ発生したかを割合で示します。音声認識の書き起こし精度の評価で広く使われるほか、Amazon Bedrockの自動評価では一般的なテキスト生成タスクの堅牢性を測る指標としても使われます。

初回トークンまでの時間(Time to First Token): 要求を送ってから最初のトークンが返るまでの時間で、利用者の体感の待ち時間を表す性能側の指標です。トークンとは、モデルが文章を処理する際に扱う文字列のまとまりを指します。

図解



解くための考え方
確かめたいのは、ファインチューニングで回答の中身が良くなったかどうかです。速さでも出力の安定性でもありません。問い合わせ窓口では、正しさに加えて「答えるべきことを落としていないか」も見る必要があります。
初回トークンまでの時間は速度の指標なので、内容とは無関係です。単語誤り率は文章同士のずれを測るもので、書き起こしや出力のぶれには向きますが、答えの正しさの採点には使いません。適合率とF1スコアはどちらも正しさに関わりますが、適合率は出した回答の正しさだけを見るため、答える範囲を絞ると取りこぼしが増えても値が上がります。正しさと漏れを1つにまとめるF1スコアだけが前後比較に耐えます。
秒やミリ秒なら速度、割合なら精度です。精度の中では、片側だけの適合率・再現率と、両方をまとめるF1スコアを、取りこぼしを見るかどうかで分けます。

前提知識
運用系サービスが記録している情報の違いについて

Amazon CloudWatch: 稼働中のリソースやアプリケーションから、時間とともに変化する数値（メトリクス）とログを集めます。しきい値を超えたときに通知するアラームや、推移を並べて見るダッシュボードを作れます。

AWS CloudTrail: アカウント内で呼ばれたAPIを、実行者・時刻・引数・送信元IPとともに一件ずつ記録します。監査や原因調査で使います。

AWS Config: リソースの設定値の状態と、その変化の履歴を記録します。定めたルールへの準拠を判定できます。

AWS Trusted Advisor: アカウントの構成を点検し、推奨事項から外れている項目を一覧で示します。コスト最適化やセキュリティのほか、パフォーマンスの点検項目もあります。

推論エンドポイントの性能を表す指標について

Amazon SageMaker AIで推論エンドポイントを動かすと、AWS/SageMakerという名前空間のメトリクスがCloudWatchへ送られます。呼び出し回数のInvocations、モデルが応答に要した時間のModelLatency、SageMaker AI側の処理時間のOverheadLatency、エラー数のInvocation4XXErrors・Invocation5XXErrorsなどがあります。

呼び出し系のメトリクスは既定で1分間隔で送られます。拡張メトリクスを有効にすると、発行頻度を10秒から300秒までのあらかじめ決められた値から選べます。傷の判別が遅くなった、失敗が増えたといった変化は、これらの指標の推移として現れます。

CloudWatchで継続監視を組み立てる要素について

メトリクスは指定した期間ごとに統計値としてまとめられ、標準の1分粒度のほか、高解像度メトリクスでは1秒単位まで細かくできます。データは自動的に集約されながら最長15か月保持されるため、長期の傾向も追えます。

アラームは監視する指標としきい値の組で定義し、評価期間のうち何回条件を満たしたかで警報状態に移ります。一時的な揺れで警報にならないよう評価回数を調整でき、状態が変わるとAmazon SNSへの通知や自動アクションを起こせます。

監視対象が増えてもマネージドサービス側で受け入れ容量が確保されるため、収集用のサーバーを利用者が増設する必要はありません。

図解



解くための考え方
運用系の4サービスは見た目の役割が似ていますが、残す情報の種類が違います。今回担当者が追いたいのは、傷検出の応答速度や失敗件数といった、時間とともに上下する数値です。時系列の数値を休まず受け取り続ける仕組みが必要です。
CloudTrailが保存するのはAPI操作の履歴、Configが保存するのはリソース設定の変更記録です。どちらも「起きたこと」を残すだけで、応答時間の推移は含まれません。Trusted Advisorが返すのは点検結果のリストで、パフォーマンス項目はあっても、それは推奨事項であって数値の継続監視ではありません。
CloudWatchだけが、指標を継続的に集め、しきい値超えで通知します。監視対象の増減に応じて基盤を組み直す必要もないため、スケーラビリティの条件を満たします。
監視では「変化し続ける数値」か「出来事・設定の記録」かで分かれます。数値ならCloudWatch、操作履歴ならCloudTrail、構成の記録ならConfig、改善提案ならTrusted Advisorです。

前提知識
AI・機械学習の基礎用語について

推論（Inference）とは、学習済みのモデルに新しいデータを入力し、予測結果を得る処理のことです。

モデルのバージョン管理とは、学習を重ねるたびに更新されるモデルを区別し、どの時点のモデルを本番環境で使っているかを追跡できるようにする取り組みです。

モデルの版を管理する機能について

SageMaker Model Registryは、学習済みモデルを本番用にカタログ化し、モデルグループの中でバージョンを管理する機能です。学習時の評価指標などのメタデータを版に紐づけ、承認状態を管理し、系統（リネージ）をたどれます。承認済みの版から本番へのデプロイやCI/CDの自動化につなげる起点にもなりますが、レジストリ自体が推論リクエストを処理するわけではありません。

推論を実行する機能について

SageMaker Serverless Inferenceは、基盤となるインフラを設定・管理せずにモデルをデプロイし、トラフィックに応じて自動で計算リソースを増減させる推論の形態です。エンドポイントに割り当てるメモリは1024MBから6144MBまでの範囲で選び、1つのエンドポイントあたりの同時呼び出しは最大200までです。トラフィックが途切れた後の呼び出しではコールドスタートが起きることがあり、プロビジョンド同時実行で緩和できます。

特徴量を管理する機能について

SageMaker Feature Storeは、機械学習で使う特徴量を特徴量グループという単位で保存し、チームやプロジェクトをまたいで検索・再利用・共有できるようにする機能です。ミリ秒単位で最新のレコードを読み出すオンラインストアと、履歴をすべてAmazon S3に蓄えるオフラインストアがあり、学習時と推論時で同じ特徴量を使えるようにしてずれを防ぎます。扱う対象はモデルへ入力する特徴量の値であり、モデルの版そのものでも、予測を返す仕組みでもありません。

あとは成果物の形で残りを突き合わせます。版を区別して追うには、版ごとの評価指標と承認状態が残る台帳が必要で、これはModel Registryの仕事です。モデルグループの中に学習のたびに新しい版が積み上がり、どの版を本番へ進めてよいかを承認状態で管理できます。現在のモデルで予測するには、入力を受けて結果を返す動いている環境が必要で、これをサーバーの用意なしに実現するのがServerless Inferenceです。

コンプライアンス関連文書を扱うサービスについて
